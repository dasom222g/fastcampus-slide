# 스킬과 플러그인이란 스토리보드

## 주제 도출

- 한 줄 주제: 스킬은 에이전트에게 특정 업무 능력을 더하는 가이드 문서이며, 업무 방식의 재사용과 공통 기준 적용을 돕는다.
- 청중: 에이전트를 사용해 본 비개발자 실무자. Input·Output이라는 용어를 선행 지식으로 두지 않는다.
- 구성: 10장. 강사 승인 순서 그대로 제작한다.
- 근거: 2026-09-19 강사 확정안과 소스 문서의 공식 근거.
- 시각: 기존 타이포·도트·색·에이전트 SVG·로고를 사용한다. 신규 이미지 생성은 필요 없다.
- 색: 요청 purple, 반복 전달 부담 orange, 스킬과 실행 brand, 결과 green. 문서 그림은 중립 카드와 회색 줄로 두고 제목 줄·표 머리·목록 점에만 green을 쓴다.
- 2·3·5·6장의 요청 → 에이전트 → 결과 도식은 무료 세미나 덱 `multi-agent-design.html`의 Input·Output 장과 같은 크기·스타일을 쓴다. 영문 Input·Output 라벨, 접힌 모서리, 순서형 회차 라벨은 넣지 않는다.
- 대응: 2↔5는 기준의 보관 위치, 3↔6은 결과의 형식을 비교한다.

## 1. 스킬과 플러그인이란

- 유형: COVER_SCENE. 기존 표지 유지.
- 핵심 메시지: 한 번 정한 기준을 다음 작업에도 사용한다.
- 제목: 스킬과 플러그인이란.
- 부제: 반복 업무를 위한 작업 기준.
- 선언: 한 번 정한 기준 / 다음 작업에도.
- 도식: 스킬 문서 → 에이전트 → 결과물. 기존 크기·자리·색 그대로.
- 등장: 선언과 스킬 → 연결 → 에이전트 → 결과물.

## 2. 매번 다시 주는 기준

- 유형: PROCESS_STRIP의 요청 상세 변형. 문제 1.
- 핵심 메시지: 새 업무를 맡길 때 일하는 방법까지 다시 작성·복사·전달한다.
- 제목: 매번 다시 주는 기준. ‘기준’ brand.
- 부제: 새 작업마다 일하는 방법도 다시 설명합니다.
- 요청 경계 안: ‘상품 소개글 써줘’, 상품 정보, 작업 절차, 작성 기준, 참고자료.
- 요청 카드는 purple 테두리와 따옴표. 이번 자료인 상품 정보는 회색 줄, 반복 전달하는 작업 절차·작성 기준·참고자료는 한 줄의 orange 묶음. 뒤에 겹친 요청 문서 윤곽으로 반복을 표시한다.
- 요청 하단: 매번 작성 · 복사 · 첨부.
- 구조: 요청 → 에이전트 → 소개글. 5장과 같은 중심축·위치·크기.
- 등장: 요청 자료 → 반복 기준 묶음 → 에이전트와 결과.
- 발표: 프롬프트 자체의 한계가 아니라 대화마다 기준을 다시 주는 방식의 부담을 설명한다.

## 3. 매번 달라지는 결과

- 유형: PROCESS_STRIP. 문제 2.
- 핵심 메시지: 같은 요청에도 결과의 형식은 달라질 수 있다.
- 제목: 매번 달라지는 결과. ‘결과’ brand.
- 부제: 같은 요청이어도 결과의 형식은 달라질 수 있습니다.
- 구조: 요청(상품 정보 / 상품 소개글 써줘) → 에이전트 → 문단·표·목록.
- 같은 크기의 중립 문서 카드 세 장. 문단은 연속 줄, 표는 헤더와 셀의 격자, 목록은 점과 항목 줄로 표현한다.
- 문단·표·목록 라벨은 각 문서 아래에 한 번씩만 쓴다. 결과 제목 오른쪽에 ‘반복 요청 시 가능한 결과’. 순서형 라벨은 쓰지 않는다.
- 요청 제목 purple, 결과 제목 green, 문서 라벨은 기본 글자색. 6장과 좌표·크기를 맞춘다.
- 등장: 요청 → 에이전트 → 결과 영역 → 각 형식.
- 발표: 같은 요청으로 나올 수 있는 결과 예시다. 세 워커나 세 상품을 동시에 실행하는 장면으로 설명하지 않는다.

## 4. 스킬이란

- 유형: SCENE_PAIR. 정의는 선언과 실제 역할로 표현한다.
- 핵심 메시지: 에이전트에게 특정 업무 능력을 더하는 가이드 문서.
- 제목: 스킬이란. ‘스킬’ brand.
- 부제: 특정 업무를 수행하는 방법을 알려줍니다.
- 선언: 에이전트에게 / 특정 업무 능력을 더하는 / 가이드 문서. 마지막 구절 brand.
- 도식: 가이드 문서(SKILL.md)에서 에이전트로 짧은 화살표. 에이전트 아래 ‘상품 소개글 작성’ 역할 라벨. 아이콘과 라벨 두 줄을 한 묶음으로 보고 그 묶음의 세로 중심을 문서 중심에 맞춘다.
- 문서 내부는 큰 제목 ‘가이드’와 줄 도형만. 작업 절차·출력 형식 항목 목록으로 정의를 대신하지 않는다.
- 등장: 선언 → 가이드 문서 → 연결 → 에이전트와 업무 역할.
- 발표: 스킬은 별도의 실행 주체나 새 모델이 아니며, 실제 작업은 지침을 읽은 에이전트가 수행한다.

## 5. 저장과 재사용

- 유형: PROCESS_STRIP. 문제 1의 대응.
- 핵심 메시지: 지침은 저장해 꺼내 쓰고 이번 자료와 짧은 요청만 전달한다.
- 제목: 저장과 재사용. ‘재사용’ brand.
- 부제: 업무 자료와 짧은 요청에 저장해 둔 스킬을 더합니다.
- 요청 경계 안: 상품 정보 / 이 스킬로 소개글 써줘.
- 요청의 뒤쪽 반복 문서 윤곽은 제거한다. 2장에 있던 작업 절차·작성 기준·참고자료는 에이전트 위 스킬 문서로 이동한다.
- 에이전트 위에 `SKILL.md` 라벨과 줄 도형만 있는 작은 문서 하나. 스킬을 쥐여준다는 것만 표현한다. 항목 목록·‘한 번 저장’·‘다음 작업 · 동료와 공유’ 문구는 화면에 올리지 않고 대본으로 설명한다.
- 스킬은 누가 에이전트에 넣어주는 것이 아니라 에이전트가 찾아서 읽는 것이다. 화살표는 에이전트 → `SKILL.md`(위쪽), 라벨 없음. 에이전트 아이콘 아래 ‘에이전트’ 이름도 5·6장에서는 쓰지 않는다(2·3장에서 이미 소개). 요청은 따로 에이전트로 들어간다. 요청이 스킬을 통과하는 파이프라인으로 그리지 않는다.
- 결과: 2장과 같은 위치의 소개글.
- 등장: 이번 요청 → 저장된 스킬 → 지침 연결 → 에이전트와 결과.
- 발표: 재사용은 요청 자체의 소멸이 아니라 반복 설명의 감소다. 동료는 공유받은 스킬을 자신의 작업 환경에서 사용할 수 있다.

## 6. 공통 기준의 적용

- 유형: PROCESS_STRIP. 문제 2의 대응.
- 핵심 메시지: 저장된 공통 형식에 따라 결과를 작성한다.
- 제목: 공통 기준의 적용. ‘공통 기준’ brand.
- 부제: 같은 작성 기준을 적용해 결과 형식의 편차를 줄입니다.
- 3장과 같은 요청·에이전트·결과 좌표. 에이전트 위에 스킬을 추가한다.
- 에이전트 위 문서는 5장과 같은 `SKILL.md` 문서, 같은 에이전트 → `SKILL.md` 화살표. 라벨과 에이전트 이름 없음. 한 줄 소개·주요 장점·구매 안내 구성은 화면에 적지 않고 대본으로 설명한다.
- 결과: 같은 세 구획의 문서 세 개. 줄 길이는 달라 내용까지 같아진다는 오해를 피한다.
- 결과 제목 오른쪽에 3장과 같은 ‘반복 요청 시 가능한 결과’. 각 문서 아래 라벨은 모두 ‘공통 형식’. 3장과 같은 자리의 라벨이 하나로 같아진 것으로 대비한다. 순서형 라벨 없음.
- 등장: 요청 → 스킬 → 에이전트 → 공통 형식의 결과.
- 발표: 예시 형식은 원리를 설명하기 위한 것이며 결과의 정확성이나 동일 문장을 보장하지 않는다.

## 7. SKILL.md의 구성

- 유형: RECORD_ANATOMY. 기존 구성·크기를 유지한다.
- 제목: SKILL.md의 구성.
- 부제: 이름·설명은 필수, 본문은 업무에 맞게 구성합니다.
- 파일 상단: name / 스킬 이름, description / 무엇을 · 언제. 옆 라벨 필수 정보.
- 본문: 작업 흐름 / 결과물·작성 규칙 / 주의사항·확인 기준 / 참조 파일·읽을 시점. 옆 라벨 권장 구성.
- 등장: 파일 경계 → 파일명 → 필수 정보 → 본문과 권장 라벨.
- 근거: Agent Skills specification의 frontmatter와 body content.

## 8. 참고자료의 분리

- 유형: PROCESS_STRIP. 기존 로딩 순서 도식 유지.
- 제목: 참고자료의 분리.
- 부제: 핵심 지침은 본문에, 긴 설명과 예시는 별도 파일에 둡니다.
- 순서: 스킬을 찾을 때 이름·설명 → 사용 결정 후 본문 → 필요할 때 참고자료.
- 파일명: SKILL.md / SKILL.md / references/.
- references/ 안의 파일: 상세페이지 템플릿 / 리뷰 답글 템플릿(강사 지정). 이번 작업(상세페이지 소개글)에 맞는 첫 파일만 brand로 선택하고, 이번 작업에 필요 없는 둘째 파일은 흐리게 둔다. 작업에 따라 읽는 파일이 다르고, 필요 없는 파일은 읽지 않는다는 점을 표현한다. ‘상세 지침·예시’ 같은 자료 종류 이름은 쓰지 않는다.
- 하단: 참조 파일의 위치와 읽을 시점은 SKILL.md에 안내.
- 등장: 세 조건과 자료를 순서대로 노출.
- 근거: Agent Skills specification의 progressive disclosure와 file references.

## 9. 플러그인의 역할

- 유형: CONTAINED_STRUCTURE. 기존 패키지 경계와 세 구성 유지.
- 제목: 플러그인의 역할.
- 부제: 스킬과 관련 기능을 함께 설치하는 묶음입니다.
- 경계 안: 스킬 / 도구 연결(MCP) / 추가 기능(훅). 짧은 보조 라벨로 실제 기능과 연결한다.
- 등장: 패키지 경계 → 스킬 → 도구 연결 → 추가 기능.
- 발표: 기존 구체 예시 대본 유지. MCP 연결 설정과 실제 도구, 훅 설정과 실행 스크립트의 차이를 설명한다.

## 10. 스킬을 쓰는 이유

- 유형: SCENE_PAIR. 기존 중앙 선언과 하단 도식 유지.
- 제목: 스킬을 쓰는 이유. ‘이유’ brand.
- 부제: 작업 방식을 쌓고, 다시 쓰고, 함께 활용합니다.
- 선언: 반복되는 업무를 / 재사용 가능한 시스템으로. ‘시스템’ brand.
- 구조: 스킬 → 에이전트 → 결과물.
- 등장: 선언 두 줄 → 스킬 → 에이전트 → 결과물.
- 발표: 시스템은 저장한 업무 방식과 필요한 자료를 에이전트가 재사용하는 구조이며, 스킬 자체의 독립 실행을 뜻하지 않는다.
