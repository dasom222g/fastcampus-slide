# 목표와 작업, 실행의 흐름

제작 목표: 목표 하나가 작업으로 나뉘고, 실행과 검토를 거쳐 결과로 모입니다.

소스: 사용자가 채팅으로 제공한 이전 강의 8~11장 대본의 핵심 메시지. 새로운 두 클립에 맞춰 분리·재구성한다.

## 현재 가이드와 대조한 내용

- 근거: 2026-09-09 로컬 `orca skills get orchestration` 전체 응답. 공식 공개 가이드: https://github.com/stablyai/orca/blob/main/skill-guides/orchestration.md
- Run은 지속되는 작업 네임스페이스와 코디네이터 수신함이다. 스스로 작업 순서나 배치를 결정하는 스케줄러가 아니다.
- Task는 업무 명세, Dispatch는 한 Task의 실행 시도를 담당 에이전트 터미널에 배정하는 관계다.
- 터미널 생성·준비·배정을 함께 수행하는 현재 권장 경로는 `worker-start`. 낮은 수준의 `dispatch --inject` 자체가 터미널 생성은 아니다.
- 스킬 문서가 독립적으로 실행되는 AI라는 표현은 쓰지 않는다. 에이전트가 스킬을 읽고 Orca의 도구를 사용한다.
- `question`은 워커→코디네이터, `reply`는 응답 동작으로 반대 방향, `worker_done`은 워커→담당 Run의 코디네이터로 전달된다. 이 셋을 전체 메시지 타입의 완전한 목록이라고 하지 않는다.
- `status`, `heartbeat`, `escalation` 등 다른 메시지도 있다. 개수는 고정하지 않는다.
- 작업 결정 게이트는 코디네이터가 관리한다. 워커 질문에 답하는 `ask/reply`와 구별한다.
- 완료 보고에는 성공/실패가 있으며, 보고가 도착했다고 산출물의 품질이 보장되는 것은 아니다.
- 작업 중 대기는 질문과 보고를 처리하는 단계다. 코디네이터가 아무것도 하지 않거나 언제나 동시에 대화 가능하다고 보장하지 않는다.
- 완료된 워커 터미널의 정리는 `worker-release`로 수행하며, 작업 폴더와 결과물을 지우는 의미가 아니다. 정리는 취합 명령이 아니므로 화면의 마지막 단계 명령은 정리 작업을 대표한다.
- 새 워커마다 새 워크트리가 필수인 것은 아니다. 도식의 분리된 폴더는 같은 파일의 동시 수정 충돌을 피하려는 배치 예시다.
- 오케스트레이션은 Orca에만 존재하는 개념이 아니다. 사람이 반복하던 전달은 줄지만 목표·기준·필요한 판단은 여전히 사람이 제공한다.

## 슬라이드 1. 목표와 작업, 실행의 흐름

역할: 목표를 실행 가능한 작업으로 바꾸고 끝까지 관리한다.

말할 내용: 앞에서는 누가 협업을 조율하는지 봤습니다. 이번에는 목표 하나가 어떤 단계를 거쳐 결과가 되는지 따라가겠습니다.

화면 부제: 목표 하나가 작업으로 나뉘고, 실행과 검토를 거쳐 결과로 모입니다.

화면 문구:
- 하나의 목표가
- 결과가 되기까지
- 목표
- 결과

시각: 목표 문서에서 개별 작업으로 갈라졌다가 결과 문서로 모이는 가로 도식. 실제 명령 목록은 표지에 넣지 않는다.

시각: 요청 문장 하나를 크게 두고 아래 입력·결과물·기준 세 줄을 열린 문서 형태로 정리. 사용자 아이콘과 문서 구조.

## 슬라이드 3. Run이란

**역할:** Run의 전체 목표·개별 Task·메시지 수신함을 함께 설명하고 다음 장의 실행 흐름으로 연결한다.

**핵심 메시지:** Run은 목표(objective)를 등록하고, 그 목표에 속한 개별 Task와 코디네이터의 메시지 수신함을 연결하는 관리 단위다. 물리적 폴더 구조가 아니다.

**근거:** 사용자 요청 및 공식 가이드의 run-create --objective, durable namespace / coordinator inbox 정의. https://github.com/stablyai/orca/blob/main/skill-guides/orchestration.md

**화면 문구**
- 상단 라벨: Part 4 · ch01-02 · 목표와 작업, 실행의 흐름
- 제목: **Run**이란
- 부제: Run은 하나의 목표와 그에 속하는 Task, 메시지를 통합 관리하는 단위입니다.
- Run
- 목표 · Objective
- 회사 소개 자료로 블로그와 카드뉴스 초안 만들기
- Task · 실행할 작업 하나
- Task A / 자료 정리
- Task B / 블로그 초안
- Task C / 카드뉴스 초안
- 메시지
- Coordinator 수신함
- 질문 · 완료 보고

**구조:** 하나의 회색 Run 경계 상단에 목표를 명시한다. 하단 왼쪽에 세 Task를 문서 도식으로 나란히 배치하고, 오른쪽에 메시지 수신함을 둔다. 수신함 그림에는 질문과 완료 보고를 상징하는 말풍선·체크를 표시한다. 목표는 상단의 전체 폭을 차지하고 Task와 수신함은 같은 목표 아래의 대등한 구성으로 구분한다. 물리적 폴더 아이콘이나 실행 순서 화살표는 사용하지 않는다.

**디자인·등장:** Run은 회색, Task A는 노랑·B는 brand·C는 purple로 다음 의존 관계 장과 연결한다. 수신함은 회색, 질문은 orange, 완료 보고는 green. Run·목표 → Task 그룹 → Task A·B·C → 메시지 수신함 순서로 제자리 등장. 단순한 포함 관계를 보여준다.

## 슬라이드 4. 오케스트레이션 실행 흐름

역할: 목표를 받은 뒤의 전체 오케스트레이션 흐름을 먼저 보여주고, 이후 장에서 각 단계를 풀어 설명할 기준을 만든다.

말할 내용: 목표를 받으면 전체 작업을 등록하고, 할 일을 나누고, 워커를 실행합니다. 보고와 결과를 확인한 뒤 취합하고 정리합니다. 이후 장에서는 이 흐름을 앞에서부터 구체적으로 살펴봅니다.

화면 부제: Coordinator가 목표를 Task로 쪼개고, 워커 배정부터 결과 확인·정리까지 맡습니다.

화면 문구:
- Run 생성
- run-create
- Task 설계
- task-create
- 워커 실행
- worker-start
- 보고 · 검토
- check --wait
- 취합 · 정리
- worker-release
- 결과를 확인한 뒤, 완료된 워커의 터미널을 정리합니다.

시각: 다섯 단계 가로 흐름, 실제 명령명은 작은 보조 라벨. 각 단계와 연결선이 교대로 등장. 마지막 단계는 결과 파일과 완료 체크.
## 슬라이드 5. Task의 의존 관계

역할: 앞 작업의 결과가 필요한 관계를 Task의 의존 관계로 정한다.

말할 내용: 아직 정리되지 않은 자료를 쓰는 작업을 먼저 돌리지 않습니다. 자료 정리를 선행 작업으로 연결하고, 이후의 두 작업은 서로 기다릴 필요가 없게 설계합니다.

화면 부제: 이전 작업의 결과물이 필요한 작업은, 그 작업이 끝나야 시작할 수 있습니다.

화면 문구:
- 자료 정리
- 공통으로 사용할 핵심 내용
- 블로그 초안
- 카드뉴스 초안
- 먼저 끝나야 하는 작업
- 이전작업 완료 후 시작 가능

시각: 왼쪽 자료 정리에서 오른쪽 블로그/카드뉴스로 분기. 공통 입력 문서를 가지 끝에서 전달. 선이 시작점부터 자라고 이후 작업 등장.

**Task 표시:** 자료 정리는 Task A, 블로그 초안은 Task B, 카드뉴스 초안은 Task C로 표시한다. 각 문서 아이콘 옆에 해당 색의 작은 라벨을 붙인다. A가 끝난 뒤 B와 C가 각각 시작할 수 있는 의존 관계이며 B→C 순서를 뜻하지 않는다.

## 슬라이드 6. 배정과 실행

역할: 실행할 Task별로 Worker를 배정하며, Dispatch가 그 실행 시도와 담당자를 연결한다.

말할 내용: 앞에서 나눈 Task에 실제 담당자를 붙이는 단계다. Task A는 Dispatch를 통해 Worker A에게, Task B는 별도의 Dispatch를 통해 Worker B에게 배정하는 예시다. Dispatch는 Task의 실행 시도와 담당자를 연결하는 기록이다. 현재 worker-start는 터미널 준비와 작업 배정을 함께 처리한다.

화면 부제: Dispatch는 실행할 Task와 담당 워커를 연결하는 배정입니다.

화면 문구:
- Task A
- Task B
- Dispatch
- Worker A
- Worker B
- worker-start
- 터미널 준비와 작업 배정을 함께 처리

시각: 두 행으로 Task A → Dispatch → Worker A, Task B → Dispatch → Worker B를 배치한다. 구체적인 작업 내용은 제거하고 앞 장의 Task 명칭을 이어 쓴다. 문서와 워커 아이콘 중심에 화살표를 맞추며 각 행의 세 이름은 같은 기준선에 놓는다. Task A 노랑·Task B brand, Worker A brand·Worker B purple, 배정 화살표는 노랑으로 기존 대상 색을 유지한다.

애니메이션: 두 Task → 두 Dispatch 연결 → 두 Worker → worker-start 보조 설명. 두 행은 함께 비교하되 작업·배정·담당자가 구분되어 등장한다.

## 슬라이드 7. 실행 중의 조율

역할: 대기는 메시지를 처리하며 협업을 이어가는 과정이다.

말할 내용: 한 작업의 보고를 받아도 다른 작업이 남아 있으면 계속 관리합니다. 질문은 기준으로 답하고, 필요한 판단은 사람에게 확인합니다.

화면 부제: 코디네이터는 보고와 질문을 받아 다음 작업을 이어갑니다.

화면 문구:
- Coordinator
- 보고 확인 · 질문 응답
- Worker A
- 블로그 초안
- 완료 보고
- Worker B
- 카드뉴스 초안
- 확인 질문
- worker_done
- question
- reply
- check --wait

시각: 왼쪽 코디네이터와 오른쪽 두 워커. A는 초록 체크, B는 주황 물음표. A의 완료, B의 질문, 코디네이터의 답변을 서로 다른 화살표로 순서대로.

## 슬라이드 8. 다음 단계의 판단

역할: 완료 보고와 다음 단계로 넘어갈 판단을 구분한다.

말할 내용: Task A의 완료 보고를 받은 뒤 기준을 확인합니다. 통과하면 Task B를 실행하고, 미충족이면 Task A를 재작업합니다. 완료 보고와 통과 판단은 구분합니다.

화면 부제: 필요한 판단을 통과한 뒤에 다음 작업을 진행합니다.

화면 문구:
- Task A
- decision gate
- 기준 확인
- Task B
- 통과
- 재작업
- 완료 보고와 통과 판단은 다릅니다.

시각: Task A→마름모 게이트→Task B. Task A의 결과를 확인해 통과하면 Task B를 실행하고, 미충족이면 Task A의 재작업으로 돌아오는 선. 앞 장과 같은 Task A(노랑)·Task B(브랜드) 매핑을 유지한다. 판단 게이트를 일반 메시지와 구분.

## 슬라이드 9. 목표는 오케스트레이터에게

역할: 앞 클립의 ‘에이전트 오케스트레이션의 시대’를 회수하고, 사람이 목표 하나를 전달하면 Coordinator가 여러 Worker의 실행을 조율한다는 전체 관계를 보여준다.

화면 부제: 사람은 Coordinator와 소통하고, Coordinator가 여러 워커의 작업을 조율합니다.

화면 문구:
- 사람
- 목표·기준
- 진행·결과
- Coordinator
- Task 분할·배정
- 결과 취합
- Worker A
- Task A
- Worker B
- Task B
- Worker C
- Task C
- 각 워커 공통 설명: 작업 수행

시각: 위쪽 왼편에 사람, 위쪽 오른편에 노란 Coordinator를 배치한다. Coordinator 아래에서 세 갈래로 내려가 Worker A·B·C가 나란히 놓인다. 사람과 Coordinator 사이에 목표·기준 전달 및 진행·결과 반환 화살표. Coordinator에서 세 Worker로 분기하는 배정 선과 돌아오는 보고 선. 사람과 Worker 사이에는 직접 연결선을 두지 않는다. Task A·B·C는 각 Worker 아래에 배정된 작업으로 표시한다. 워크트리나 새로운 실행 단위는 추가하지 않는다.

말할 내용: 사람은 목표와 기준을 Coordinator에게 전달한다. Coordinator가 목표를 Task로 쪼개고 워커를 배정하며, 작업 중 질문과 완료 보고를 받아 결과를 취합한다. 사람은 Coordinator와 진행과 결과를 확인하고 필요한 판단을 전달한다. 앞 클립의 과도기 대비에서 본 오케스트레이션 구조가 실제로 이렇게 작동한다.
