# 오케스트레이션 구조 살펴보기

제작 목표: 오케스트레이션은 여러 에이전트의 작업과 협업 흐름을 조율합니다.

소스: 사용자가 채팅으로 제공한 이전 강의 8~11장 대본의 핵심 메시지. 새로운 두 클립에 맞춰 분리·재구성한다.

## 현재 가이드와 대조한 내용

- 근거: 2026-09-09 로컬 `orca skills get orchestration` 전체 응답. 공식 공개 가이드: https://github.com/stablyai/orca/blob/main/skill-guides/orchestration.md
- Run은 지속되는 작업 네임스페이스와 코디네이터 수신함이다. 스스로 작업 순서나 배치를 결정하는 스케줄러가 아니다.
- Task는 업무 명세, Dispatch는 한 Task의 실행 시도를 담당 에이전트 터미널에 배정하는 관계다.
- 터미널 생성·준비·배정을 함께 수행하는 현재 권장 경로는 `worker-start`. 낮은 수준의 `dispatch --inject` 자체가 터미널 생성은 아니다.
- 스킬 문서가 독립적으로 실행되는 AI라는 표현은 쓰지 않는다. 에이전트가 스킬을 읽고 Orca의 도구를 사용한다.
- `question`은 워커→코디네이터, `reply`는 응답 동작으로 반대 방향, `worker_done`은 워커→담당 Run의 코디네이터로 전달된다. 이 셋을 전체 메시지 타입의 완전한 목록이라고 하지 않는다.
- `status`, `heartbeat`, `escalation` 등 다른 메시지도 있다. 개수는 고정하지 않는다.
- 작업 결정 게이트는 코디네이터가 관리한다. 워커 질문에 답하는 `ask/reply`와 구별한다.
- 완료 보고에는 성공/실패가 있으며, 보고가 도착했다고 산출물의 품질이 보장되는 것은 아니다.
- 작업 중 대기는 질문과 보고를 처리하는 단계다. 코디네이터가 아무것도 하지 않거나 언제나 동시에 대화 가능하다고 보장하지 않는다.
- 완료된 워커 터미널의 정리는 `worker-release`로 수행하며, 작업 폴더와 결과물을 지우는 의미가 아니다. 정리는 취합 명령이 아니므로 화면의 마지막 단계 명령은 정리 작업을 대표한다.
- 새 워커마다 새 워크트리가 필수인 것은 아니다. 도식의 분리된 폴더는 같은 파일의 동시 수정 충돌을 피하려는 배치 예시다.
- 오케스트레이션은 Orca에만 존재하는 개념이 아니다. 사람이 반복하던 전달은 줄지만 목표·기준·필요한 판단은 여전히 사람이 제공한다.

## 덜어낸 내용

- 다른 강의의 Hermes 사전 학습 언급은 이 커리큘럼의 선수 지식이 아니므로 제외.
- 모든 CLI 인자, 전체 메시지 타입, 복구·중첩·원격 실행은 입문 범위를 넘어 제외.
- 실제 사용자 작업 화면 캡처는 사용하지 않는다. 구조와 흐름은 SVG/CSS로 설명한다.
- 뒤 Chapter 2의 설치·실습 화면은 만들지 않는다. 기존 실습 도입 덱은 보존한다.

## 슬라이드 1. 오케스트레이션 구조 살펴보기

역할: 목표 하나를 여러 에이전트의 협업으로 실행한다.

말할 내용: 앞에서 에이전트가 일할 공간을 나눴습니다. 이제 그 에이전트에게 누가 일을 나누고, 다음 일을 이어주는지 보겠습니다.

화면 부제: 오케스트레이션은 여러 에이전트의 작업과 협업 흐름을 조율합니다.

화면 문구:
- 목표는 하나
- 일하는 에이전트는 여럿
- 목표
- 결과

시각: 목표에서 갈라져 두 에이전트를 거쳐 결과로 합쳐지는 단일 도식. 목차 없음.

## 슬라이드 2. 협업을 잇는 역할

역할: 사람이 반복하던 분배와 전달을 협업 흐름으로 맡긴다.

말할 내용: 에이전트를 늘려도 결과를 복사하고 다음 담당자에게 전달하는 일은 남습니다. 오케스트레이션은 이 반복적인 연결을 담당합니다.

화면 부제: 에이전트가 여럿이어도, 일을 나누고 넘겨줄 역할이 필요합니다.

화면 문구:
- 사람이 직접 넘기면
- 멀티 에이전트 과도기
- 에이전트가 여럿이어도, 자료 전달은 사람 몫
- 협업 흐름으로 연결하면
- 에이전트 오케스트레이션의 시대
- 목표 하나로 일을 나누고, 결과를 다음 담당자에게 전달

시각: ch02-01-orchestration-skill-setup의 1번 슬라이드에서 왼쪽 ‘자료 → 사람 → 자료’ 도식과 문구를 그대로 가져온 2단 비교. 오른쪽은 현재의 조율 에이전트 → 두 워커 도식을 유지한다. 두 영역의 표제·타이틀·본문과 중앙 전환 화살표는 참고 장의 규격을 쓴다. 왼쪽 제목은 orange, 오른쪽 제목은 brand, 제목 2rem/800, 표제 1.2rem, 본문 1.3rem/1.6이다. 도식 높이는 12rem으로 맞추고 전체 묶음의 최대 너비는 90rem으로 제한한다. 현재 덱의 장 제목·부제·푸터는 유지한다. 왼쪽 → 중앙 화살표 → 오른쪽을 시간차로 보여준다. 테두리 없음.

## 슬라이드 3. 환경과 스킬

역할: Orca는 작업 환경이며, 에이전트가 스킬의 절차에 따라 협업을 조율한다.

말할 내용: 스킬은 에이전트가 따르는 작업 지침과 도구 사용 절차입니다. 별도의 AI가 하나 더 생기는 것이 아니라, 이미 쓰는 에이전트가 이 지침으로 Orca의 도구를 사용합니다.

화면 부제: Orca를 설치하는 것만으로 에이전트들이 저절로 협업하지는 않습니다.

화면 문구:
- Orca는 작업 환경
- 협업은 스킬로
- Orca
- 오케스트레이션 스킬
- 분배 · 전달 · 취합
- 에이전트 실행 · 작업 공간 · 상태 관리

시각: 회색 Orca 창 안의 조율 에이전트와 두 워커. 스킬 문서가 조율 에이전트에 연결된다. 오른쪽 큰 선언문.

## 슬라이드 4. 조율과 실행

역할: Coordinator와 Worker는 제품 이름이 아니라 에이전트의 역할이다.

말할 내용: 팀장과 실무 담당자에 빗대면 쉽습니다. 코디네이터는 전체 목표와 순서를 관리하고, 워커는 맡은 범위의 결과물을 만듭니다.

화면 부제: 협업을 조율하는 에이전트와 실제 작업을 수행하는 에이전트로 역할을 나눕니다.

화면 문구:
- Coordinator
- 협업 조율
- 일을 나누고, 배정하고, 결과를 확인
- Worker
- 작업 수행
- 맡은 작업을 실행하고, 결과를 보고
- 둘 다 이미 쓰는 에이전트가 맡는 역할입니다.

시각: 노란 코디네이터와 브랜드/보라 워커를 좌우 대등한 크기로 표현. 코디네이터 앞에는 작업표, 워커 앞에는 파일.

## 슬라이드 5. 협업의 구조

역할: 목표는 사람에서 코디네이터로, 작업은 워커로, 보고는 코디네이터로 돌아온다.

말할 내용: 사람이 매번 워커를 찾아다니는 대신 코디네이터가 배정과 보고를 연결합니다. 목표나 중요한 기준이 불명확하면 사람에게 다시 확인합니다.

화면 부제: 사람은 목표와 기준을 주고, 코디네이터는 워커의 작업을 조율합니다.

화면 문구:
- 사람
- 목표 · 기준 · 필요한 판단
- Coordinator
- 작업 분배 · 결과 확인
- Worker A
- Worker B
- 작업 지시
- 질문 · 보고

시각: 사람→코디네이터→두 워커를 연결하는 가로 분기 구조. 지시 실선과 보고 점선은 방향이 반대. 단계별 등장.

## 슬라이드 6. 작업과 소통

역할: 워커의 배치와 협업 메시지를 구별한다. 같은 워크트리에서도 여러 워커가 작업할 수 있다.

말할 내용: 워커는 같은 워크트리에서 함께 작업할 수도 있고, 작업 공간을 분리할 수도 있습니다. 어느 배치든 작업 파일은 폴더에 두고, 진행과 결과는 메시지로 공유합니다.

화면 부제: 같은 공간에서 작업해도, 진행과 결과는 메시지로 공유합니다.

화면 문구:
- 같은 워크트리
- Worker A
- Worker B
- Coordinator
- 진행 상황·결과 보고
- 완료 보고에는 결과물 위치와 작업 내용을 함께 남깁니다.

시각: 하나의 회색 워크트리 폴더 안에 Worker A(brand)와 Worker B(purple)를 함께 배치한다. 각 워커 옆에는 작업 파일을 둔다. 폴더 오른쪽에서 두 워커의 보고 화살표가 Coordinator(yellow)에게 향한다. 메시지 라벨은 ‘진행 상황·결과 보고’. 폴더를 나누는 대신 작업 파일이 놓인 공간과 메시지로 소통하는 관계를 구분한다. 별도 워크트리가 오케스트레이션의 필수 조건처럼 보이지 않게 한다.

정확성: 워커마다 별도 워크트리가 필수인 것은 아니다. 같은 파일을 동시에 수정하는 작업은 공간을 나누거나 작업 순서를 정한다. 작업 배치는 에이전트가 결정하며 자동 충돌 방지를 보장하지 않는다. 공식 가이드의 두 `worker-start --worktree current` 예시 확인: https://github.com/stablyai/orca/blob/main/skill-guides/orchestration.md#canonical-supervised-loop (2026-09-09).

## 슬라이드 7. 서로 다른 워크트리

역할: 앞 장의 같은 워크트리 배치에 이어, 워크트리를 분리해 협업하는 배치를 보여준다. 작업의 성격과 협업 설계에 따라 배치를 선택한다.

말할 내용: 같은 파일을 각자 다른 방식으로 수정하거나 작업 결과를 독립적으로 비교하려면 워크트리를 나눌 수 있습니다. 어느 배치든 코디네이터는 메시지로 진행과 결과를 확인합니다. 워크트리를 함께 쓸지 나눌지는 작업의 성격과 협업 설계에 따라 정합니다.

화면 부제: 공간을 나눠 작업해도, 진행과 결과는 메시지로 공유합니다.

화면 문구:
- Coordinator
- Worker A
- 작업 폴더 A
- Worker B
- 작업 폴더 B
- 진행 상황·결과 보고
- 완료 보고에는 결과물 위치와 작업 내용을 함께 남깁니다.

시각: 이전 「작업과 소통」의 분리된 두 폴더 도식을 복원한다. 상단 중앙 Coordinator(yellow), 하단 왼쪽 작업 폴더 A와 Worker A(brand), 오른쪽 작업 폴더 B와 Worker B(purple). 각 폴더 안에 실제 파일을 표시하고 위쪽 Coordinator에게 보고하는 점선 화살표를 연결한다. 폴더마다 새 워커가 반드시 생기는 관계로 설명하지 않는다.

애니메이션: Coordinator → 작업 폴더 A·Worker A → 작업 폴더 B·Worker B → A의 보고 → B의 보고 → 보고 내용 → 하단 설명.

## 슬라이드 8. 메시지의 종류

역할: 질문·응답·완료 보고는 서로 다른 방향과 역할을 가진다.

말할 내용: 서로 다른 세션의 에이전트는 대화 맥락이 자동으로 합쳐지지 않습니다. 질문은 워커에서 코디네이터로, 답은 반대로, 결과 보고는 다시 코디네이터로 갑니다.

화면 부제: 질문·응답·결과 보고에 사용하는 대표 메시지입니다.

화면 문구:
- Worker
- Coordinator
- question
- 작업 중 필요한 질문
- reply
- 질문에 대한 답변
- worker_done
- 작업 결과 보고

시각: 왼쪽 Worker와 오른쪽 Coordinator는 메시지 세 행 전체를 기준으로 수직 중앙에 둔다. 두 주체는 로봇 아래에 이름을 배치한다. 가운데 세 행은 question→, reply←, worker_done→ 방향이다. 각 메시지명 바로 옆에 물음표·문서·체크 아이콘을 붙이고, 그 아래 화살표와 설명을 둔다. 본문 가용 높이 안에서 세 행을 균등 배분한다. 각 행은 아이콘+메시지명·12px 화살표 구간·설명의 세 줄로 정렬한다. 좁고 낮은 화면에서도 마지막 설명이 푸터를 침범하지 않게 한다.
