## 사실과 제작 범위

완성 프로젝트는 제작자의 설명 준비 자료다. 수강생에게 완성본의 근거를 역추적하는 과제를 주지 않는다. 상품과 리스크는 완성 프로젝트의 예시이며 현재 시장의 추천·수익 보장이 아니다. 기존 시장 조사 노트에는 공급가 등의 구체적인 출처 링크가 없어 새 조사의 정답으로 고정하지 않는다. 카테고리 등급과 세부 품목 점수의 변화에는 별도의 근거 확인이 필요하다.

Ch04-01~03은 일반 에이전트에게 개별 작업을 요청하고, Ch04-04는 품질 게이트 이론을 설명한다. Ch05-01 「단계별 품질 기준 정하기」(14분)는 시장 조사 노트·아이템 후보 비교표·판매 아이템 기획서의 단계별 통과·반려 기준을 정해 `artifacts/quality-gate/criteria.md`로 저장하는 실습만 한다. 프롬프트 작성·실행·반려 시연은 포함하지 않는다. Ch05-02 「목표 하나로 처음부터 끝까지 실행하기」(15분)는 강사가 제공한 프롬프트의 작업 순서·입출력·품질 기준 참조·반려/재검사 규칙을 이해한 뒤 바로 전체를 실행한다. 진행·검사·실제 반려 시 담당 워커의 수정 과정과 최종 세 문서를 확인한다. 프롬프트를 새로 작성하지 않으며, 반려를 만들기 위한 필수 오류 주입·사전 실행은 없다. 실제 반려 기록으로 설명하고 추가 연습은 본 실행 이후 선택사항이다. 코디네이터가 검사하며, 반려하면 원인 문서의 담당 워커가 수정하고 전체 기준을 재검사한다. 통과한 경우에만 다음 작업을 배정하고 상위 문서가 바뀌면 영향받는 후속 문서를 재확인한다. Part 5 같은 모델 기준 검사와 Part 6 다른 모델 교차 검증을 구분한다. 제작 중 상태이며 강사 확정·촬영 완료로 기록하지 않는다.

## Ch01-02 1차 자료 검증 (2026-09-22)

세 용어는 기존 강의 기획의 교육용 분류다. 아래 자료가 이 세 용어를 그대로 제안했다는 주장은 하지 않는다. 업무 상황은 원리를 설명하기 위해 만든 예시다.

- [Anthropic, How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system), 2025-06-13: 담당마다 목적·출력 형식·명확한 범위를 주고 파일에 결과를 남겨 전달 손실을 줄인다는 설계 근거. 이 강의에서는 조건을 문서에 남기고 다음 작업의 입력으로 지정하는 방식으로 적용한다.
- [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), 2025-11-26: 장기 작업 중 성급한 완료 선언과 충분한 확인 없이 완료로 처리하는 사례를 기록한다. 파일 없는 보고는 이를 강의 업무에 적용한 설명용 상황이며 해당 글의 직접 사례로 소개하지 않는다.
- [Huang et al., Large Language Models Cannot Self-Correct Reasoning Yet](https://arxiv.org/abs/2310.01798), ICLR 2024: 외부 피드백 없는 내재적 자기 수정의 한계를 특정 추론 과제에서 분석한다. 모든 모델과 모든 작업에서 자체 검사가 불가능하다는 뜻이 아니다. 다른 모델을 쓰면 정답이 보장된다는 결론도 아니다.

원본·평가 기준·항목별 판정을 함께 제공하는 것은 강의 설계의 적용이다. Part 5의 동일 모델 자체 검사는 유지하며 다른 모델 평가 루프는 Part 6에서 다룬다.

### 4. 작업마다 기준 입력 (해결 01)

역할: TURN_SCOPED_INPUT

> 코디네이터가 작업을 시킬 때마다 그 작업에 필요한 기준을 함께 넣습니다.

실습 근거: 가이드의 모든 작업 프롬프트가 `#### 참고자료`에 그 작업에 필요한 문서를 건다.
앞 작업이 언제 끝날지 모르므로 원래는 사람이 기다렸다 넣어야 하지만, 실제 실행에서는 코디네이터가 그 시점에 넣는다.

**조건은 작업마다 독립이다.** 같은 문서를 세 작업에 반복해 넣는 그림을 쓰지 않는다.
예시는 이 프로젝트의 문서 이름이 아니라 설명에 맞는 일반 작업으로 든다.

화면 문구·요소:
```json
{
  "coordinator": ["Coordinator", "작업을 시킬 때마다", "yellow"],
  "workers": [
    ["Worker A", "자료 조사", "조사 기준"],
    ["Worker B", "초안 작성", "작성 양식"],
    ["Worker C", "검토", "검토 기준"]
  ],
  "wires": "코디네이터 아이콘 아래에서 각 워커 아이콘 위로 내려오는 곡선 (직각 엘보 금지)",
  "docbox": "기준은 목록이 아니라 문서 카드로 보여준다",
```

### 6. 파일로 완료 확인 (해결 02)

역할: ARTIFACT_GATE

> 완료 보고에 성공·실패와 남긴 파일이 함께 옵니다.

실습 근거: 실제 실행은 오케스트레이션 구조를 따른다(`orca skills get orchestration`).
워커의 완료 보고는 **성공·실패를 값으로** 달고 오고(실패를 설명 문장으로만 남기지 않는다),
**남긴 파일 목록**이 함께 온다. 진행 중 신호(살아 있다는 신호)는 완료가 아니다.
실패로 오면 그 작업은 실패로 남고 다음 작업은 시작되지 않으며, 같은 작업을 다시 하게 된다.
막히면 완료 보고 대신 질문이 올라온다.

**이 장의 확인 범위는 「파일이 남았는가」까지다.** 파일 내용이 기준에 맞는지는 8장의 품질 기준이 판정한다.
두 장의 경계를 섞지 않는다.

화면에 오케스트레이션·스킬 이름이나 명령을 쓰지 않는다. 사람이 여는 결정 게이트도 두지 않는다 —
요청에는 게이트를 넣지 않고, 갈래는 보고 값에 따라 자동으로 갈린다.

화면 문구·요소:
```json
{
  "worker": ["Worker", "brand"],
  "report": {
    "tag": "보고에 함께 오는 것",
    "title": "성공·실패 + 남긴 파일",
    "sub": "진행 중 신호는 완료가 아님"
  },
  "branches": [
    ["성공 · 파일 있음", "다음 작업 시작", "green 실선, 보고 카드와 같은 y에서 직선"],
    ["실패 · 파일 없음", "워커로 되돌아간다", "orange 점선, 아래로"]
  ],
  "note": "실패로 오거나 파일이 없으면 다음 작업은 시작되지 않습니다."
}
```

### 8. 기준 문서로 판정 (해결 03)

역할: QUALITY_GATE_LOOP

> 작성한 워커가 아니라 코디네이터가 품질 기준으로 검사합니다.

실습 근거: 가이드의 「단계별 품질 기준 정하기」에서 `criteria.md`에 Y/N 검사 문장과 판정 규칙을 저장한다.
코디네이터가 그 기준으로 검사하고, 기준에 못 미치면 그 문서를 쓴 워커에게 돌려보내 수정 후 재검사한다.
기준값은 숫자로 옮겨 적지 않고 사업 조건을 가리키게 한다.

화면 문구·요소:
```json
{
  "criteria": {"chrome": "품질 기준", "title": "검사 항목과 판정 규칙"},
  "nodes": [
    ["agent", "Worker", "문서 작성", "brand"],
    ["document", "초안", "검사 대상", "green"],
    ["agent", "Coordinator", "품질 기준으로 Y/N 판정", "yellow"]
  ],
  "links": ["Output (실선)", "완료 보고 (점선)", "반려 사유와 수정 요청 (orange 점선, 워커로 되돌아간다)"],
  "note": "기준에 못 미치면 그 문서를 쓴 워커에게 돌려보냅니다."
}
```

슬라이드: 1장
