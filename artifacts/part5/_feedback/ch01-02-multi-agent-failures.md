## 5차 (2026-09-28 · 도식 규격 정비 · 검수 대기)

사용자 지적과 반영:

- **1920×940과 1920×1020이 다 맞아야 한다.** 절대좌표(%·viewBox)로 박아둔 도식이 화면 높이에 따라 어긋났다 → 4·6·8·9장을 절대좌표 없이 CSS grid/flex로 다시 짰다. 간격은 `column-gap`이 만들고 좌표가 없어 해상도에 따라 틀어질 일이 없다.
- **검증을 가라로 했다.** zsh 워드 스플리팅 때문에 뷰포트가 바뀌지 않은 채 "OK"만 찍고 있었다 → `while read`로 고치고 `innerWidth/innerHeight`를 매번 함께 기록한다. 그리고 **스크립트 통과와 무관하게 렌더 화면을 눈으로 본다.**
- **화살표가 박스에 붙는다 / 혼자 굵다 / 박스가 화살표보다 작다** → 선은 어디서나 `2px`, 화살촉은 어디서나 `20×14px` 셰브론, 카드 `min-width`는 화살표보다 크게. SVG 기본 고유 폭 300px 때문에 커넥터 칸이 벌어지던 것도 고쳤다.
- **되돌림 선이 블록 중앙에 안 붙는다** → 칸 바깥에서 그리던 것을 각 칸 **안에서** 그리도록 바꿨다(`.p5-rt`). 세로 구간이 항상 블록 가로 중앙(50%)에 온다.
- **되돌림 선이 라벨을 덮는다** → `::after`가 텍스트보다 나중에 칠해지던 문제. 라벨에 `z-index`를 줘 선 위로 올렸다.
- **직각 엘보 대신 곡선** → 4장 배정선을 실측 좌표 베지어 곡선으로 그린다(`drawDispatchFan`). 참고 덱의 역할 지도와 같은 형태다.
- **워커는 텍스트 더미가 아니라 캐릭터로** → 4장 워커를 로봇 캐릭터로 세웠다.
- **박스가 의미 없이 크고 왼쪽 정렬이라 비어 보인다** → 카드는 콘텐츠 폭 + 패딩, 가운데 정렬로 바꿨다.
- **모든 작업에 같은 조건을 넣지 마라 / 예시가 프로젝트 문서다** → 4장의 기준을 작업마다 독립으로 바꾸고(`조사 기준`·`작성 양식`·`검토 기준`), 프로젝트 문서 이름을 뺐다. 목록 대신 문서 카드로 담았다.
- **반려 조건을 단정하지 마라** → `한 항목이라도 반려면`은 기준을 어떻게 쓰느냐에 따라 달라지므로 `기준에 못 미치면`으로 바꿨다.
- **체크리스트 키워드** → 기준 문서 카드 제목을 `체크리스트`로 했다. 설명 문장은 원래대로 둔다(용어를 문장까지 일괄 치환하지 않는다).
- **9장(정리)이 성의 없다** → 실패 하나당 한 열로 다시 짰다. 번호·실패명 → 세로선 → 대응 카드이며, 대응은 4·6·8장 제목과 1:1로 맞췄다.

## 3. 다음부터 이렇게 해

- **도식을 절대좌표로 박지 않는다.** 블록은 CSS 레이아웃으로 배치하고, 연결선만 필요할 때 DOM 실측으로 그린다. 좌표를 손으로 계산하면 해상도가 바뀔 때마다 틀어진다.
- **사이즈 규칙을 먼저 정하고 그린다** — 선 굵기·화살촉 크기·박스 최소폭을 변수로 고정한다. SVG를 쓸 때 고유 폭(300×150) 때문에 칸이 벌어지는지 확인한다.
- **연결선의 시작·끝은 블록의 같은 기준점(가로 중앙)에 맞춘다.** 한쪽은 중앙, 한쪽은 모서리로 두지 않는다.
- **흐름선은 곡선으로 그린다.** 직각 엘보는 이 강의 덱의 문법이 아니다.
- **검증은 사용자가 보는 화면으로 한다.** 스크립트가 통과해도 렌더를 직접 보고, 뷰포트가 실제로 바뀌었는지 `innerWidth/innerHeight`로 확인한다.
- **주체는 캐릭터로 세운다.** 이름만 나열한 텍스트 열로 대체하지 않는다.
- **같은 조건을 여러 칸에 반복해 그리지 않는다.** 작업마다 다른 것을 보여줘야 "작업마다 넣는다"가 읽힌다.
- **예시는 설명에 맞는 일반 작업으로 든다.** 이 클립이 프로젝트 문서를 가르치는 자리가 아니면 프로젝트 이름을 끌어오지 않는다.
- **판정 조건을 단정하지 않는다.** 반려 기준은 기준 문서를 어떻게 쓰느냐에 달렸다.
- 용어를 맞추라는 지적은 **그 자리(제목·라벨)에만** 반영한다. 설명 문장까지 일괄 치환하지 않는다.


- 큰 문구는 승인 덱처럼 짧은 구절로 쓴다. ‘빈틈’ 같은 모호한 말 대신 전달·완료·검증의 실패 지점을 명시한다.
- 표지는 왼쪽 문구·오른쪽 시각 슬롯 규격을 따른다. 여러 에이전트의 관계를 설명할 때는 한 사례의 가로로 긴 장면 이미지가 아니라 작고 명확한 SVG 구조도를 쓴다. 1920×1080과 1280×800에서 크기와 연결선을 확인한다.
- 실패 세 가지는 01·02·03으로 표기한다. 장면과 해결 구조를 구분하고, 균형이 필요한 비교 화면에서는 이미지와 아이콘 나열을 섞지 않는다.
- 사용자가 부적절하다고 지적한 `무재고` 사례나 임의의 콜아웃을 되살리지 않는다. 관계는 짧은 문서 연결 도식으로 설명한다.
- 제목 강조는 위치 규칙이 아니라 이 장에서 구분할 개념·주체·조건으로 고른다. “맥락 붕괴” 같은 용어를 마지막 단어만 잘라 강조하지 않는다.
- 하단 보충 문구를 본문 flex gap으로 처리하지 않는다. 본문과 하단 영역을 분리하고 실제 렌더링으로 상하 거리를 확인한다.
- 프로젝트 copy는 결과물·과정 두 줄로 정리한다. 학습자에게 불필요한 제작자 관점의 “완성 예시”는 넣지 않는다.

## 4차 (2026-09-28 · 6장 두 갈래 · 검수 대기)

사용자: 6번에 통과인 경우만 있고 아닌 경우가 없다. 실제로는 오케스트레이션으로 돌리니 공식 문서를 확인하고 그 기준·구조에 맞출 것(용어는 화면에 내지 말 것). 파일이 있는지까지만 확인하는지 필수 항목까지 확인하는지 명확히 할 것. 요청에는 결정 게이트를 주지 않는다.

`orca skills get orchestration`으로 확인한 계약:

- 완료 보고(`worker_done`)는 **성공·실패를 값으로** 달고 온다 — 실패를 설명 문장으로만 남기지 않는다.
- 같은 보고에 **남긴 파일 목록**이 함께 온다.
- **진행 중 신호(heartbeat)는 완료가 아니다.** 터미널이 움직인다고 끝난 게 아니다.
- 막히면 완료 보고 대신 질문·에스컬레이션이 올라온다.
- 실패면 그 작업이 실패로 남고, 같은 작업을 3번 연속 실패하면 거기서 끊긴다.
- 결정 게이트는 코디네이터가 작업 순서를 정할 때 쓰는 것이라 이 화면에 두지 않는다.

반영:

- **6장을 두 갈래로 다시 그렸다.** 보고 카드에서 `성공 · 파일 있음 → 다음 작업 시작`(green 실선)과 `실패 · 파일 없음`(orange 점선, 워커로 되돌아감)으로 나뉜다. 통과만 있던 한 줄짜리 흐름을 버렸다.
- 보고 카드 문구를 계약대로 `성공·실패 + 남긴 파일`로 바꾸고 `진행 중 신호는 완료가 아님`을 함께 뒀다.
- **6장과 8장의 확인 범위를 갈랐다.** 6장은 파일이 남았는지까지, 8장은 그 내용이 기준에 맞는지다. 6장에 있던 `필수 항목 / 출처 · 추정 근거 · 양식`은 8장의 품질 기준 카드로 옮겨 `필수 섹션 · 근거 · 계산`으로 적었다.
- 9장 요약 02행도 `완료 보고의 성공·실패와 파일 확인`으로 맞췄다.
- 화면에는 오케스트레이션·스킬 이름·명령을 쓰지 않았다. 구조와 기준만 따랐다.
- 라벨의 글리프 화살표(`→`)를 없앴다. 방향은 그려진 화살표가 말한다.
- 사용자: 성공 카드를 위로 올릴 이유가 없다. 갈래마다 다른 작업을 하는 것도 아니고 실패는 되돌아가는 루프라 그 자리에 놓일 게 없다. → **성공 경로를 보고 카드와 같은 y에 직선으로 폈고, 실패 루프만 아래로 내렸다.**

## 3. 다음부터 이렇게 해

- **갈래를 그릴 때 계속 진행하는 쪽은 직선으로 둔다.** 두 갈래가 대등한 다른 작업일 때만 위아래로 가른다. 한쪽이 되돌아가는 루프면 그 쪽만 꺾고, 빈 자리를 만들려고 나머지를 올리지 않는다.
- **분기가 있는 장에는 통과와 실패를 모두 그린다.** 통과 경로만 그리면 실패했을 때 어떻게 되는지가 화면에서 사라진다.
- 실행 구조를 설명하는 장은 **실제로 돌릴 도구의 공식 문서를 먼저 확인하고** 그 계약에 맞춘다. 도구 이름과 명령은 화면에 내지 않고 구조와 기준만 가져온다.
- **연속한 두 해결 장은 확인 범위를 갈라 적는다.** 앞 장이 어디까지 보고 뒤 장이 무엇을 보는지 겹치지 않게 한다.
- 사용자가 요청에 넣지 않을 장치(결정 게이트 등)를 화면에 그리지 않는다.
- 문제를 여러 장 세울 때는 **문제마다 그 문제의 해결 장을 바로 뒤에 붙인다.** 해결을 마지막 요약표에서 처음 꺼내지 않는다.
- 해결 장의 동작은 **실습 가이드에서 실제로 하는 것**을 쓴다. 이론적으로 옳은 일반론을 만들어 넣지 않는다.
- **제목과 화면이 같은 동작 하나를 가리키는지 확인한다.** 제목이 A를 말하고 도식이 B를 보여주면 그 장은 실패다.
- 본문에 파트·챕터 번호로 범위를 설명하는 장이나 문구를 넣지 않는다. 다음 파트 예고도 화면이 아니라 대본에서 한다.
- 구조도에 아무것과도 연결되지 않은 카드를 두지 않는다. 화살표는 시작과 끝이 실제 요소에 닿아야 한다.
