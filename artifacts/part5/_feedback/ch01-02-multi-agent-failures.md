## 5차 (2026-09-28 · 도식 규격 정비 · 검수 대기)

사용자 지적과 반영:

- **1920×940과 1920×1020이 다 맞아야 한다.** 절대좌표(%·viewBox)로 박아둔 도식이 화면 높이에 따라 어긋났다 → 4·6·8·9장을 절대좌표 없이 CSS grid/flex로 다시 짰다. 간격은 `column-gap`이 만들고 좌표가 없어 해상도에 따라 틀어질 일이 없다.
- **검증을 가라로 했다.** zsh 워드 스플리팅 때문에 뷰포트가 바뀌지 않은 채 "OK"만 찍고 있었다 → `while read`로 고치고 `innerWidth/innerHeight`를 매번 함께 기록한다. 그리고 **스크립트 통과와 무관하게 렌더 화면을 눈으로 본다.**
- **화살표가 박스에 붙는다 / 혼자 굵다 / 박스가 화살표보다 작다** → 선은 어디서나 `2px`, 화살촉은 어디서나 `20×14px` 셰브론, 카드 `min-width`는 화살표보다 크게. SVG 기본 고유 폭 300px 때문에 커넥터 칸이 벌어지던 것도 고쳤다.
- **되돌림 선이 블록 중앙에 안 붙는다** → 칸 바깥에서 그리던 것을 각 칸 **안에서** 그리도록 바꿨다(`.p5-rt`). 세로 구간이 항상 블록 가로 중앙(50%)에 온다.
- **되돌림 선이 라벨을 덮는다** → `::after`가 텍스트보다 나중에 칠해지던 문제. 라벨에 `z-index`를 줘 선 위로 올렸다.
- **직각 엘보 대신 곡선** → 4장 배정선을 실측 좌표 베지어 곡선으로 그린다(`drawDispatchFan`). 참고 덱의 역할 지도와 같은 형태다.
- **워커는 텍스트 더미가 아니라 캐릭터로** → 4장 워커를 로봇 캐릭터로 세웠다.
- **박스가 의미 없이 크고 왼쪽 정렬이라 비어 보인다** → 카드는 콘텐츠 폭 + 패딩, 가운데 정렬로 바꿨다.
- **모든 작업에 같은 조건을 넣지 마라 / 예시가 프로젝트 문서다** → 4장의 기준을 작업마다 독립으로 바꾸고(`조사 기준`·`작성 양식`·`검토 기준`), 프로젝트 문서 이름을 뺐다. 목록 대신 문서 카드로 담았다.
- **반려 조건을 단정하지 마라** → `한 항목이라도 반려면`은 기준을 어떻게 쓰느냐에 따라 달라지므로 `기준에 못 미치면`으로 바꿨다.
- **체크리스트 키워드** → 기준 문서 카드 제목을 `체크리스트`로 했다. 설명 문장은 원래대로 둔다(용어를 문장까지 일괄 치환하지 않는다).
- **9장(정리)이 성의 없다** → 실패 하나당 한 열로 다시 짰다. 번호·실패명 → 세로선 → 대응 카드이며, 대응은 4·6·8장 제목과 1:1로 맞췄다.

## 2026-10-06 출처 재검토 반영

- 사용자가 확인한 출처는 shalomeir의 MAST 기반 경험 글이다. 세 명칭을 논문의 공식 3분류로 소개하지 않는다.
- 9장 전체 슬라이드·대본과 소스·스토리보드·커리큘럼의 해당 3개 항목을 동기화했다.
- 맥락 붕괴: 목적·배경이 작업 위임에서 빠짐 → 모든 담당의 작업 시작 시 전체 목표와 작업의 이유 전달.
- 유령 위임: 인수인계 실패·미착수·미완료 방치 → 결과물·후속 배정·착수 확인 및 누락/지연 대응. 파일 부재는 한 사례다.
- 검증 오류: 불완전한 검사·검증자의 오판 → 생성과 검증 분리 및 실제 근거로 요구사항 확인. 검사 주체나 모델 변경만으로 정확성을 보장하지 않는다.
- 이전 자료 과다·원본 대조 누락 중심 설명은 현행 기준에서 폐기한다. 사용자 요청으로 대본도 함께 수정했으며 최종 승인 상태는 바꾸지 않았다.

## 2026-10-06 문제 장의 형식 복원

- 내용 수정 요청을 문제 장의 도식 재설계로 확대하지 않는다. 3·5·7장은 기존 왼쪽 설명·오른쪽 이미지를 유지한다.
- 맥락 붕괴는 코디네이터의 존재를 전제로 하는 문제가 아니다. 문제 정의·원인은 에이전트 간 목적·배경 전달 누락으로 설명하고, 코디네이터는 해결 적용 장에만 둔다.
- 3장의 원래 이미지와 장면 레이아웃을 복원하고, 대본 원인 설명에서도 코디네이터를 제거했다.

## 2026-10-06 해결 도식의 문구 압축

- 목적 공유의 핵심은 작업별 설명을 늘리는 것이 아니라 각 작업과 전체 목표·배경을 모든 에이전트에게 함께 전달하는 것이다.
- 4장 카드는 담당 작업과 `+ 전체 목표·배경` 두 줄로 줄이고, 중복 작업명·이유 예시를 삭제했다. 대본 자동 수정은 하지 않았다.

## 2026-10-06 유령 위임 문구 압축

- 5장 큰 문구는 기존 두 줄 규격으로 `일은 넘겼는데 / 인수인계가 끊김`. 설명은 `일을 넘겼는데, 다음 담당이 시작하지 않음`.
- 위임·완료 처리, 전달·배정 누락의 방치처럼 추상 명사를 겹친 표현을 삭제하고, 누구의 일이 어떻게 멈췄는지 쉽게 쓴다.

## 2026-10-06 검증 문제·해결의 전제 분리

- 7장은 작성자가 자기 답안을 채점하고 스스로 완료 판단하는 문제로 구성한다. 이미 별도 검증자가 있는 상황을 문제의 전제로 삼지 않는다.
- 8장에서 실행·검증·판정(Executor–Validator–Critic)의 역할 분리를 해결로 처음 제시한다. 화면·대본·개요·요약의 표현을 함께 맞춘다.
- 7장은 기존 왼쪽 두 줄 문구·오른쪽 이미지 형식을 유지한다. 다만 그림 속 독립 검증자도 제거해 자기 승인 장면으로 맞춘다.
- 사용자가 7·8장 대본을 직접 지적한 수정 요청이므로 해당 대본과 앞뒤 연결을 수정한다. 덱 전체 승인으로 기록하지 않는다.

## 2026-10-06 마지막 장 문제 설명 추가

- 문제명 바로 아래 회색 설명 한 줄을 넣고, 그 아래 기존 화살표와 해결 카드를 유지한다.
- 맥락 붕괴: 할 일은 알지만, 목적은 모름. 유령 위임: 일을 넘겨도, 다음 담당은 대기. 검증 오류: 자기 결과를 스스로 채점.

## 2026-10-06 실습의 2인 검토 구조로 정정

- 최신 지시: 8장은 작성자와 검토자 두 역할을 둔다. 검토자에게 검증 기준을 체크리스트로 주고 통과·수정 판단까지 맡긴다.
- 3단 역할 도식은 폐기하고 기존 2인 구조·체크리스트 입력·통과·반려 경로를 복원했다. 7장의 자기 채점 문제는 유지한다.
- 현재 대본 수정 요청의 후속 정정으로 8장 대본과 9장 연결 문장도 맞췄다. 마지막 장의 회색 문제 설명은 유지했다.

## 3. 다음부터 이렇게 해

- **2026-10-06 반영 위치 오류:** 2장 제목·부제를 논의하며 승인한 연구 소개를 1장 대본에 넣고 반영 완료라고 보고했다. 편집 전 대상 장/요소를 고정하고, 저장 후 승인 문구의 실제 장 번호·제목·본문 및 원래 위치의 삭제 여부를 확인한다. 보고도 그 실물 기준으로 한다. 이미 승인한 수정의 누락·오배치는 추가 승인 요청 없이 바로잡는다.

- **연구에 근거한 실패 설명은 원문의 정의·관찰과 강의용 적용을 구분한다.** 검증 오류는 불완전한 검사와 검증자의 오판을 포함한다. 생성과 검증을 분리하고 실제 근거로 요구사항 충족을 확인하게 한다. 검사 담당은 코디네이터 또는 별도 에이전트로 둘 수 있으며, 한 실습의 역할 배정을 일반 원칙으로 고정하지 않는다.

- **문제 장의 대본은 문제의 정의 → 원인 순서로 설명하고, 다음 해결 장에서 그 원인에 대한 대응을 말한다.** 정의 전에 낯선 예시부터 늘어놓지 않는다. 예시는 필요한 경우 정의·원인 뒤의 보조로만 쓰고, “설명하려고 만든 상황” 같은 제작 설명이나 불필요한 모델 면책 문구를 낭독문에 넣지 않는다.

- **수정 제안도 기존 슬라이드 문체로 쓴다.** 제목은 짧은 명사구(예: `완료 기준 명시`), 부제는 한 문장, 도식 라벨은 짧은 구절. `정하세요` 같은 권유형 제목이나 예외를 길게 설명하는 문구로 바꾸지 않는다.
- **보고와 실제 확인을 구분한다.** 완료 보고의 상태·경로가 있다는 이유로 실제 파일 검증이 끝났다고 설명하지 않는다. 사용자가 준 완료 기준을 코디네이터가 수행하는 구조를 보여준다. 파일 작업 예시에서는 `worker_done`과 성공·실패 여부·결과물 경로를 명시한다.

- **도식을 절대좌표로 박지 않는다.** 블록은 CSS 레이아웃으로 배치하고, 연결선만 필요할 때 DOM 실측으로 그린다. 좌표를 손으로 계산하면 해상도가 바뀔 때마다 틀어진다.
- **사이즈 규칙을 먼저 정하고 그린다** — 선 굵기·화살촉 크기·박스 최소폭을 변수로 고정한다. SVG를 쓸 때 고유 폭(300×150) 때문에 칸이 벌어지는지 확인한다.
- **연결선의 시작·끝은 블록의 같은 기준점(가로 중앙)에 맞춘다.** 한쪽은 중앙, 한쪽은 모서리로 두지 않는다.
- **흐름선은 곡선으로 그린다.** 직각 엘보는 이 강의 덱의 문법이 아니다.
- **검증은 사용자가 보는 화면으로 한다.** 스크립트가 통과해도 렌더를 직접 보고, 뷰포트가 실제로 바뀌었는지 `innerWidth/innerHeight`로 확인한다.
- **주체는 캐릭터로 세운다.** 이름만 나열한 텍스트 열로 대체하지 않는다.
- **같은 조건을 여러 칸에 반복해 그리지 않는다.** 작업마다 다른 것을 보여줘야 "작업마다 넣는다"가 읽힌다.
- **예시는 설명에 맞는 일반 작업으로 든다.** 이 클립이 프로젝트 문서를 가르치는 자리가 아니면 프로젝트 이름을 끌어오지 않는다.
- **판정 조건을 단정하지 않는다.** 반려 기준은 기준 문서를 어떻게 쓰느냐에 달렸다.
- 용어를 맞추라는 지적은 **그 자리(제목·라벨)에만** 반영한다. 설명 문장까지 일괄 치환하지 않는다.


- 큰 문구는 승인 덱처럼 짧은 구절로 쓴다. ‘빈틈’ 같은 모호한 말 대신 전달·완료·검증의 실패 지점을 명시한다.
- 표지는 왼쪽 문구·오른쪽 시각 슬롯 규격을 따른다. 여러 에이전트의 관계를 설명할 때는 한 사례의 가로로 긴 장면 이미지가 아니라 작고 명확한 SVG 구조도를 쓴다. 1920×1080과 1280×800에서 크기와 연결선을 확인한다.

## 3. 다음부터 이렇게 해

- **갈래를 그릴 때 계속 진행하는 쪽은 직선으로 둔다.** 두 갈래가 대등한 다른 작업일 때만 위아래로 가른다. 한쪽이 되돌아가는 루프면 그 쪽만 꺾고, 빈 자리를 만들려고 나머지를 올리지 않는다.
- **분기가 있는 장에는 통과와 실패를 모두 그린다.** 통과 경로만 그리면 실패했을 때 어떻게 되는지가 화면에서 사라진다.
- 실행 구조를 설명하는 장은 **실제로 돌릴 도구의 공식 문서를 먼저 확인하고** 그 계약에 맞춘다. 도구 이름과 명령은 화면에 내지 않고 구조와 기준만 가져온다.
- **연속한 두 해결 장은 확인 범위를 갈라 적는다.** 앞 장이 어디까지 보고 뒤 장이 무엇을 보는지 겹치지 않게 한다.
- 사용자가 요청에 넣지 않을 장치(결정 게이트 등)를 화면에 그리지 않는다.
- 문제를 여러 장 세울 때는 **문제마다 그 문제의 해결 장을 바로 뒤에 붙인다.** 해결을 마지막 요약표에서 처음 꺼내지 않는다.
- 해결 장의 동작은 **실습 가이드에서 실제로 하는 것**을 쓴다. 이론적으로 옳은 일반론을 만들어 넣지 않는다.
- **제목과 화면이 같은 동작 하나를 가리키는지 확인한다.** 제목이 A를 말하고 도식이 B를 보여주면 그 장은 실패다.
- 본문에 파트·챕터 번호로 범위를 설명하는 장이나 문구를 넣지 않는다. 다음 파트 예고도 화면이 아니라 대본에서 한다.
- 구조도에 아무것과도 연결되지 않은 카드를 두지 않는다. 화살표는 시작과 끝이 실제 요소에 닿아야 한다.


## 2026-10-06 맥락 붕괴 논리 수정

- 강사 확정 핵심: “일은 여러 에이전트에게 나눴지만, 각자에게 줄 자료는 구분하지 않았다.”
- 해결: 공통 목표·필수 조건은 함께 주되, 작업별 지침이나 필요한 자료는 필요한 담당에게 전달한다. 필요한 시점에 필요한 자료를 주는 것이 원칙이며, 작업 기준 문서는 한 예시다.

- 2장 개요·3장 문제·4장 해결·9장 요약을 맞춘다. 3·4장은 동일한 배정 구조에서 전체 자료 일괄 제공과 공통·작업별 자료 구분을 대비한다.
- 기존의 “같은 조건을 여러 칸에 반복하지 않는다”는 지침을 공통 조건 공유 금지로 해석하지 않는다. 공통 조건은 위에서 한 번 표시하고 모든 담당에게 연결한다.

- 다음부터: 해결 장의 동작은 실습자료·프로젝트 뼈대에서 실제로 하는 방식으로 쓴다. 이론상 가능한 요청 문구로 대체하지 않는다.

## 2026-10-07 — 대본 결론 먼저로 재작성

- 사용자: 대본이 핵심 없이 구구절절하다. 무엇에 대한 건지·결과가 첫 문장에 나오고 부연이 뒤따라야 한다. 기획팀 대본 1~3장 강사 정답 제공(골든셋 74절).
- 반영: 장마다 첫 문장을 그 장의 결론으로 바꾸고, 같은 말을 반복하는 문단·결론을 받치지 않는 단서를 삭제. 사용자 확정 문장(수치·연구 소개·직접 쓴 도입과 마무리)은 유지. 팀 구조 소개 영상은 앞 3장을 정답 틀(표지 → 최종 결과물 → 협업 패턴)로 맞춤.
- 다음부터: 장의 첫 문장 = 제목이 말하는 결론. 상황·질문·비유로 열지 않는다.

## 2026-10-07 — 파이프라인 프롬프트에 사업 조건 전달 추가

- 사용자: 단계별 실습은 작업마다 사업 조건을 참고하게 하는데, 파이프라인 프롬프트의 워커 전달 목록에는 사업 조건이 없다.
- 반영: boilerplate `prompts/pipeline.md` 작업 흐름 2번을 「각 워커에게 공통 지침과 사업 조건, 해당 단계의 확정 기준·양식·샘플, 앞 단계에서 통과한 문서를 전달해 줘.」로 수정(로컬, 미푸시). (edu-note 예시 프롬프트 수정은 범위 밖이라 되돌림. 테스트용 프로젝트 `[패캠] 프로젝트 테스트용/sales-item-planning-boilerplate/prompts/pipeline.md`에도 같은 수정 반영.) 대본 6장 문장도 「공통 지침과 사업 조건, 그 단계의 기준 문서」로 맞춤.

## 2026-10-07 — 대본 강사 정답 확정
