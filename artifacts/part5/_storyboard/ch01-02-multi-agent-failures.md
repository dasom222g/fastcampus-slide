# 멀티 에이전트가 오히려 나빠지는 3가지 이유 스토리보드

- 구성: 표지 · 세 실패 개요 · 문제 3장 → 해결 3장 · 적용 정리 = 9장.
- 2026-10-06 출처 재검토에 따른 전면 수정. 최신 사용자 지시가 이전 자료 과다·파일 부재·원본 대조 누락 중심의 설명을 대체한다.
- 주제: 일을 나눈 뒤에도 목적을 공유하고, 인수인계가 이어지는지 확인하며, 결과의 정확성을 별도로 검증해야 한다.

- S2: [Cemri et al., Why Do Multi-Agent LLM Systems Fail?](https://arxiv.org/html/2503.13657v3), §4, 부록 A.3·N.11. 연구는 검증 누락/불완전한 검증과 잘못된 검증을 구분한다. 검사 주체가 있거나 검사를 지시했다는 사실만으로 정확성이 보장되지 않는다.

## 1. 멀티 에이전트가 오히려 나빠지는 3가지 이유

- 질문: 담당을 늘려도 왜 결과가 나빠질 수 있는가?
- 답: 개별 작업 능력과 협업의 신뢰성은 별개다.
- 패턴: 기존 COVER_SCENE. 제목·캐릭터·연결 단절 구조 유지.
- 부제: `일을 나눈 뒤에도 목적 공유·인수인계·검증을 설계해야 합니다.`
- 발표: 최신 사용자 원고를 따른다. 스스로 협업해 더 빨리 끝낼 것이라는 기대 → 딥마인드·MIT 등이 참여한 연구에서 순차적 추론 과제의 성능 39~70% 저하 → 에이전트 수가 성능을 보장하지 않음 → 협업 설계 필요성. 성능 저하 연구는 1장에 둔다.
- 근거: S1·S2. 등장: 문구 → 연결 구조.

## 2. 자주 겪는 멀티에이전트 실패 유형

- 부제: `UC 버클리의 MAST 연구에서 분석한 실패 원인을 실무 관점에서 정리했습니다.`

- 질문: 담당 사이에서 무엇이 실패하는가?
- 답/화면: 맥락 붕괴 `할 일은 알지만 목적을 모름`, 유령 위임 `넘겼다고 생각한 일이 멈춤`, 검증 오류 `자기 결과를 스스로 통과시킴`.
- 패턴: NUMBERED_TRIO. brand/yellow/purple 세 열, 순서 화살표 없음.
- 발표: MAST 연구와 실무 적용 분석의 출처를 밝히고, 맥락 붕괴·유령 위임·검증 오류 세 이름만 나열한다. 각각의 정의·원인은 설명하지 않고 이어지는 상세 설명으로 넘긴다. 1장의 성능 저하 연구를 반복하지 않는다.
- 근거: S1, 검증은 S2로 보정. 등장: 세 열 차례로.

## 3. 01 맥락 붕괴

- 질문: 맡은 일은 했는데 왜 의도와 다른 결과가 나오는가?
- 답/부제: `각 에이전트가 할 일만 알고, 전체 목적과 배경을 놓칩니다.`
- 패턴: 기존 SCENE_IMAGE 복원. 왼쪽 설명·오른쪽 이미지, 4·5장과 동일 규격.
- 문구: `전달된 작업 / 빠진 목적·배경`, 보조 `할 일은 알아도, 왜 하는지는 모름`.
- 이미지: 기존 `ch01-02--context-loss-transparent.png`. 전달 과정의 맥락 누락을 보여준다.
- 발표: 정의 → 작업 설명과 직전 결과만 전달하는 원인 → 후속 작업까지 잘못된 방향을 이어받는 영향.
- 근거: S1 맥락 붕괴·S3 위임. 코디네이터의 존재를 전제로 정의하지 않는다. 긴 대화·자료 과다·윈도우 한계로 설명하지 않는다.
- 등장: 왼쪽 문구 → 오른쪽 이미지. 코디네이터 도식은 해결 장에만 둔다.

## 4. 02 유령 위임

- 질문: 위임했는데 왜 전체 작업이 멈추는가?
- 답/부제: `일을 넘겼는데 다음 담당에게 이어지지 않습니다.`
- 패턴: 기존 SCENE_IMAGE. 핵심 문구 두 줄 `일은 넘겼는데 / 인수인계가 끊김`, 설명 `일을 넘겼는데, 다음 담당이 시작하지 않음`.
- 기존 빈 결과함 이미지는 인계할 결과물이 누락된 한 사례로 사용한다.
- 발표: 정의 → 전달 실패·후속 배정 누락을 감지/복구하지 못함 → 대기·미완료 방치. 파일 부재는 이 중 한 사례다.
- 근거: S1 유령 위임·S3 운영 안정성. 등장: 문구 → 이미지.

## 5. 03 검증 오류

- 질문: 왜 잘못된 결과를 만들고도 완료라고 판단하는가?
- 핵심: 작성자가 자기 답안을 스스로 채점하면서, 그럴듯한 결과를 완료로 받아들이는 문제.
- 부제: `작성한 에이전트가 자기 결과를 평가하며 오류를 놓칩니다.`
- 왼쪽 큰 문구 두 줄: `자기가 쓴 답안 / 자기가 채점`. 보조: `잘못된 결과도 스스로 통과 처리`.
- 오른쪽: 기존 캐릭터의 단독 자기 승인 이미지. 같은 로봇이 작성한 오류 문서에 스스로 승인 표시를 남긴다. 별도 검증자는 등장하지 않는다. 기존 SCENE_IMAGE 좌우 배치 유지.
- 발표: 문제 정의 → 작성/평가/완료 판단을 같은 주체가 맡는 원인 → 잘못된 결과가 후속 작업으로 전달되는 영향. 해결 단계의 검증자·판정자를 미리 등장시키지 않는다.
- 근거: S1 검증 오류의 자기 채점 설명. MAST 전체 검증 실패가 모두 이 원인이라고 일반화하지 않는다.
- 등장: 문구 → 이미지.

## 6. 목적·배경 함께 전달

- 질문: 각 작업을 맡길 때 무엇을 함께 전달해야 하는가?
- 답: 모든 에이전트가 일을 시작할 때, 왜 이 작업이 필요한지 함께 전달한다.
- 해결 파트 도입 부제: `Orca는 실행을 돕는 수단이며, 목적과 기준은 우리가 정해야 합니다.`
- 발표 첫 문장: Orca의 오케스트레이션을 활용해 이 문제들을 줄일 수 있지만, 도구를 쓴다고 완전히 해결되는 건 아닙니다.
- 이어서 사람이 작업 목적·완료 기준·검증 기준을 정해야 함을 설명하고, 앞서 본 목적 누락의 원인을 짚은 뒤 전달 방법으로 연결한다.
- 해결 도식: Coordinator가 각 담당의 작업에 전체 목표·배경을 함께 담아 전달한다. 중앙 조율자는 해결 방법을 적용하는 주체로만 제시한다.
- 상단: `각 작업 시작 전 / 전체 목표·배경`.
- 하단: Worker A 카드 `자료 조사 / + 전체 목표·배경`, Worker B 카드 `초안 작성 / + 전체 목표·배경`, Worker C 카드 `검토 / + 전체 목표·배경`.
- 카드마다 두 줄만 사용한다. 작업별 이유의 긴 예시·보조 라벨·캐릭터 밑의 중복 작업명은 삭제한다. 공통 목표가 모든 담당에게 전달되는 점은 각 요청 카드에 명시한다.
- 하단 보충: `왜 해야 하는지도 함께 전달합니다.`
- 근거: S1·S3의 강의 적용. 세 갈래는 전달 범위이며 동시 실행을 뜻하지 않는다.
- 등장: 전체 목표 → 배정선 → 작업과 목표를 함께 받는 각 워커 → 하단. 기존 골격·간격 유지.

## 7. 인수인계 확인

- 질문: 완료 보고 이후 실제로 일이 이어지게 하려면?
- 답/부제: `완료 기준과 인수인계 절차를 정하고, 후속 작업의 착수까지 확인합니다.`
- 패턴: 기존 ARTIFACT_GATE 확장. 완료 기준 카드 `결과물 확인 / 후속 담당 배정` → Coordinator.
- 가로: Worker → 완료 보고 → `worker_done / 성공·실패 여부 / 결과물 경로` → Coordinator `결과물·인계 확인` → `확인 후 배정` → `다음 담당 / 착수·진행 확인`.
- orange 점선 반환 `누락·실패 · 재요청`, 라벨과 선 동일 등장 단계.
- 하단: `지연·실패를 확인하면 재요청하거나 담당을 다시 배정합니다.`
- 발표: 앞서 본 인수인계 누락의 원인을 짚고 대응한다. 파일 작업 예시에서는 파일 존재 확인을 완료 기준으로 지정. 이후 담당 배정·착수·지연 대응도 지시한다. 모두 사람이 설계하는 운영 절차다.
- 근거: S1의 체크포인트·복구 방향을 강의에 적용. worker_done 표기는 기존 사용자 확정 유지.
- 간격: 상단 카드/세로 선/아이콘 사이의 여백 및 가로 요소·화살표 양끝의 동일 간격 유지.
- 등장: 기준 → Worker → 보고선 → 보고 → Coordinator → 후속 담당 → 반환선·라벨 → 하단.

## 8. 작성·검토 분리

- 질문: 작성자의 자기 채점으로 작업이 끝나지 않게 하려면?
- 핵심/부제: `작성자와 검토자를 나누고, 검토자는 체크리스트로 통과 여부를 판단합니다.`
- 실습 적용: 작성자는 결과물을 만들고, 검토자는 검사와 통과·수정 판단을 함께 맡는다.
- 위: `체크리스트 / 필수 항목 · 근거 · 계산` 문서(purple) → 검토자.
- 가로: 작성자(brand, `결과물 작성`) → 작성 → 결과물 → 검토 → 검토자(purple, `체크리스트로 확인`) → 통과 → 다음 작업.
- 검토자 → 작성자 orange 점선: `미달 항목 · 수정 요청`. 점선과 라벨 동일 등장 단계 6.
- 하단: `체크리스트를 통과한 결과만 다음 작업으로 넘깁니다.`
- 발표: 앞서 본 자기 채점 원인을 짚고, 그 대응으로 작성/검토를 분리한다. 체크리스트의 각 항목과 대조 자료를 주고, 검토자가 확인 근거를 남기며 통과/수정을 판단한다. 수정본도 재검토.
- 근거: S1의 별도 검증 취지를 사용자 실습 구조에 적용. Executor–Validator–Critic 세 역할을 강의 실습의 필수 구조로 제시하지 않는다.
- 화면/동작: 기존 2인 QUALITY_GATE_LOOP의 간격·문서·통과/반려 경로 복원. 체크리스트 → 작성자 → 작성선 → 결과물 → 검토선·검토자 → 통과 → 수정 요청 점선 → 하단.

## 9. 협업 설계의 기준

- 각 문제명 바로 아래 회색 서브 텍스트: 맥락 붕괴 `할 일은 알지만, 목적은 모름`, 유령 위임 `일을 넘겨도, 다음 담당은 대기`, 검증 오류 `자기 결과를 스스로 채점`. 설명 다음에 기존 해결 화살표와 카드를 둔다.

- 질문: 에이전트에게 어떤 협업 지침을 줄 것인가?
- 화면: 맥락 붕괴 → `목적·배경 함께 전달 / 전체 목표와 작업의 이유`, 유령 위임 → `인수인계 확인 / 결과물·후속 담당 착수`, 검증 오류 → `작성·검토 분리 / 체크리스트로 통과 여부 확인`.
- 패턴: 기존 세 열과 세로 연결. 하단 `에이전트를 늘리기 전에 협업 절차부터 정합니다.`
- 발표: 사람이 줄 지침 세 축을 회수하고 기획팀 구성으로 연결.
- 근거: 앞 3쌍의 강의 적용 요약. 등장: 각 열 → 하단.
