# 멀티 에이전트가 오히려 나빠지는 3가지 이유 스토리보드

- 소스: `../_source/ch01-02-multi-agent-failures.md`
- 슬라이드: `../outputs/ch01-02-multi-agent-failures.html`
- 구성: 표지 1장, 확인 지점 1장, 실패 3쌍(문제·해결) 6장, 요약 1장 = 9장

## 주제

에이전트를 나눠 맡길 때는 조건 전달, 실제 결과물 확인, 원본 대조가 각각 필요하다. 세 실패를 01 맥락 붕괴, 02 유령 위임, 03 검증 오류로 구분한다. 화면의 큰 문구는 문장이 아닌 짧은 구절로 쓰고, 설명은 발표 대본에 둔다.

| 장 | 제목 | 화면의 핵심 |
|---|---|---|
| 1 | 멀티 에이전트가 오히려 나빠지는 3가지 이유 | 전달·완료·검증의 3가지 실패 지점 |
| 2 | 세 가지 실패 | 실패가 생기는 세 확인 지점 |
| 3 | 01 맥락 붕괴 | 조건이 다음 담당에게 전달되지 않는다 |
| 4 | 작업마다 기준 입력 | 작업을 시킬 때마다 그 작업에 필요한 기준을 함께 넣는다 |
| 5 | 02 유령 위임 | 완료 보고 뒤에 실제 파일이 없다 |
| 6 | 파일로 완료 확인 | 완료 보고의 성공·실패와 남긴 파일로 판단하고, 실패면 다음이 없다 |
| 7 | 03 검증 오류 | 원본 대조 없이 통과한다 |
| 8 | 기준 문서로 판정 | 코디네이터가 품질 기준으로 Y/N 판정하고 반려한다 |
| 9 | 실패를 막는 기준 | 세 실패에 대응하는 세 동작 |

**문제 한 장 다음에 반드시 그 문제의 해결 한 장이 온다.** 해결 장 셋은 같은 고정 좌표 도식(`.p5-flow`)과
같은 선 문법(실선 = 만든다·확인한다, 점선 = 거쳐서 전달된다, orange 점선 = 반려)을 쓴다.
해결 장의 동작은 이 강의 실습에서 실제로 하는 것만 쓰고, 파트·챕터 번호로 범위를 설명하지 않는다.

## 장별 구성

### 1. 표지

- 질문: 에이전트가 늘면 무엇이 더 중요해지는가?
- 문구: `전달·완료·검증 / 3가지 실패 지점`
- 구조도: Coordinator와 Worker A·B의 연결 경로에 `?`·`×`를 표시한다. 세 실패 중 한 사례로 한정되는 장면 이미지는 쓰지 않는다.
- 강조: `오히려 나빠지는`.

### 2. 세 가지 실패

- 질문: 어디에서 실패하는가?
- 01 맥락 붕괴 — 조건 전달 누락.
- 02 유령 위임 — 완료 보고와 실제 파일 불일치.
- 03 검증 오류 — 원본 대조 없는 판정.
- 세 카드는 같은 크기와 밀도로 나란히 놓는다. 순서 화살표는 쓰지 않는다.

### 3. 01 맥락 붕괴

- 질문: 맥락 붕괴란 무엇인가?
- 문구: `앞 작업의 조건 / 다음 작업에 누락`.
- 이미지: 사람이 문서를 놓치고 다음 에이전트가 그 조건을 받지 못하는 장면.
- 결과: 달라진 판단 기준.

### 4. 작업마다 기준 입력 (해결 01)

- 질문: 빠진 조건을 어떻게 전달하는가?
- 한 문장 답: 작업을 시킬 때마다 그 작업에 필요한 기준을 함께 넣는다.
- 위: Coordinator 아이콘(yellow). **아이콘이 세 워커의 가로 중앙에 온다** — 라벨이 중심을 밀지 않게 라벨은 절대배치.
- 아래: Worker A·B·C 캐릭터 3열. 각 워커 아래에 그 작업의 기준 **문서 카드** 하나.
  `자료 조사 → 조사 기준` / `초안 작성 → 작성 양식` / `검토 → 검토 기준`.
- **기준은 작업마다 다르다.** 같은 문서를 세 열에 반복하지 않는다. 구분선 목록(hr)이 아니라 문서 카드를 쓴다.
- 예시는 이 프로젝트의 문서 이름을 쓰지 않는다.
- 배정선은 **실측 좌표로 그린 곡선**이다(`drawDispatchFan`). 직각 엘보를 쓰지 않으며 화살촉은 곡선 도착 방향에 맞춘다.
- 하단: `작업이 바뀌면 넣어 주는 기준도 바뀝니다.`

### 5. 02 유령 위임 (문제)

- 질문: 유령 위임이란 무엇인가?
- 문구: `완료 보고 / 결과물 없음`.
- 이미지: 완료를 보고하지만 지정 폴더가 비어 있는 장면. (유지)

### 6. 파일로 완료 확인 (해결 02)

- 질문: 완료를 무엇으로 판단하는가?
- 한 문장 답: 완료 보고에 성공·실패와 남긴 파일이 값으로 함께 온다.
- **확인 범위는 파일이 남았는지까지다.** 내용이 기준에 맞는지는 8장이 판정한다. 이 장에 필수 항목 검사를 넣지 않는다.
- 왼쪽 `Worker`(brand) →green 실선 `완료 보고`→ 보고 카드(green): `보고에 함께 오는 것` / `성공·실패 + 남긴 파일` / `진행 중 신호는 완료가 아님`.
- 보고 카드에서 두 갈래로 나뉜다.
  - **성공은 같은 y에서 곧게 이어진다** — green 실선 `성공 · 파일 있음` → `다음 작업 시작` 카드. 계속 진행하는 경로이므로 위아래로 꺾지 않는다.
  - 실패만 아래로 빠진다 — orange 점선 `실패 · 파일 없음` → 워커로 되돌아간다.
  - 갈래마다 다른 작업이 붙는 게 아니라 한쪽은 계속, 한쪽은 되돌림이다. 계속 가는 쪽을 직선으로 둔다.
- 하단: `실패로 오거나 파일이 없으면 다음 작업은 시작되지 않습니다.`
- 사람이 여는 결정 게이트 노드를 두지 않는다. 갈래는 보고 값으로 자동으로 갈린다.
- 화면에 오케스트레이션·스킬 이름이나 명령어를 쓰지 않는다. 구조와 기준만 그것을 따른다.
- 애니메이션: 워커 → 완료 보고 선 → 보고 카드 → 성공 갈래 → 실패 갈래 → 하단 문구.

### 7. 03 검증 오류 (문제)

- 질문: 검증 오류란 무엇인가?
- 문구: `검사 완료 / 원본 대조 누락`.
- 이미지: 같은 문서를 보며 오류를 놓치는 두 에이전트. (유지)

### 8. 기준 문서로 판정 (해결 03)

- 질문: 누가 무엇으로 검사하는가?
- 한 문장 답: 작성한 워커가 아니라 코디네이터가 품질 기준으로 검사한다.
- 상단 우측: `품질 기준 / 검사 항목과 판정 규칙 / 필수 섹션 · 근거 · 계산` 문서 카드(purple). **내용 검사는 이 장이 맡는다.** 코디네이터 위에 세로 실선(yellow)으로 붙인다 — 떠 있는 카드를 두지 않는다.
- 아래 가로: `Worker / 문서 작성`(brand) →green 실선 `Output`→ `초안 / 검사 대상`(green)
  ⇢purple 점선 `완료 보고`⇢ `Coordinator / 품질 기준으로 Y/N 판정`(yellow).
- 되돌아가는 경로: 코디네이터 아래에서 워커까지 **orange 점선** 한 줄, 라벨 `반려 사유와 수정 요청`.
- 하단: `기준에 못 미치면 그 문서를 쓴 워커에게 돌려보냅니다.`
- 다른 모델 교차 검증은 이 장에서 언급하지 않는다.

### 9. 실패를 막는 기준

- 질문: 결국 무엇을 하면 되는가?
- 세 줄: `01 맥락 붕괴 — 조건·기준 문서를 참고자료로 지정` / `02 유령 위임 — 저장된 파일과 필수 항목 확인` / `03 검증 오류 — 품질 기준으로 Y/N 판정`.
- 4·6·8장에서 본 동작을 그대로 쓴다. 새 표현을 만들지 않는다.

## 화면 검수 기준

- 표지는 승인 덱과 같은 왼쪽 제목·오른쪽 시각 슬롯 규격을 따른다. 관계를 보여주는 구조도는 SVG/HTML로 그린다.
- 3·5·7장(문제)은 동일한 장면 이미지 규격을 쓰고, 큰 문구와 보조 문구 모두 짧은 구절로 제한한다.
- 장면은 이미지, 문서 간 관계와 화살표는 HTML/SVG 도식으로 표현한다.
- 전 장을 1920×1080과 1280×800에서 구조도·이미지 잘림, 본문 겹침, 강제 줄바꿈으로 확인한다.
- 4·6·8장은 좌표를 고정하고 등장만 opacity 페이드한다. 첫 프레임과 마지막 프레임의 노드·선 위치가 같아야 한다.
- 파트·챕터 번호로 범위를 설명하는 문구가 본문에 없는지 확인한다. 머리말 `slide__label`은 예외다.
