# Ch01-01. Generator–Evaluator 패턴이란

제작 목표: 만드는 쪽과 판정하는 쪽을 나누는 이유를 이해하고, 기준·판정·반려·라운드로 이어지는 루프의 모양을 본다.

## 앞 파트와 겹치지 않게

Part 5 Ch01-02에서 **검증 오류**를 실패 세 가지 중 하나로 다뤘다. 거기서는 "작성자의 설명에 동의하는 것만으로는 오류가 드러나지 않는다"까지였고, 해결로 생성과 평가의 분리를 한 장에 보여줬다.
이 클립은 그 해결을 펼치는 자리다. **같은 설명을 반복하지 않고 한 줄로 회수한 뒤**, 기준을 언제 정하는지·판정을 어떻게 남기는지·반려가 어떻게 다음 입력이 되는지로 바로 들어간다.

## 사실과 제작 범위

- 다른 모델을 쓰면 오류가 없어진다고 말하지 않는다. 같은 모델이 같은 방식으로 놓치는 것을 줄이는 방법이다.
- 체크리스트 항목 수는 프로젝트마다 다르다. 특정 개수를 정답으로 고정하지 않는다.
- 검산 스크립트·역할 분리 실행은 Part 6 실습(Ch03~04)에서 한다. 이 클립은 구조만 다룬다.
- 완성 프로젝트의 라운드 기록은 실제 실행 결과이며, 반려 횟수를 목표치로 제시하지 않는다.

## 화면 구성

### 1. Generator–Evaluator 패턴이란

역할: COVER_SCENE

> 만드는 에이전트와 판정하는 에이전트를 나눠, 통과할 때까지 돌립니다.

화면: 왼쪽 로봇이 제안서를 작성하고 오른쪽 로봇이 체크리스트와 돋보기로 검사하는 장면 이미지 1점.

슬라이드: 1장
근거: 실습자료 「전체 구조 이해」

### 2. 자기 결과는 자기가 통과시킨다

역할: SCENE_COMPARE

> 만든 쪽에게 다시 물으면 대개 문제없다는 답이 돌아옵니다.

말할 내용

- 초안을 쓴 에이전트에게 "문제없지?"라고 물으면 자기 결론을 다시 설명한다
- Part 5에서 본 검증 오류가 이 자리다. 여기서는 그 해결을 펼친다
- 판정하는 쪽이 따로 있어야 통과·반려가 의미를 가진다

슬라이드: 1장
근거: Part 5 Ch01-02 검증 오류, 실습자료 4절 역할 지정

### 3. 만드는 쪽과 판정하는 쪽

역할: STRUCTURE_EXCHANGE

> Generator는 작성하고 Evaluator는 판정합니다. 서로의 역할을 넘지 않습니다.

화면 문구·요소:
```json
{
  "left": ["Generator", "작성자", "브리프와 회사 문서를 읽고 초안을 쓴다"],
  "right": ["Evaluator", "평가자", "고정한 기준으로 판정하고 사유를 남긴다"],
  "note": "평가자는 초안을 직접 고치지 않습니다."
}
```

슬라이드: 1장
근거: 실습자료 용어표, 4절 「역할」

### 4. 다른 모델로 평가하는 이유

역할: OPEN_TRIPTYCH

> 같은 모델은 같은 자리에서 같은 방식으로 놓칩니다.

화면 문구·요소:
```json
{
  "items": [
    ["같은 판단 습관", "만든 근거를 그대로 다시 쓴다"],
    ["다른 하네스", "작성은 Codex, 평가는 Claude Code"],
    ["보장은 아니다", "다른 모델도 놓칠 수 있어 기준과 근거가 필요하다"]
  ]
}
```

슬라이드: 1장
근거: 실습자료 사전 준비·전체 구조, Part 5 Ch01-02의 단서

### 5. 기준은 먼저, 따로

역할: PROCESS_STRIP

> 체크리스트를 첫 평가 전에 정하고 작성자에게는 전달하지 않습니다.

화면 문구·요소:
```json
{
  "items": [
    ["기준 작성", "첫 평가 전에 저장", "purple"],
    ["전 라운드 동일 적용", "같은 기준으로 매번 검사", "yellow"],
    ["작성자에게 비공개", "기준에 맞춘 글쓰기를 막는다", "gray"]
  ]
}
```

슬라이드: 1장
근거: 실습자료 3절 판정 규칙

### 6. 판정은 항목별로

역할: GOAL_ACCEPTANCE

> 항목마다 통과·반려와 이유를 남기고, 한 오류를 여러 항목에 중복으로 세지 않습니다.

화면: 체크리스트 항목 4~5개에 Y/N 표시와 통과 수 표기. 실제 금액·수치는 넣지 않는다.

슬라이드: 1장
근거: 실습자료 3절 판정 규칙

### 7. 반려는 사유와 수정 요청으로

역할: SEMINAR_IO_FLOW

> 반려된 항목과 고칠 내용을 문서로 남겨 작성자에게 넘깁니다.

화면: 평가 기록 → 수정 요청 문서 → 작성자. 평가 전체가 아니라 반려 사유만 전달한다는 점을 표시.

슬라이드: 1장
근거: 실습자료 4·5절

### 8. 통과할 때까지 도는 루프

역할: REVIEW_LOOP

> 한 라운드는 작성·수정 → 평가·검산 → 판정입니다.

화면: 라운드 루프 도식과 실제 교차 검토 보고서의 라운드 판정 기록 캡처.

슬라이드: 1장
근거: 실습자료 용어표·6절, `project2-ads-proposal/final/cross-review-report.html`

### 9. 어디에 쓰나

역할: SCENE_PAIR

> 숫자와 약속이 들어가는 문서일수록 만든 쪽과 판정하는 쪽을 나눕니다.

말할 내용

- 제안서·견적서처럼 금액과 기한이 들어간 문서
- 고객에게 그대로 나가는 문서
