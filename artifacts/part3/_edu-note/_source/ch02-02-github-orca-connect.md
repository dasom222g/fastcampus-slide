# GitHub 저장소 생성부터 에이전트 작업·업로드까지

내일 `edu-note` 스킬로 실습자료를 제작할 때 사용할 기획 원자료다. 아래 순서는 강사가 저장을 요청한 구성이다. 실제 실행 로그나 완성된 수강생용 실습자료는 아니다.

## 1. 대상과 교육 의도

- 대상: 비개발자. Git 개념이 익숙하지 않고 GitHub도 처음 보는 수강생.
- 목표: GitHub 저장소와 내 컴퓨터의 작업 폴더를 구분하고, 에이전트에게 작업을 맡긴 뒤 커밋·푸시로 결과를 기록하고 올리는 흐름 이해.
- 직접 하는 범위: GitHub 저장소 생성, Orca에서 URL로 열기, 작업 결과 확인, GitHub에서 업로드 결과 확인.
- 에이전트에게 맡기는 범위: 파일 생성·수정, 확인한 변경의 커밋, GitHub로 푸시.
- 수동 조작을 남기는 이유: 앞으로 계속 찾아가고 확인할 장소를 직접 경험하게 하기 위해서다. 저장소 이름·공개 범위를 정하고 URL을 복사하면서 결과물이 어디에 보관되는지 익힌다.
- 이해를 확인할 지점: 처음 만들어진 저장소 화면 → Orca의 로컬 작업 폴더 → 푸시 후 GitHub에 파일과 커밋이 나타난 화면.

## 2. 실습 진행 구성 — 확정

| 단계 | 방식 | 수강생이 이해할 것 |
|---|---|---|
| GitHub 저장소 생성 | 직접 | 프로젝트를 보관할 곳, 이름, 공개 범위 |
| Orca에서 URL로 열기 | 직접 | GitHub 저장소와 내 작업 폴더의 연결 |
| 파일 생성·수정 | 에이전트에게 요청 | 실제 작업은 내 컴퓨터의 폴더에서 진행 |
| 커밋 | 확인 후 에이전트에게 요청 | 지금 결과를 버전으로 기록 |
| 푸시 | 에이전트에게 요청 | 기록한 버전을 GitHub에 업로드 |
| GitHub에서 결과 확인 | 직접 | 파일과 커밋이 실제로 올라왔는지 확인 |

## 3. 제작 시 유지할 구분

- 파일 작업, 커밋, 푸시는 각각 나눠 요청한다. 첫 실습부터 ‘만들고 커밋하고 푸시까지 해줘’로 묶지 않는다.
- 파일 생성·수정은 로컬 작업, 커밋은 버전 기록, 푸시는 GitHub 업로드라는 차이를 실행 전후 화면으로 확인한다.
- `git init`, `git remote`를 직접 입력하는 경로를 먼저 시연한 뒤 같은 작업을 AI로 반복하는 구성은 사용하지 않는다. 이번 실습 경로는 GitHub에서 만든 저장소를 URL로 클론하는 것이다.
- 저장소 생성도 자연어로 요청할 수 있다는 점은 마지막에 짧게 언급한다. 같은 과정을 자동 방식으로 다시 시연할 필요는 없다.

마지막에 덧붙일 설명의 취지:

> 저장소를 만드는 것도 에이전트에게 맡길 수 있습니다. 오늘은 우리가 어디에서 작업하고 어디에 올리는지 확인하려고 직접 만들어 봤습니다. 다음부터는 이 과정도 요청해서 처리할 수 있습니다.

## 4. 실제 실습 시 채울 기록

아직 실행하지 않았으므로 성공한 프롬프트·화면·결과·실패 사례를 만들어 적지 않는다. 제작할 때 다음을 실제 진행 순서대로 기록한다.

- GitHub 가입·로그인과 저장소 생성 화면, 저장소 이름·공개 범위.
- README를 포함해 첫 커밋을 만들어 둘지 여부. 앞선 논의에서는 이후 워크트리 실습을 위해 README 포함을 제안했다.
- Orca의 URL 입력 위치, 로컬 저장 경로, 실제 연결 결과.
- Git 설치·초기 설정 및 GitHub 인증 확인. Git 설치·초기 설정 자체는 앞 클립 Ch02-01의 범위.
- 만들 결과물과 실제로 사용한 파일 작업·커밋·푸시 프롬프트.
- 각 단계 실행 전후 화면과 GitHub에서 확인한 최종 파일·커밋.
- 실제로 겪은 오류가 있다면 증상과 해결. 없으면 없는 것으로 기록.
