## 2차 — 개념·구성·디자인 분석 후 개선 — 반영완료

- 사용자 요청: 정식 HTML을 분석하고 부족한 점을 수정한다.
- 표지 누락, 브랜치·워크트리의 대체 관계 오해, 후반의 같은 폴더 도식 반복, 옛 카드·개별 타이포 규격을 확인했다.
- 표지를 추가하고 기존 브랜치 정의와 분기·합류를 한 장으로 통합해 8장을 유지했다. 커밋 범례, 기준·작업 브랜치 라벨, 분기·병합 위치를 표시했다.
- 워크트리를 같은 저장소에 연결된 실제 작업 폴더로 정의했다. 기본 작업 폴더도 워크트리임을 대본에서 설명한다. 개념 비교에서 ‘브랜치=폴더 하나’ 대비를 없앴다.
- 5번은 각 폴더 안의 브랜치 라벨과 공유 이력 연결로 새로 구성했다. 7번의 승인된 본문은 그대로 보존했다. 8번은 Orca→작업 폴더 생성의 짧은 도식으로 정리했다.
- 기존 두 투명 장면 이미지를 유지했다. 1·3·4·8번의 선언문을 같은 Pretendard 규격으로 통일했다. 템플릿 파일 자체는 변경하지 않았다.
- 분기·병합은 선과 커밋 점을 제자리에서 순차 표시한다. CSS 지연으로 재진입 때도 순서가 유지된다.
- 소스·스토리보드·전체 대본을 동기화했다. 분석 보고서와 전후 캡처를 `_qa/`에 저장했다.
- 검수: 2133×1200·1280×800 전 8장, 본문·제목 넘침 없음. HTTP·파일 직접 열기에서 이미지 정상. 버튼·화살표·스페이스·하단 이동·본문 클릭 유지·페이지 경계·URL/번호 동기화 정상. 브랜치 도식의 최초·중도 이탈 후 재진입 순서 확인. 브라우저 오류 없음.

## 3차 — 한 폴더에서 한 번에 한 브랜치 — 반영완료

- 3번의 보조 설명을 ‘한 폴더에서는 한 번에 한 브랜치를 엽니다.’로 변경했다.
- 핵심은 브랜치 전환의 결과보다 한 작업 폴더에서 동시에 열어두는 브랜치가 하나라는 제약이다. 대본도 이 제약에서 각자의 작업 폴더가 필요한 이유로 이어지도록 맞췄다.
- 소스·스토리보드·대본을 동기화했다. 디자인·글자 규격·장수는 유지했다.
- 2133×1200·1280×800의 3번 화면에서 문구·이미지·넘침 정상 확인.

## 4차 — 타임머신 비유 한 장 추가 — 반영완료

- 요청대로 기존 8장 본문을 보존하고, 3번 다음에 비유 장 「한 번에 한 시점만」을 추가했다. 현재 총 9장이다.
- 타임머신 한 대와 여러 대를 같은 시간선 구조로 대비했다. 시간선=브랜치, 시점=커밋, 타임머신=작업 폴더의 대응을 하단에 표시했다.
- 브랜치 전환 전에 반드시 커밋해야 한다거나, 에이전트 수만큼 워크트리가 무조건 필요하다는 단정은 넣지 않았다. 서로 다른 브랜치의 동시 작업이라는 범위를 대본에서 설명한다.
- 소스·스토리보드·대본·목록의 장수와 번호를 동기화했다. 기존 8개 article 본문은 data-index 외 변경 없음 확인.
- 2133×1200·1280×800의 새 장 이미지와 넘침 정상. 3→4→5, 마지막 9번 이동과 경계, 4번 복귀, 번호·점 이동 정상.

## 5차 — 중복 슬라이드 구성 검토 — 제안만, 미적용

- 비유 장을 채택한다면 현재 3번 「한 폴더의 한계」, 5번 「폴더를 하나 더」는 비유와 역할이 겹친다. 7번 「줄기와 작업 폴더」도 정의를 반복한다.
- 권장 구성은 현재 1→2→4→6→8→9의 6장이다. 5번의 정확한 워크트리 정의는 6번 실제 폴더 구조 장으로 옮기는 조건이다.
- 사용자는 중복 여부를 물었으므로 삭제·이동은 적용하지 않았다. 기존 보존 요청에 따라 현재 9장을 유지한다.

## 6차 — 중복 두 장 제거·쓰임 비교 유지 — 반영완료

- 사용자 정정: 두 개념을 비교하는 클립이므로 한 장에서 나란히 비교하는 장은 필요하다. 기존 제안 중 두 장의 삭제만 수용하고 「줄기와 작업 폴더」는 유지한다.
- 기존 9장 중 3번 「한 폴더의 한계」와 5번 「폴더를 하나 더」를 제거해 7장으로 정리했다. 투명 PNG 파일은 보존했다.
- 비교 장은 새 5번 「브랜치와 워크트리, 언제 쓸까?」로 변경했다. 양쪽 라벨은 「작업 이력을 나눌 때」·「여러 브랜치에서 동시에 작업할 때」로 맞췄다. 기존 도식·정의·함께 쓰는 관계는 유지했다.
- 사용자가 인용한 대본 문장 「브랜치와 워크트리는 하나를 골라 쓰는 관계가 아닙니다. 브랜치로 작업 이력을 나누고, 워크트리마다 서로 다른 브랜치를 열어 두어 동시에 진행할 수 있습니다.」를 그대로 유지했다.
- 제거한 워크트리 장의 정의를 새 4번 실제 폴더 구조 장의 부제와 대본에 옮겼다. 원래 폴더도 워크트리라는 설명을 보존했다.
- 소스·스토리보드·대본·HTML·정식 및 Codex 목록의 장수·번호를 동기화했다. CSS와 남은 도식은 변경하지 않았다.
- 검수: 2133×1200·1280×800 전 7장(14화면) 렌더링·시각 확인. 본문·헤더 넘침 없음, 이미지 정상. 비교 제목·양쪽 라벨 한 줄. 버튼·하단 점·키보드·마지막 경계·본문 클릭 시 이동 없음·페이지 번호 동기화 정상.

## 7차 — 물리적으로 독립된 작업 파일 표현 — 반영완료

- 4번 A·B 폴더의 마지막 파일을 각각 브랜드 빨강·보라로 표시했다. 원래 폴더와 나머지 파일은 중립색을 유지한다. 폴더별로 서로 다른 파일 상태임을 그림에서 바로 구분한다.
- 하단 문장을 「워크트리는 물리적으로 분리된 작업 폴더이므로, 각 폴더의 작업 파일은 서로 영향을 받지 않습니다.」로 변경했다. 핵심을 자동 반영 여부에서 작업 파일의 물리적 독립성으로 옮겼다.
- 공통 연결 영역은 「공유하는 Git 저장소」로 명확히 했다. 브랜치·커밋 정보는 공유하고, 실제 작업 파일은 각 폴더에 따로 있다는 설명을 대본에 맞췄다.
- 소스·스토리보드·대본을 동기화했다. 나머지 6장과 전체 CSS·폰트·레이아웃 보존 확인.
- 검수: 2133×1200·1280×800 4번 화면에서 파일 색상·한 줄 하단 문구·이미지 로딩·헤더/본문 넘침 정상. 캡처와 보고서는 `_qa/`의 independent-files 파일에 저장했다.

## 8차 — 생성 흐름 비교안 한 장 추가 — 반영완료

- 요청: 기존 4번을 덮어쓰지 않고 제안한 장을 추가해 비교한다.
- 4번 다음에 새 5번 「같은 버전에서, 각자의 작업으로」를 추가했다. 기존 7개 article은 data-index 외 변경 없이 유지했고 총 8장으로 맞췄다.
- 왼쪽 main의 「커밋된 버전 v1」에서, 「v1을 기준으로 생성」 화살표가 A·B 작업 폴더로 갈라진다. 각 폴더 안에 해당 브랜치가 표시된다. 마지막 파일의 빨강·보라는 생성 후 각자 수정한 상태임을 캡션과 대본에 명시했다.
- 기존 4번과 같은 하단 핵심 문구를 썼다. 비교안에는 공유 저장소 연결선을 넣지 않았다.
- 폴더 도형·파일 배치·공통 타이포를 재사용했다. 새 장 전용 CSS만 추가하고 기존 CSS를 보존했다.
- 소스·스토리보드·대본·HTML·정식 및 Codex 목록의 번호와 장수를 동기화했다.
- 2133×1200·1280×800에서 새 장 시각 검수 완료. 작은 화면의 SVG 최소 높이로 인한 겹침을 새 장의 grid 행 규격으로 해결했다. 파일 색상·이미지 로딩·헤더/본문 넘침 정상. 4→5→6, 마지막 8번 이동·경계·5번 복귀·페이지 번호·하단 점 동기화 정상.

## 9차 — 브랜치와 워크트리의 관계 공식 문서 검토 — 답변·제안

- 사용자 지적: 「언제 쓸까?」라는 비교가 두 개념을 선택지처럼 보이게 한다. 브랜치로 작업 이력을 나누고 그 브랜치의 파일을 워크트리에서 실제로 작업하는 관계가 핵심이다.
- 공식 문서 확인: 브랜치는 커밋을 가리키는 이동 가능한 참조이다. 브랜치 생성만으로 작업 폴더가 늘어나지 않는다. worktree add는 같은 저장소에 연결된 작업 폴더를 만들고 지정한 브랜치·커밋의 파일을 체크아웃한다.
- 원래 작업 폴더도 워크트리이며 브랜치마다 추가 워크트리가 필수인 것은 아니다. 여러 브랜치에서 동시에 작업하려 할 때 추가한다.
- 답변에서 기존 비교 장을 「브랜치와 워크트리의 관계」로 이름 짓고 브랜치 A↔작업 폴더 A, 브랜치 B↔작업 폴더 B를 연결하는 안을 제안했다. 이번 질문은 공식 문서 기반 확인 요청이므로 이 비교 장 자체는 아직 수정하지 않았다.
- 근거: https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell · https://git-scm.com/docs/git-worktree#_description · https://git-scm.com/docs/git-worktree#_commands

## 10차 — 워크트리가 필요한 문제부터 설명 — 반영완료

- 사용자 정정: 같은 폴더에서 여러 에이전트가 같은 파일을 건드리므로 독립 작업 공간이 필요하다는 문제에서 출발한다. 워크트리의 동시 작업 구조를 이해하기 위해 브랜치를 설명하는 흐름이다.
- 표지 다음에 새 2번 「한 폴더에서 겹치는 작업」을 추가했다. 「에이전트는 둘, 작업 폴더는 하나」와 기존 투명 공유 책상 장면으로 실제 파일을 함께 수정하는 문제를 보여준다.
- 대본은 문제→워크트리로 공간을 나눌 필요→각 작업 이력을 구분하는 브랜치→워크트리에서 동시 작업으로 연결했다.
- 기존 「언제 쓸까?」는 새 7번 「브랜치와 워크트리의 관계」로 바꿨다. 왼쪽 실제 작업 폴더 A·B를 오른쪽 각 작업 브랜치의 이력에 연결한다. 관계선에 커밋 점과 같은 표식을 쓰지 않는다.
- 「원래 작업 폴더도 워크트리」·브랜치당 추가 폴더 필요 여부·워크트리당 에이전트 수 같은 부연은 대본에서 덜어냈다. main을 열어 둔 작업 폴더라는 정확한 예시는 유지했다.
- 기존 공유 저장소 구조 장과 생성 흐름 비교안은 새 5·6번으로 모두 보존했다. 승인된 에이전트 작업 공간 장은 8번으로 본문을 그대로 유지했다. 총 9장으로 문서·대본·목록·HTML 번호를 동기화했다.

## 11차 — 생성 흐름을 수직 구조로 변경 — 반영완료

- 대상은 새 6번 「같은 버전에서, 각자의 작업으로」다. 원래 작업 폴더를 상단의 작은 출발점으로, A·B 워크트리를 하단의 큰 두 폴더로 배치했다.
- 화살표는 main에 커밋된 v1에서 아래로 갈라진다. A의 마지막 파일은 빨강, B는 보라로 유지했다. 「생성 후 각자 수정」과 하단 독립 작업 문구를 보존했다.
- main의 이름과 버전 라벨은 작은 폴더 옆에 둬 내부 파일과 겹치지 않게 했다. 공통 글자 크기는 유지하고 이 장의 공간 배분만 조정했다.
- 시각 검수: 2133×1200·1280×800 전 9장 검사 후, 마지막 수정한 6·7번을 두 크기로 다시 검수했다. 이미지·본문·제목 넘침 및 겹침 없음. 비교용 기존 구조 장과 승인된 작업 공간 장 본문 보존 확인.
- 동작 검수: 2→3, 5→6→7, 마지막 9번·다음 버튼 비활성·6번 복귀·하단 점·번호 동기화 정상. 본문 클릭으로 이동하지 않음.
- 증빙: `_qa/`의 problem-first, current-final 및 vertical-origin 캡처·보고서.

## 12차 — 독립 작업 메시지를 헤더로 이동하고 도식 공간 확보 — 반영완료

- 6번 제목을 「물리적으로 분리된 작업 폴더」, 서브텍스트를 「각 워크트리의 작업 파일은 서로 영향을 받지 않습니다.」로 변경했다. 기존 하단 문장은 삭제했다.
- 이 장의 slide__body에만 gap:0을 적용했다. main·작업 A·작업 B의 브랜치 아이콘과 라벨은 모두 폴더 안 같은 상대 위치에 배치했다.
- main 옆 설명은 「v1 시점」만 남겼다. 「원래 작업 폴더」와 「v1을 기준으로 생성」은 삭제했다. A·B 폴더는 작은 화면에서도 더 크게 표시하고 공통 폰트 크기는 유지했다.
- 소스·스토리보드·대본을 동기화했다. 나머지 8장 본문은 바이트 단위로 동일하다.
- 검수: 2133×1200·1280×800의 6번 캡처, 이미지 로드·제목·본문 넘침 없음. main 브랜치 표시와 내부 파일이 겹치지 않음을 확인했다. 증빙: `_qa/`의 workspace-header 캡처와 레이아웃 보고서.

## 13차 — 본문 바깥 부모 행 간격 제거 — 반영완료

- 사용자 지적: 본문 gap을 없앴다고 했지만 여전히 간격이 남아 있었다.
- 원인: slide__body 내부 간격만 0으로 바뀌었고 부모 .slide의 행 간격은 남아 있었다. 1280×800에서 헤더→본문·본문→푸터가 각각 30px임을 실측했다.
- 6번 부모 .slide에만 gap:0을 추가했다. 기본 헤더·푸터 패딩과 나머지 8장 간격은 유지했다.
- 검수: 부모·본문 gap과 두 행 사이 실제 거리가 모두 0px. 2133×1200·1280×800의 제목·본문 넘침 및 이미지 이상 없음. 증빙은 `_qa/`의 parent-gap 캡처·보고서.

## 14차 — 실제 남는 높이의 원인 수정 — 반영완료

- 사용자 캡처의 위아래 빗금은 gap 속성이 아니라 세로 중앙 정렬로 분배된 여유 공간이었다. 도식은 내용 높이만큼만 차지하고 A·B 폴더의 최대 너비가 21rem으로 제한되어 있었다.

- 6번 본문을 명시적인 행으로 나누고 도식이 남은 높이를 사용하게 했다. 작은 main과 연결선 아래의 공간은 A·B 폴더가 사용한다. 폴더는 비율을 유지해 확대하며 선 두께와 글자 크기는 유지한다.
- 2133×1200·1551×1000·1280×800에서 본문 위쪽→도식, 도식→하단 문장, 하단 문장→본문 아래쪽의 남는 간격이 모두 0px임을 실측했다. 캡처에서도 큰 위아래 빈 띠가 제거됐다.
