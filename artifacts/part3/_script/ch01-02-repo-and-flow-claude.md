## 저장소와 작업흐름 슬라이드 대본 (8장) - 클로드

## 슬라이드 1/8 — 저장소와 작업흐름 (표지)

앞에서 Git은 파일이 어떻게 바뀌었는지를 기록하는 시스템이라고 했죠. 이번에는 그 기록을 어디에 두고 어떻게 남기는지 보겠습니다.

여기서 하나 미리 알고 가셔야 할 게 있어요. 파일을 저장하는 거랑 Git에 기록을 남기는 건 별개의 동작입니다. 평소처럼 컨트롤 S 눌렀다고 버전이 하나 생기는 게 아니거든요.

이게 왜 별개인지, 그리고 기록이 남기까지 어떤 단계를 거치는지 순서대로 따라가 보겠습니다.

## 슬라이드 2/8 — 저장소란

저장소는 영어로 Repository라고 합니다. 이름만 들으면 뭔가 특별한 것 같은데, 일반 폴더랑 나란히 놓고 보면 금방 이해되실 거예요.

일반 폴더는 파일을 담아두는 곳입니다. 문서든 코드든 이미지든 넣어두고 열어서 고치죠. 예전 내용을 남기고 싶으면 파일을 복사해두는 수밖에 없고요. 앞에서 본 최종, 진짜최종이 그렇게 생긴 겁니다.

Git으로 관리하는 프로젝트에는 여기에 하나가 더 있습니다. 점 git이라는 숨김 폴더예요. 이 안에 Git이 변경 이력이랑 설정을 보관합니다. 그러니까 내가 고치는 파일들 옆에, 그 파일들이 어떻게 바뀌어왔는지를 들고 있는 폴더가 같이 있는 거죠.

점 git은 내가 직접 문서를 넣고 빼는 데가 아닙니다. Git이 알아서 쓰고 읽는 자리예요. 저는 이걸 잘못 건드려서 이력을 날려본 적도 있는데, 열어볼 일은 거의 없다고 보시면 됩니다.

그래서 저장소는 파일을 담는 데다가 그 파일들의 이력까지 같이 관리하는 폴더인 겁니다.

## 슬라이드 3/8 — 버전 관리를 위한 3 단계

그럼 기록이 어떻게 남는지 볼 텐데요. Git은 이걸 세 자리로 나눠놨습니다. 작업하는 자리, 담아두는 자리, 기록되는 자리.

첫 번째가 작업 디렉토리입니다. 영어로 Working Directory인데, 우리가 평소에 보고 고치는 그 폴더예요. 여기서 문서를 쓰고 코드를 고치고 파일을 만들고 지웁니다. 특별할 게 없는 자리죠.

여기서 소개 문서를 열어서 내용을 바꾸고 저장했다고 해볼게요. 파일 내용은 분명히 바뀌었습니다. 그런데 Git 입장에서는 아직 아무 기록도 안 남았어요. 뭔가 바뀐 것 같다고 감지만 하고 있는 상태입니다.

아까 말씀드린 저장하고 기록이 별개라는 게 이 얘기예요. 저장은 지금 파일을 덮어쓰는 거고, 기록은 이 시점을 따로 남겨두는 겁니다.

## 슬라이드 4/8 — 버전 관리를 위한 3 단계

두 번째 자리가 스테이징 영역입니다. Index라고도 부르는데요. 다음에 남길 기록에 뭘 담을지 골라두는 자리예요.

이게 왜 필요하냐면, 작업하다 보면 파일 여러 개를 한꺼번에 고치게 되거든요. 근데 그게 다 한 덩어리로 묶일 일은 아니잖아요. 로그인 기능 고친 거랑 오타 하나 잡은 거를 같은 기록에 넣으면 나중에 이력을 봐도 뭐가 뭔지 모릅니다.

그래서 이번 기록에 담을 것만 골라서 여기다 담아둡니다. 그때 쓰는 명령어가 git add고요. 장바구니에 담는 거랑 비슷해요. 담았다고 산 건 아니고, 살 것만 골라놓은 상태인 거죠.

파일이 작업 폴더에서 여기로 옮겨가는 것도 아닙니다. 파일은 그 자리에 그대로 있고, 그 시점의 내용만 다음 기록용으로 찍혀 있는 겁니다.

## 슬라이드 5/8 — 버전 관리를 위한 3 단계

세 번째가 로컬 저장소입니다. 골라둔 걸 실제 기록으로 남기는 자리예요. 장바구니로 치면 여기서 결제가 되는 겁니다.

이때 쓰는 명령어가 git commit이고, 이렇게 남긴 기록 하나하나를 커밋이라고 부릅니다. 커밋마다 고유한 이름표가 붙는데 이걸 해시라고 해요. 기록이 수백 개가 돼도 서로 구분되게 하는 장치입니다.

여기서 로컬이라는 말을 기억해두세요. 세 자리가 전부 내 컴퓨터 안에 있습니다. 인터넷이랑 아직 아무 상관이 없어요.

정리하면 고치는 자리, 담아두는 자리, 기록되는 자리가 이렇게 나뉘어 있는 겁니다. 한 번에 안 하고 굳이 나눠놓은 이유가 방금 말씀드린 골라 담기예요.

## 슬라이드 6/8 — 기록으로 남는 순간 - commit

커밋 하나에 뭐가 들어가는지 조금 더 보겠습니다.

커밋에는 그 시점의 프로젝트 내용이 통째로 남습니다. 바뀐 문장 몇 개만 메모해두는 게 아니에요. 그래서 나중에 그 커밋으로 돌아가면 그때 상태를 그대로 다시 볼 수 있는 겁니다.

그리고 커밋 메시지가 붙습니다. 이번에 뭘 왜 했는지 적는 한 줄인데요. 앞에서 파일 이름으로 관리할 때 이름만 봐서는 뭐가 바뀐지 모른다고 했잖아요. 그 문제를 여기서 푸는 겁니다. 시점만 남기는 게 아니라 이유까지 같이 남기는 거죠.

작성자랑 시간도 자동으로 붙습니다. 그래서 나중에 누가 언제 뭘 왜 고쳤는지가 한 줄로 읽힙니다.

한 가지만 다시 짚을게요. Git으로 관리하는 폴더라도 파일을 고치고 저장하는 것만으로는 버전이 안 생깁니다. 커밋한 시점만 돌아갈 수 있는 지점이에요.

## 슬라이드 7/8 — 내 기록과 원격 기록

지금까지 본 건 전부 내 컴퓨터 안이었습니다. 이걸 로컬 저장소라고 하고요. 여기에 원격 저장소가 하나 더 붙습니다.

원격 저장소는 인터넷에 올려둔 같은 프로젝트예요. GitHub가 그 자리를 제공하는 서비스 중 하나고요. 여기에 올려두면 다른 사람이랑 같이 보거나, 다른 컴퓨터에서 이어서 작업할 수 있습니다.

내 기록을 원격으로 보내는 게 git push, 원격에 있는 걸 받아오는 게 git pull입니다.

중요한 건 이겁니다. 내 컴퓨터에 커밋했다고 원격이 저절로 바뀌지 않아요. 기록을 남기는 거랑 남긴 걸 공유하는 건 완전히 다른 동작입니다. 이걸 헷갈리면 나는 분명히 커밋했는데 상대방은 못 보는 상황이 생깁니다. 올리는 걸 안 한 거죠.

## 슬라이드 8/8 — 한 번의 작업 흐름

지금까지 본 걸 한 줄로 이으면 네 단계입니다. 고친다, 고른다, 남긴다, 올린다.

고치는 건 작업 디렉토리에서, 고르는 건 git add로 스테이징에, 남기는 건 git commit으로 로컬 저장소에, 올리는 건 git push로 원격 저장소에 합니다. 아까 나눠서 본 자리들이 이렇게 순서대로 붙는 거예요.

여기서 경계 하나만 잡고 가시면 됩니다. 고치고 고르고 남기는 세 단계는 전부 내 컴퓨터 안에서 벌어집니다. 인터넷이 끊겨 있어도 다 돼요. 마지막 올리는 단계에서만 밖으로 나갑니다.

명령어를 지금 외우실 필요는 없습니다. 실제로 어떻게 치는지는 실습에서 볼 거고요. 지금은 자리가 넷으로 나뉘어 있고 그중 셋은 내 컴퓨터 안이라는 것만 잡고 가시면 충분합니다.

다음 영상에서는 같은 프로젝트에서 작업 줄기를 나누는 방법을 볼 겁니다. 브랜치랑 워크트리가 어떻게 다른지 이어서 보겠습니다.
