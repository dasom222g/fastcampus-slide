## 브랜치와 워크트리 차이 슬라이드 대본 (8장) - 클로드

## 슬라이드 1/8 — 브랜치와 워크트리 차이 (표지)

앞에서 커밋으로 버전을 남기는 방법까지 봤죠. 이번에는 Orca를 쓸 때 핵심이 되는 개념, 워크트리를 볼 겁니다.

Orca의 기본 작업 단위가 워크트리라고 앞에서 말씀드렸는데, 그게 왜 폴더가 아니라 워크트리여야 하는지가 오늘 풀 얘기예요.

개념부터 꺼내지 않고 문제부터 보겠습니다. 여러 에이전트한테 일을 나눠 줬는데 일하는 폴더가 하나면 어떻게 되는지부터요.

## 슬라이드 2/8 — 한 폴더에서 겹치는 작업

에이전트 둘이 같은 프로젝트 폴더에서 일한다고 해보겠습니다. A가 문서를 고치는 동안 B도 같은 문서를 열고 수정하면, 한쪽이 저장한 내용 위에 다른 쪽이 자기 내용을 덮어씁니다. 일은 나눴는데 실제 파일을 놓는 자리는 하나인 거예요.

앞에서 터미널 얘기할 때 같은 책상을 셋이 쓰고 있는 거라고 했죠. 지금이 딱 그 상황입니다. 각자 자기 파일을 놓고 동시에 진행할 공간이 있어야 합니다.

그럼 익숙한 방법대로 프로젝트 폴더를 통째로 복사하면 될까요.

앞에서 본 점 git 폴더까지 같이 복사되면 변경 이력을 담은 저장소도 복사됩니다. 폴더마다 저장소가 따로 생기니까 이후 작업 기록도 따로 관리해야 하죠. 나중에 합치려고 하면 그때부터 일이 커집니다.

그래서 Git에는 워크트리라는 게 있습니다. 같은 저장소는 그대로 두고 작업 폴더만 나누는 방식이에요. 이 구조를 이해하려면 브랜치를 먼저 알아야 합니다.

## 슬라이드 3/8 — 따로 이어가는 작업 이력

브랜치는 작업을 나눠서 이어가는 이력의 줄기입니다. 점 하나하나가 앞에서 배운 커밋이고, 선은 그 기록이 이어진 순서예요.

기준이 되는 줄기가 하나 있고, 어느 커밋에서든 거기서 갈라져 나올 수 있습니다. 처음엔 같은 기록에서 출발하지만 새 줄기에서 작업하고 커밋하면 거기서부터 별도의 이력이 이어집니다.

이게 왜 필요하냐면, 기존 걸 그대로 두고 다른 방향을 시험해보고 싶을 때가 있거든요. 문서 구성을 통째로 바꿔보고 싶은데 지금 것도 살려두고 싶은 거죠. 파일을 복사해서 이름 붙이는 대신 줄기를 갈라놓는 겁니다.

시험한 게 괜찮으면 기준 줄기에 합칠 수 있습니다. 이걸 병합이라고 해요. 작업이 끝나는 순간 자동으로 합쳐지는 게 아니라, 결과를 확인하고 나서 사람이 합치는 겁니다.

## 슬라이드 4/8 — 한 번에 한 시점만

브랜치를 삶의 시간선에 비유해보겠습니다. 열 살, 스무 살, 서른 살의 나를 커밋처럼 찍어놓은 거예요.

지금 서른 살인 내가 타임머신을 타고 열 살로 돌아간다고 해보세요. 그때 다른 선택을 해서 새로운 삶을 시작하는 겁니다. 열 살이라는 같은 출발점에서 시간선이 갈라지고, 그쪽의 스무 살은 원래 삶의 스무 살과 달라지겠죠. 브랜치가 딱 이렇게 동작합니다.

그런데 여기서 문제가 하나 나와요. 타임머신은 한 대입니다. 열 살로 돌아가면 열 살에 있는 거고, 새 삶의 스무 살로 가면 거기 있는 겁니다. 시간선이 몇 개가 남아 있어도 내가 동시에 여러 시점에 있을 수는 없어요.

작업 폴더도 똑같습니다. 브랜치를 열 개 만들어놔도 폴더 하나에서는 한 번에 하나만 열립니다. 다른 브랜치로 옮기면 그 폴더 안 파일 내용이 통째로 바뀌어요.

그러니까 브랜치를 나누는 것만으로는 에이전트 둘이 동시에 일하지 못합니다. 이력은 갈렸는데 펼쳐놓을 자리가 하나뿐인 거죠.

## 슬라이드 5/8 — 워크트리란

그 자리를 늘리는 게 워크트리입니다. 같은 Git 저장소에 연결된 실제 작업 폴더예요.

원본이 v1 시점에 있다고 해볼게요. A와 B가 따로 일할 수 있게 폴더를 두 개 더 마련합니다. 둘 다 v1에서 출발하고, A 폴더에서는 작업 A 브랜치를, B 폴더에서는 작업 B 브랜치를 엽니다. 처음엔 세 폴더의 파일 내용이 똑같습니다.

그다음 각자 자기 폴더에서 고칩니다. 폴더를 만드는 순간 달라지는 게 아니라, 각자 작업하면서 내용이 갈리는 거예요.

핵심은 이겁니다. 워크트리는 물리적으로 분리된 폴더라서 A에서 파일을 고쳐도 B 폴더의 파일은 건드려지지 않습니다. 원본 폴더도 그대로고요. 아까 복사해서 쓰던 것과 다른 점은, 저장소는 여전히 하나라는 거예요. 이력은 한곳에 모이고 작업할 자리만 늘어나는 겁니다.

## 슬라이드 6/8 — 브랜치와 워크트리의 관계

그럼 브랜치 줄기에 작업 폴더를 붙여보겠습니다.

곧게 이어지는 줄기가 기준 브랜치고, 중간에서 갈라진 게 작업 B 브랜치입니다. 여기까지가 이력 얘기고요. 여기에 실제 파일이 들어 있는 워크트리를 하나씩 연결합니다. A 폴더는 기준 브랜치를, B 폴더는 작업 B 브랜치를 열어두는 거죠.

이러면 브랜치를 바꿔 가며 한 폴더를 돌려쓸 필요가 없어집니다. 두 작업을 동시에 펼쳐놓은 상태가 되는 거예요.

그리고 여기다 에이전트를 하나씩 붙입니다. 에이전트 A는 A 폴더에서, B는 B 폴더에서 일합니다. 아까 같은 책상을 둘이 쓰던 문제가 여기서 풀리는 겁니다. 책상을 하나 더 놓은 거죠.

작업 B에서 한 건 커밋하고 검토한 다음 기준 브랜치에 병합합니다. 공간은 나눠 쓰고 결과는 확인하고 합치는 구조예요.

## 슬라이드 7/8 — Orca의 작업 단위

이제 Orca의 기본 작업 단위가 워크트리라는 말이 무슨 뜻인지 연결이 될 겁니다.

워크트리는 에이전트가 실제로 일하는 폴더입니다. 에이전트는 그 안의 자료를 읽고, 거기서 작업하고, 결과도 그 안에 남깁니다. 그러니까 워크트리 하나가 곧 에이전트 하나의 작업 단위가 되는 거예요.

Orca 안에 워크트리 A와 B가 있으면, A에서 하는 작업과 결과는 A를 기준으로 보고 B는 B를 기준으로 봅니다. 터미널 여러 개를 한곳에 모아둔 것과 다른 게 이 지점이에요. 창이 여러 개인 게 아니라 공간이 여러 개인 겁니다.

여러 에이전트한테 일을 맡기려면 각자 일할 자리가 필요하다고 했잖아요. Orca는 그 자리를 워크트리로 잡고, 그 안의 에이전트랑 작업 파일을 묶어서 다루는 겁니다.

## 슬라이드 8/8 — 한 창에서 작업 전환

그럼 공간을 나눴으니 끝이냐. 하나가 더 남았습니다.

워크트리마다 에디터 창을 따로 열어서 쓴다고 해볼게요. A 창에서 에이전트한테 일을 시켜놓고 B 결과를 보려면 B 창을 찾아가야 합니다. 다시 A가 어디까지 갔나 보려면 또 창을 바꿔야 하고요. 공간은 나뉘었는데 확인하러 창을 오가는 일이 그대로 남는 겁니다. 앞에서 봤던 터미널 여러 개 문제가 폴더 단위로 옮겨온 것뿐이에요.

Orca는 이걸 한 창 안에 넣습니다. 같은 화면에 워크트리 A와 B가 있고, A에서는 에이전트가 작업 중이고 B는 결과가 나와 있어요. B를 눌러서 결과를 보는 동안에도 A는 자기 공간에서 계속 일합니다. 작업 중이라는 표시도 그대로 남아 있고요.

그래서 한쪽에 일을 맡겨놓고 다른 쪽으로 넘어가 결과를 확인하고 수정을 요청하는 게 한 창에서 됩니다. 여러 에이전트가 여러 공간에서 일하는 상황을 창 하나로 운영하는 거죠.

이제 기본 구조는 다 봤습니다. 이어지는 실습에서 Git을 준비하고 저장소랑 작업 공간을 직접 만들어보겠습니다.
