# 브랜치와 워크트리 차이 슬라이드 대본 (7장)

덱: `artifacts/part3/outputs/ch01-03-branch-vs-worktree.html`

## 슬라이드 1/7 — 브랜치와 워크트리 차이

앞에서는 커밋으로 돌아갈 수 있는 버전을 기록하는 방법을 봤습니다. 이번에는 여러 에이전트가 같은 프로젝트에서 동시에 일하려면 무엇이 필요한지 보겠습니다.

먼저 실제로 작업하다가 생기는 문제부터 볼게요. 작업을 여러 에이전트에게 나눠 줬는데, 일하는 폴더가 하나라면 어떻게 될까요?

## 슬라이드 2/7 — 한 폴더에서 겹치는 작업

두 에이전트가 같은 프로젝트 폴더에서 일한다고 해 보겠습니다. A가 문서를 고치는 동안 B도 같은 문서를 열고 수정하면, 한쪽이 저장한 내용 위에 다른 쪽이 자기 내용을 저장할 수 있습니다. 일을 나눴어도 실제 파일을 놓는 자리는 하나인 거예요.

그림에서도 에이전트는 둘인데 같은 책상 위의 문서 한 장을 함께 건드리고 있죠. 각자의 작업 파일을 따로 두고 동시에 진행할 수 있는 공간이 필요합니다.

그럼 익숙한 방법대로 프로젝트 폴더를 통째로 복사하면 될까요?

앞에서 본 .git 폴더까지 함께 복사하면, 변경 히스토리를 담은 저장소도 복사됩니다. 폴더마다 저장소가 따로 생기니, 이후의 작업 기록도 따로 관리해야 하죠.

그래서 Git에는 워크트리라는 게 있습니다. 같은 저장소를 그대로 두고 작업 폴더만 나누는 방식입니다. 이 구조를 이해하려면 브랜치를 알아야 하는데요. 브랜치부터 보겠습니다.

## 슬라이드 3/7 — 따로 이어가는 작업 이력

각 작업의 이력을 어떻게 구분하는지 보겠습니다. 작업을 나누어 이어가는 이력의 줄기라고 보면 됩니다. 그림의 점 하나하나가 앞에서 배운 커밋이에요. 선은 그 기록이 이어진 순서를 보여줍니다.

위에는 기준이 되는 브랜치가 있습니다. 어느 커밋에서 다른 작업을 시작하고 싶다면, 그 지점에서 새로운 브랜치를 만들 수 있습니다. 처음에는 같은 기록에서 출발하지만, 새 브랜치에서 작업하고 커밋하면 별도의 이력이 이어집니다.

예를 들어 기존 문서 구성은 유지하고, 새로운 구성을 시험하고 싶을 수 있죠. 작업 브랜치에서 수정하고 기록하면 기준 브랜치의 기록을 그대로 두고 다른 방향을 시도할 수 있습니다.

작업 결과가 괜찮으면 기준 브랜치에 합칠 수 있습니다. 이것을 병합이라고 합니다. 그림의 초록 점선은 그렇게 합칠 수 있다는 뜻이에요. 작업이 끝나는 순간 자동으로 합쳐지는 것은 아니고, 결과를 확인한 뒤 병합합니다.

작업 이력은 이렇게 브랜치로 구분합니다. 이제 이 서로 다른 작업을 실제 파일로 열어두고 동시에 진행할 공간을 보겠습니다.

## 슬라이드 4/7 — 한 번에 한 시점만

앞에서 본 브랜치를 삶의 시간선에 비유해 보겠습니다. 위쪽 점은 열 살, 스무 살, 서른 살의 나입니다. 앞에서 본 커밋처럼 각 시점을 표시한 거예요.

지금 서른 살인 내가 타임머신을 타고 열 살로 돌아간다고 생각해 보세요. 그때 다른 선택을 해서 새로운 삶을 시작해 보는 겁니다. 열 살이라는 같은 출발점에서 새로운 시간선이 갈라지고, 그쪽의 스무 살은 원래 삶의 스무 살과 달라지겠죠. 브랜치도 기록해 둔 같은 시점에서 출발해 서로 다른 작업 이력을 이어갑니다.

여기서 타임머신은 한 대입니다. 열 살로 돌아가면 열 살의 시점에 있고, 새로운 삶의 스무 살로 가면 그 시점에 있습니다. 여러 시간선이 남아 있어도 내가 한꺼번에 모든 시점에 머물 수는 없죠.

작업 폴더도 같습니다. 브랜치가 여러 개 있어도 폴더 하나에서는 한 번에 하나의 시점을 열고 작업합니다. 다른 시점을 열면 그 폴더에 보이는 파일 내용이 바뀝니다.

그럼 서로 다른 작업을 동시에 펼쳐 놓으려면 어떻게 해야 할까요? 이제 실제 작업 폴더를 나누는 구조를 보겠습니다.

## 슬라이드 5/7 — 워크트리란

워크트리는 같은 Git 저장소에 연결된 실제 작업 폴더입니다. 각 폴더의 작업 파일이 서로 영향을 받지 않는 이유를 그림으로 보겠습니다. 위쪽 main 폴더는 v1 시점입니다.

A와 B가 따로 일할 수 있도록 아래에 두 작업 폴더를 마련합니다. 이 예시에서는 두 폴더가 main의 v1에서 출발하도록 하고, A 폴더에서는 작업 A 브랜치, B 폴더에서는 작업 B 브랜치를 사용합니다. 처음에는 두 폴더 모두 v1과 같은 파일 내용을 갖습니다.

그다음 각자의 폴더에서 수정합니다. A의 마지막 파일은 빨강, B의 마지막 파일은 보라로 표시했죠. 폴더를 만드는 순간 달라진 것이 아니라, 각자 작업한 뒤 서로 다른 내용이 된 모습입니다.

워크트리는 물리적으로 분리된 작업 폴더이므로, A에서 자기 파일을 고쳐도 B의 작업 파일을 건드리지 않습니다. main의 작업 파일도 그대로 유지됩니다. 같은 저장소를 사용하면서 실제 작업할 공간은 독립적으로 마련하는 것입니다.

기록해 둔 버전에서 출발해 각자의 폴더에서 작업하고, 작업 A와 B의 이력도 각자의 브랜치로 이어가는 구조입니다.

## 슬라이드 6/7 — 브랜치와 워크트리의 관계

이번에는 브랜치의 줄기에 작업 폴더를 붙여 보겠습니다. 왼쪽에서 위로 곧게 이어지는 줄기는 main이고, 중간에서 아래로 갈라진 줄기는 작업 B 브랜치입니다. 같은 기록에서 출발해 서로 다른 작업 이력을 이어가는 모습이죠.

오른쪽에는 실제 파일이 들어 있는 워크트리가 있습니다. 이 예시에서는 작업 폴더 A에서 main을, 작업 폴더 B에서 작업 B 브랜치를 열어둡니다. main과 A 폴더는 빨강, 작업 B와 B 폴더는 보라색으로 연결했습니다.

두 폴더가 함께 있으니 브랜치를 바꿔 가며 한 폴더를 사용할 필요 없이, 각각의 작업을 동시에 펼쳐 놓을 수 있습니다.

폴더 오른쪽 위에 에이전트를 하나씩 붙여 보겠습니다. 에이전트 A는 A 폴더에서, 에이전트 B는 B 폴더에서 작업합니다. 이렇게 작업 폴더를 나누면, 여러 에이전트가 각자의 폴더에서 동시에 작업할 수 있습니다.

작업 B처럼 별도 브랜치에서 진행한 작업은 결과를 커밋하고 검토한 뒤 main에 병합할 수 있습니다. 작업 공간은 나눠 쓰고, 검토한 결과를 합치는 거죠.

앞에서 Orca의 기본 작업 단위가 워크트리라고 했던 말이 이 구조와 이어집니다. 이제 Orca가 이 작업 폴더를 어떻게 마련해 주는지 보겠습니다.

## 슬라이드 7/7 — Orca의 작업 폴더

Part 2에서 보았던 Orca의 작업 공간으로 돌아오겠습니다. Orca는 이 Git 워크트리를 앱 안에서 만들고 관리할 수 있게 해 줍니다. 명령어로 하나씩 마련하던 작업 폴더를 클릭으로 만드는 거예요.

화면에 작업 칸만 늘어나는 것이 아니라, 에이전트가 실제 파일을 두고 작업할 폴더가 생깁니다. 그래서 Orca의 작업 공간을 이해하려면 어떤 이력을 이어가는지, 어느 폴더에서 일하는지를 구분하면 됩니다.

이제 기본 구조를 봤습니다. 이어지는 실습에서 Git을 준비하고, 저장소와 작업 공간을 직접 만들어 보겠습니다.
