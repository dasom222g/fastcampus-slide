## 저장소와 작업흐름 슬라이드 대본 (8장)

## 슬라이드 1/8 — 저장소와 작업흐름 (표지)

앞에서 Git이 파일의 변경 이력을 기록하고 관리하는 시스템이라고 했죠. 이번에는 Git을 쓸 때 꼭 알아야 하는 개념들을 볼 겁니다.

이제 전문 용어들이 나올 텐데 너무 어렵게 생각하지 않으셔도 돼요. 저는 남들이 어려워하는 기술을 가장 쉽게 알려드리는 사람이라고 했잖아요. 이것도 하나씩 뜯어보면 사실 별거 아닙니다.

## 슬라이드 2/8 — 저장소란

그럼 먼저 저장소부터 볼게요. 보통 Repository라고 많이 하는데, 그림으로 보면 바로 이해되실 거예요.

일반 폴더는 현재 파일만 보관하는 곳입니다. 그래서 문서든 이미지든 여기에 넣어두고 열어서 수정하죠. 버전 관리는 안 되는 상태입니다.

Git 저장소는 여기에 하나가 더 있습니다. 점 git이라는 숨김 폴더예요.

쉽게 생각하면 일반 폴더에 점 git 폴더가 하나 더 들어가 있는 게 저장소고, 이 점 git이 해당 폴더의 변경 이력을 관리해준다고 봐주시면 됩니다.

이렇게 일반 폴더에 점 git을 추가하는 걸 Git을 초기화한다고 하는데요. 이걸 해주셔야 버전 관리가 됩니다.

저는 예전에 폴더 정리한다고 이걸 지웠다가 이력을 통째로 날린 적이 있는데, 그냥 숨김 폴더가 아니니까 건드리지 마세요.

## 슬라이드 3/8 — 버전 관리를 위한 3 단계

그럼 파일을 고친 게 어떻게 하나의 버전으로 저장되는지 볼 텐데요. Git은 이 과정을 3단계로 나눴는데 각 단계마다 독립적인 영역을 사용합니다. 이 개념을 이해하는 게 Git의 핵심이에요.

첫 번째 영역은 작업 디렉토리입니다. 우리가 로컬에서 직접 파일을 확인하고 수정하는 폴더예요. 에이전트들도 여기서 작업을 하겠죠.

중요한 건, 여기서 변경이 일어났다고 해서 자동으로 버전이 저장되지는 않습니다. 글자 하나 바뀌었다고 그걸 다 새로운 버전으로 저장하면 버전이 수백 개가 쌓입니다. 그럼 정작 내가 원하는 버전을 찾기 힘들어지겠죠.

그래서 저장할 시점과 파일은 우리가 정할수 있는데

## 슬라이드 4/8 — 버전 관리를 위한 3 단계

그게 두 번째인 스테이징 영역입니다. 여긴 다음 커밋에 담을 파일을 고르는 단계인데, 로컬에만 존재하던 변경 사항을 새로운 버전으로 저장하기위한 준비를 합니다.

이게 왜 필요하냐면, 작업하다 보면 파일 여러 개를 한꺼번에 고치게 되잖아요. 근데 그게 다 하나의 버전으로 묶일 일은 아닐수 있겠죠. 예를들어, 기획서 수정 작업이랑 디자인 작업을 한번에 다 했다고 할게요. 그런데 이 둘을 같은 버전에 묶어버리면 나중에 기획서 수정한 것만 되돌리고 싶어도 그게 안 됩니다. 디자인까지 해당 시점의 코드로 돌아가거든요.

그래서 한번에 여러 작업을 했어도 task별로 나눠서 버전을 남길 수 있게 해주는 게 바로 이 스테이징 영역입니다. 작업 디렉토리에서 이 영역으로 올리는 명령어가 git add인데 우리가 직접 명령어를 칠일은 거의 않겠지만 이걸 알아야 ai에게 정확히 요청할수 있겠죠. 그래서 각 단계마다 어떤 명령어가 쓰이는지 정도는 눈에 익혀두시면 좋습니다.

이 영역은 장바구니라고 생각하시면 되는데 담았다고 산 건 아니고, 살 것만 골라놓은 상태인 거죠. 그럼 진짜 버전 저장은 언제 되느냐

## 슬라이드 5/8 — 버전 관리를 위한 3 단계

마지막 3단계입니다. git commit으로 앞에서 골라둔 것들을 하나의 버전으로 저장하는 단계예요. 이 단계를 거치면 비로소 Git 저장소에 올라가게 되는 거죠.

여기는 변경 사항이 영구적으로 기록되는 영역입니다. 각 커밋마다 고유한 이름표가 붙는데, 이 이름표를 기준으로 언제든 그 시점으로 돌아갈 수 있어요. 앞에서 특정 시점으로 되돌릴 수 있다고 했던 게 이렇게 가능해지는 겁니다.

그래서 정리하면 .. 파일 변경했으면 git add로 스테이징에 올리고,  git commit으로 레포지퇼에에 올려주셔야지 버전이 저장됩니다. 원래는 이 명령어를 직접 우리가 쳐야했는데 이젠 프롬프트 한줄이면 ai가 알아서 다 해줍니다. 

참고로 지금까지 본 세 영역은내 컴퓨터 안에서 일어나는 일입니다. 아직 인터넷에 올라간건 아니예요. 그 단계는 뒤에서 볼게요.

## 슬라이드 6/8 — 기록으로 남는 순간 - commit

그럼 커밋 하나에 뭐가 들어가는지 조금 더 볼게요.

제가 커밋을 강조하는 이유는 버전을 기록하는 기준점이기 때문이예요. 우리가 파일 수정하고 저장할땐 컨트롤 s누르잖아요. git에서 이 컨트롤 s 역할을 하는게 커밋입니다.

커밋을 안하고, ai한테 "전에 했던걸로 돌려놔" 하면 얘가 기억을 못합니다. 그래서 작업하다가 여기까지는 괜찮다 싶으면 꼭 커밋으로 저장해주셔야 돼요. 그래야 이전 버전으로  돌아갈수도 있고, 코드 비교도 되고 그렇습니다.

그럼 커밋하면 어떤게 저장되는지 보자면 첫 번째는 프로젝트 버전이에요. 그 시점에 프로젝트가 어떤 상태였는지가 통째로 담겨요. 그래서 나중에 이 커밋으로 돌아가면 그때 모습이 그대로 복원되는거죠.

그리고 작성자랑 시간인데 커밋하는 계정과  커밋 시간이 자동으로 저장되고, 사실 우리가 커밋할때 직접 넣어주는건 커밋메시지 하나입니다. 대략적으로 어떤 작업에 대한 수정사항을 써주는데 이게 필수는 아니지만 꼭 작성해주시는게 좋아요. 그래야 나중에 버전확인할때 편하겠죠.

## 슬라이드 7/8 — 내 기록과 원격 기록

근데 지금까지의 작업은 사실 내 컴퓨터 안에서 일어난 일어있습니다. 앞에서 커밋하면 git 저장소에 저장된다고 했죠. 그게 로컬 저장소를 의미하는데 이걸 인터넷에 올리려면 원격 저장소가 하나 더 붙습니다.

원격 저장소는 말그대로 인터넷에 올리는 저장소예요. 앞에서 본 GitHub가 그 공간을 제공하는 서비스고요.

그래서 commit까지만 하고 github을 보면 변경이 반영되어 있지 않습니다. git push로 원격 저장소에 업로드까지 해야 최종 반영이 되는거죠. 비유하자면 우리 블로그 올릴때 임시저장하는게 커밋 단계인거고, 최종 발행을 하는게 git pull이라고 보시면 됩니다.

사실 커밋까지만 해도 이력이 다 남는데 이런게 헷갈린다 하시면 일단 Push가 최종 단계라고 기억해주시면 되고, ai한테 요청할때도 그냥 "푸시해줘"하면 앞에있던 단계까지 얘가 다 알아서 해주고 우리 github에 올리는거 까지 해줄거예요. 이건 세팅하고 실습할때 직접 같이 해보겠습니다.

그리고 우리가 작업한걸 올렸으면 반대로 내려 받을수도 있어야겠죠. 이때는 pull이라는 명령어를 쓰는데 예를들어, 집에서 내컴퓨터로 작업하다가 회사에서도 이어서 작업을 해야한다 라고 하면 push로 원격저장소에 올리고 회사 컴퓨터로는 pull로 내려받을수 있습니다.

근데 이렇게 내려받는 방법이 두가지가 있는데, 첫번째가 방금 본  pull이고, 두번째가 클론입니다. 이게 용어때문에 어려워 보이는데 전혀 그렇지 않습니다. pull은 내가 이미 작업하던 상태에서 내려 받을때 쓰는거고, clone은 처음 해당 레포지토리를 다운받을때 사용합니다. 즉, 깃헙에 오픈소스로 공개된 스킬이나 프로그램을 다운받을때는 clone을 쓰는거고, 이미 git연결해서 쓰고 있었던 거다 하면 pull로 하는거죠.

근데 이게 헷갈리시면 지금은 넘어가셔도 됩니다. 실습하면서 제가 하는거 보시면 금방 이해 되실거예요.

## 슬라이드 8/8 — 한 번의 작업 흐름

git의 핵심은 사실 이게 다예요.

우리 컴퓨터인 작업 디렉토리에서 고치고, task별로 나눠서 스테이징 영역에 올리고, commit으로 로컬 저장소에 저장하고, git push로 원격 저장소에 올린다. 이게 git이 버전을 관리하는 흐름입니다.

그리고 커밋까지만 하면 github에선 확인이 안되고 push까지 해야 확인이 가능하다 라고 생각해주시면 되겠습니다.
