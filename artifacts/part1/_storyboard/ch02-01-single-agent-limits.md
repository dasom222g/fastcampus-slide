# Ch02-01 — 단일 에이전트의 한계

총 슬라이드: 5장 (표지 1 + 본문 4). 작업·역할·검증 분리까지 설명하고 다음 파트로 말로 연결한다.

주제: 한 에이전트로 잘 되는 일을 인정하고, 실무에서 드러나는 문제를 통해 작업·역할·검토를 나눌 이유를 이해한다.

청중: AI를 업무에 쓰려는 실무자. 개발 지식이나 고급 용어를 전제하지 않는다.

화면 흐름: 표지 → 하나로 되는 일 → 단일 에이전트의 한계 → 왜 안 되는가 → 멀티 에이전트가 필요한 이유.

편집 기준: 사용자 채팅은 설명 의도로 해석한다. 실제 화면 문구는 강의 목적에 맞게 재작성하며 자료 조사 · 스타일 · 최종 원고라는 예시는 유지한다. 예시는 설명용이며 측정된 사실이나 제품 성능 주장으로 다루지 않는다.

디자인: 기존 흰 봇과 생성 장면 유지. 문제는 orange, 해결 행은 기존 brand·purple·yellow. 목차와 수정안 표시는 제거한다.

## 슬라이드 1 / 5 — 에이전트 하나로 되는 일과 안 되는 일

타입: single-title-cover

핵심 메시지: 클립 제목과 대표 시각으로 시작한다.

근거: docs/curriculum.md Part 1 Chapter 2 Ch02-01

화면 요소:
```json
[
  "사람의 요청",
  "AI의 직접 실행",
  "결과물"
]
```

시각·등장 순서: 회색 말풍선(사람의 요청) → 흰 봇과 빨강 얼굴(AI의 직접 실행) → 초록 문서(결과물). 본문 가로폭 전체에 세 요소를 크게 정렬하고 SVG 화살표로 연결한다.

발표 노트: 표지는 클립 제목과 사람의 요청 → AI의 직접 실행 → 결과물 도식으로 구성한다. 사용자가 선택한 기존 말풍선·흰 봇·초록 문서의 시각을 복원하고 목차와 학습목표는 넣지 않는다.

## 슬라이드 2 / 5 — 하나로 되는 일

타입: hero-list

핵심 메시지: 짧고 명확한 일은 하나씩 맡기고 결과를 확인하며 완성할 수 있습니다.

근거: 원문 §1. 에이전트 하나로 되는 일

화면 요소:
```json
[
  "블로그 초안 한 편 작성",
  "대화하며 고쳐 나가는 작업",
  "짧고 명확한 작업"
]
```

시각·등장 순서: 사람이 지시하고 AI가 노트북에서 실행하는 기존 생성 이미지. 왼쪽에 블로그 초안 작성·대화하며 수정·짧고 명확한 작업을 순서대로 표시한다.

발표 노트: 실무자가 블로그 초안 한 편을 요청하는 장면으로 시작합니다. AI가 직접 파일을 작성하고, 사람이 결과를 읽고 말투나 구성을 조정해 달라고 하면 AI가 수정합니다. 한 번에 하나의 분명한 목표를 맡기고 대화하며 다듬는 일은 단일 에이전트로도 충분히 잘 됩니다. 잘 되는 것을 먼저 인정한 다음, 여러 일과 검토까지 몰아서 맡기는 상황으로 넘어갑니다.

## 슬라이드 3 / 5 — 단일 에이전트의 한계

타입: single-problem-outcomes

핵심 메시지: 여러 산출물, 긴 공정, 자기 검증을 혼자 맡겼을 때 드러나는 문제입니다.

근거: artifacts/part1/_source/ch02-01-single-agent-limits.md §2. 안 되는 일 / 사용자 최종 설명

화면 요소:
```json
[
  [
    "single-queue",
    "여러 산출물 한꺼번에",
    "블로그 · 카드뉴스 · 스레드",
    [
      "한꺼번에 맡겨도",
      "세 개가 다 끝날 때까지 기다림"
    ]
  ],
  [
    "long-chain",
    "긴 공정 한 번에",
    "자료 조사 · 스타일 · 최종 원고",
    [
      "뒤로 갈수록",
      "앞의 맥락이 흐릿해짐"
    ]
  ],
  [
    "self-loop",
    "자기 검증",
    "작성한 결과의 오류·누락 확인",
    [
      "자기가 만든 걸 검증하면",
      "대부분 “문제없다”"
    ]
  ]
]
```

시각·등장 순서: 사용자 지정 단일 에이전트 → 첫 문서 + 대기 문서 둘 도식·긴 단계·자기 검토 도식을 사용. 첫 카드에 분기 화살표를 쓰지 않는다. 각 카드 하단에 상황 한 줄 + 강조 결과 한 줄을 배치한다. 세 번째 제목은 자기 검증. 원문을 새로운 사례로 대체하지 않는다.

발표 노트: 소스의 세 현상을 그대로 유지하고 화면에서는 상황과 결과를 나누어 표시합니다. 여러 산출물을 한꺼번에 맡겨도 세 개가 다 끝날 때까지 기다려야 합니다. 첫 번째 항목은 품질이 아니라 기다림의 문제이며, 다음 장의 순차 처리와 마지막 장의 독립 작업 병렬 처리에 대응합니다. 긴 공정을 한 번에 맡기면 뒤로 갈수록 앞의 맥락이 흐릿해집니다. 자기가 만든 것을 검증시키면 대부분 문제없다고 답합니다. 소상공인·대기업이나 빠진 견적 항목 같은 별도 사례로 이 핵심을 대체하지 않습니다. 세 번째 항목 제목은 사용자가 지정한 자기 검증으로 유지합니다. 다음 장은 이 현상들이 생기는 원인을 설명합니다.

## 슬라이드 4 / 5 — 왜 안 되는가

제목 강조: 「왜」만 강조색, 「안 되는가」는 기본 흰색.

타입: single-source-causes

핵심 메시지: 단일 에이전트에게 모든 과정을 맡길 때의 한계입니다.

근거: artifacts/part1/_source/ch02-01-single-agent-limits.md §3. 왜 안 되는가

화면 요소:
```json
{
  "causes": [
    [
      "hourglass",
      "한 번에 하나만 처리한다",
      "순서대로 기다려야 하니 시간이 더 든다"
    ],
    [
      "fading-context",
      "작업이 길어지면 앞의 맥락이 흐릿해진다",
      "처음 잡은 방향이 최종 결과까지 이어지지 않는다"
    ],
    [
      "mirror",
      "만든 사람이 검사하면 문제를 놓친다",
      "자기 결과물을 후하게 평가하는 성향이 있다"
    ]
  ]
}
```

시각·등장 순서: 모래시계·흐려지는 맥락·거울 도식과 원인 세 줄을 전체 폭에 배치한다.

발표 노트: 소스 §3의 원인 세 가지를 순서대로 설명한다. 한 번에 하나만 처리하므로 기다리는 시간이 늘어난다. 작업이 길어지면 앞에서 잡은 방향과 맥락이 뒤로 밀린다. 만든 사람이 검사하면 자기 결과를 후하게 평가하는 성향으로 문제를 놓친다. 화면은 세 원인을 크게 나열하며 별도의 처리·기억·검사 분류나 추가 결론으로 재해석하지 않는다.

## 슬라이드 5 / 5 — 멀티 에이전트가 필요한 이유

타입: single-solution-cards

핵심 메시지: 작업은 동시에 진행하고, 역할별로 필요한 맥락에 집중하고, 검증은 다른 주체가 맡습니다.

근거: 원문 §4. 그래서 나눈다

화면 요소:
```json
[
  [
    "brand",
    "parallel",
    "순차 → 병렬",
    "작업을 쪼갠다",
    "서로 독립된 작업",
    "동시에 진행"
  ],
  [
    "purple",
    "role-scope",
    "긴 맥락 → 역할별 맥락",
    "역할을 나눈다",
    "담당 역할 · 필요한 맥락",
    "필요한 맥락에 집중"
  ],
  [
    "yellow",
    "separate-review",
    "자기 검증 → 별도 검증",
    "검증을 따로 둔다",
    "만드는 쪽 · 검증하는 쪽",
    "다른 주체가 확인"
  ]
]
```

시각·등장 순서: 기존 grid-3/media-card로 세 해결을 나란히 비교한다. 각 카드는 기존 방식 → 바뀌는 방식 한 줄 → 해결 제목 → 도식 → micro 설명 → 강조 효과 순서로 통일한다. 작업 카드만 동시 분기를 표시한다. 역할 카드는 한 담당자와 역할별 맥락 문서를 경계 안에 묶어 보여주며 분기 화살표가 없다. 검증 카드는 작성자 → 문서 → 별도 검토자를 실선으로 표시하고, 검토자 → 작성자의 수정 요청은 아래쪽 점선 루프로 표시한다.

발표 노트: 앞 장과 같은 순서로 원인에 대응하는 세 해결을 설명한다. 각 카드 상단에 기존 방식에서 바뀌는 방식을 짧게 표시하며 해결의 그림과 효과를 중심으로 본다. 작업 분리는 독립된 작업의 동시 진행, 역할 분리는 담당 역할에 필요한 맥락을 전달해 집중하는 것, 검증 분리는 다른 주체의 확인이다. 역할 카드에는 분기 화살표를 쓰지 않고 한 담당자와 필요한 맥락 문서를 하나의 경계로 묶는다. 역할을 나누는 핵심을 동시에 작업하는 것으로 설명하지 않는다. 검증 도식의 실선은 작성 결과를 별도 검토자에게 넘기는 흐름이며, 점선은 문제를 발견한 검토자가 작성자에게 수정을 요청하는 반환 경로다. 수정 후 같은 실선 경로로 다시 검증한다.

발표 연결: 그런데 일을 나눴다고 끝은 아닙니다. 각 에이전트의 진행을 확인하고, 결과를 다음 담당자에게 넘기는 일이 남습니다. 여러 에이전트를 실제로 쓰면 어떤 문제가 생기는지 다음 파트에서 보겠습니다.
