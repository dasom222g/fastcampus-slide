## 슬라이드 2/12 — IDE와 ADE

그럼 오르카가 뭔지를 봐야겠죠.

얘는 새로운 에이전트로 오해하기 쉬운데 아닙니다. 여러 에이전트들이 일할수 있도록 해주는 작업장에 가깝습니다. 그래서 오르카는 이 툴을 ADE라고 소개하는데요

기존에는 사람 중심의 IDE환경에서 일했다면 이제는 에이전트가 중심이 되는 환경이 필요해졌고 그걸 ADE라고 정의한겁니다.

IDE는 vscode나 인텔리제이 같은 코드 에디터를 의미하는데 여기서는 사람이 파일 열고 코드를 썼죠. 그래서 코드가 메인으로 보여지고 사람이 직접 작성하는게 큰 부분을 차지했는데

ADE는 다릅니다. 이제는 사람보다 에이전트가 파일 만들고 코드 쓰는 시간이 길어졌잖아요. 그래서 이 작업을 에이전트가 중심이 돼서 하는 개발 환경이 ADE입니다.

즉 에이전트용 vscode라고 보시면 됩니다.

그래서 Orca는 에이전트가 아니라 Codex, Claude Code 같은 에이전트들이 각자 일할 수 있게 해주는 작업 공간, 그 자체예요.

## 슬라이드 3/12 — 기존의 틀을 깬 도구

전 모든 기술의 발전은 기존 기술의 한계에서부터 시작된다고 생각하는데 orca도 마찬가지입니다.

지금까지는 기본적으로 에디터 하나에 에이전트 하나를 붙여서 썼죠. 프로젝트 하나에 에이전트 하나만 붙여서 쓰고 얘한테 일을 다 시키고 끝날때까지 기다렸다가 확인하고 다음일 시키고 하는 구조였는데 이 기본적인 전제를 깬 게 Orca 입니다.

오르카에서는 여러 에이전트를 동시에 실행시키는게 기본값 입니다. 그래서 각자의 작업 공간에서 동시에 일을 시킬수 있게 된거죠.

사실 기존 도구에서도 여러 에이전트를 못 돌렸던건 아닙니다. tmux나 혹은 vscode안에서도 터미널 창 여러개 띄워놓고 에이전트들 붙여서 쓸수도 있지만 이 관리를 전부 사람이 해줘야 했습니다. 하지만 Orca는 이런 작업들이 이미 내장되어 있어서 따로 세팅하지 않아도 편하고 안정적으로 돌릴수 있게 해주는데, 이런점 만으로도 충분히 써볼만한 가치가 있다고 생각합니다

## 슬라이드 4/12 — 용어 정리

그럼 이제 orca는 어떻게 동작하고 어떤 개념이 있는지를 봐야하는데  
그 전에 용어 정리부터 하겠습니다.

용어들을 다 외울 필요는 없지만 이게 중요한 이유는 용어가 정리되어 있어야 명확한 소통이 가능하거든요. 같은 단어는 서로에게 같은 의미로 전달해야지 오해가 없겠죠.

그래야 여러분도 개념잡을때 수월하실거고, 무엇보다 AI와 의사소통이 원활해집니다.

그래서 여기서 다룰 용어는 세가지인데

먼저 에이전트는 [역할과 목표를 받아 실제 작업을 수행하는 실행 단위]를 의미하는데 실제 일을 하는 작업자 라고 봐주시면 됩니다.

그 다음으로 하네스라는 개념은 많이 들어보셨을텐데 [에이전트를 실행하고 도구와 파일, 세션을 관리하는 환경]이라고 할수 있겠는데 에이전트가 제대로 일할수 있도록 구성해놓은 환경 이라고 보시면 됩니다. 쉽게 비유하자면 작업자의 개인 책상이라고 이해해주시면 되는데 책상에는 사람만 앉아있느게 아니라 서류나 컴퓨터가 있죠. 이런 의미의 작업 환경인데 클로드코드나 코덱스가 하네스단위 라고 봐주시면 되요. 얘네는 일하는 에이전트를 내장하고 있고, cli즉 터미널 안에서 일할수 있는 환경이 만들어져 있죠.

그리고 책상과 직원이 놓인 이 공간 전체가 Orca입니다. 여러 harness와 agent를 배치하고 작업 상태를 관리하는 환경인데요. 여러명의 하네스들 위에서 조율하고 관리할수 있는 하나의 운영 레이어라고 보시면 됩니다.

정리하면, Orca 안에 여러 개의 harness가 있고 그 각각에 agent가 한 명씩 들어가있는 구조입니다.

## 슬라이드 5/12 — Git이란

Orca를 보기 전에 git이라는 개념부터 짚고 갈게요.

왜 git을 알아야하냐면 orca의 기반이 되는게 git이거든요.

공식 발표에서도, Orca가 새로운 개념을 만든 게 아니라 이미 존재하는 Git 저장소 구조 **위에 오케스트레이션 레이어를 얹은 것**

사실 이 개념은 개발자들에겐 친숙할텐데 개발자가 아니어도 괜찮습니다.  
왜냐면 저는 남들이 어려워하는 기술을 가장 쉽게 알려드리는 사람이거든요.ㅎㅎ

git을 정의하면 [코드의 변경 이력을 기록하고 여러 사람이 함께 협업할 수 있도록 도와주는 분산 버전 관리 시스템]이라고 하는데 쉽게 말해서 우리 구글 드라이브 있죠? 이 구글 드라이브가 동작하게 하는 시스템이라고 보시면되고, 다른점이 있다면 버전 관리가 됩니다.

구글 드라이브에서 여러명의 팀이 실시간으로 파일들을 볼수 있죠. 그런데 git은 이 파일들이 변경될때 마다 그 이력들을 작성해둬서 추적이 가능해요. 여기에는 누가 몇시에 몇번째줄을 수정했고 이런것들이 작성됩니다.

git이 이런 시스템이라면 github은 클라우드 저장소 인데요. 개발자가 올려놓은 코드를 인터넷만 연결되어 있으면 누구나 볼 수 있고 확인할수 있습니다. 그래서 오픈소스로 공개됐다 하면 개발자가 깃헙에 자기 코드를 전체공개로 올려놨구나 라고 생각하시면 됩니다.

그리고 깃헙에는 리포지토리라는 개념이 있는데 이건 컴퓨터로 따지면 하나의 프로젝트 폴더라고 보면 되는데, 로컬에만 존재하는 폴더를 github에 올릴때 쓰는 단위가 리포지토리입니다. 이 안에는 여러개의 파일이나 이미지들이 있겠죠.

오늘 실습에서도 이 리포지토리를 다룰건데 폴더 하나라고 봐주시면 되요

## 슬라이드 6/12 — Orca의 작업 단위 (worktree)

그리고 orca에는 핵심 개념으로 워크트리 라는게 나오는데 이건 사실 git에 나오는 개념인데 쉽게 말해서 원본 리포지토리가 있을때 해당 그 폴더를 복제한 새로운 폴더를 의미합니다.

그리고 이 복제된 워크트리를 orca는 기본적인 작업단위로 사용합니다. 같은 폴더에서 여러명의 에이전트가 일하면 파일이 충돌나겠죠. A라는 애랑 B라는애가 같은 파일을 고치려고 하면 서로 고치려다가 충돌이 나는데 orca는 이 문제를 git 워크트리로 푼겁니다.

원본 프로젝트의 현재 버전 기준으로 폴더자체를 복제해서 물리적으로 독립된 공간을 만들어주고 그 안 에이전트를 붙여서 각자 일을 할수 있도록하는거죠. 작업이 다 완료되면 폴더 정리도 orca가 해주고.

근데 워크트리는 단순 폴더라고 하기엔 브랜치나 diff같은 여러 개념들이 붙어있는데 이건 다음 영상에서 자세하게 다룰게요. orca를 쓰는데있어 정도로만 이해하셔도 충분하고, 오늘 실습에서는 여러개의 워크트리를 띄우진 않을거거든요.

다음 영상에서는 여러개 워크트리 띄워서 병렬 에이전트 돌리는 법 다룰예정이니까 그때 좀더 자세히 보겠습니다.

## 슬라이드 7/12 — 병렬 작업 패턴

그럼 작업 구조를 볼텐데.

병렬방식 즉 동시에 여러 에이전트를 굴리는 방식은 크게 두가지 정리할수 있겠습니다.

에이전트끼리 경쟁을 시키는 패턴, 협업을 시키는 패턴.

먼저 경쟁은 동일한 작업을 여러개의 하네스에게 동시에 시키는 겁니다.  
그래서 동일 프롬프트를 코덱스, 클로드코드, 헤르메스 같은 하네스에 주고 결과물을 비교해서 제일 괜찮은 걸로 최종 반영하는 패턴인데 여기서 핵심은 서로 독립된 공간에서 작업을 하는데 있습니다.

각각 물리적으로 독립된 워크트리에서 작업을 하니까 서로 충돌없이 작업을 끝낼수 있겠죠.

반면에 협업패턴은 각각 다른 작업을 하나의 워크트리에서 시킵니다. 하나의 프로젝트에서 클로드한테는 리서치 시키고, 코덱스에게는 웹페이지 제작하라고 시키면 동시에 일하면서도 서로 다른 파일을 작업하니까 충돌없이 진행합니다.

보통 이런 구조로 병렬작업을 돌리는데 중요한건 이 설계를 어떻게 하느냐에 있습니다. 작업과 하네스를 어떻게 조합하느냐에 따라서 다양한 에이전트 아키텍처가 나오고 결과물의 퀄리티가 달라지거든요. 하나의 워크트리 안에서도 동일한 작업을 다른 하네스 들에게 시키면 경쟁을 시킬수 있겠죠.

이런식으로 조합을 다르게해서 내 작업에 최적화된 설계를 하는게 실력의 차이를 만드는 지점인것 같습니다.

## 슬라이드 8/12 — 오케스트레이션 스킬

여기서 하나 짚고 갈게요. orca 깔았다고해서 에이전트들이 저절로 협업하지 않아요.

협업을 시키는건 오케스트레이션이라는 별도 스킬이 맡습니다. 사람이 목표하나 던져주면 일을 쪼개고 결과를 취합하고 각 서브에이전트의 생명주기를 관리하는걸 이 스킬하나가 다 해주는거죠.

사실 이 작업은 orca가 아니어도 기술적으로 가능은 합니다. 근데 다른점이 사람의 개입이 없어진다는 거죠. 일 분배하고, 에이전트 간 작업이나 파일 넘겨주고.. 이런 작업이 중간중간 필요한데 이걸 사람이 아닌 이 스킬이 담당한다고 보시면 됩니다

## 슬라이드 9/12 — 오케스트레이션의 역할

이 스킬은 두가지 역할로 나뉘는데 coordinator와 worker입니다.

이 개념은 이전 영상에서 hermes로 멀티에이전트 구축할때도 다뤘는데 오케스트레이터 역할을 orca에서는 coordinator가 담당합니다. 얘의 목적은 사람이 시킨일을 하는데 있지 않습니다. 사람이 준 큰 목표를 작업 가능한 범위로 쪼개서 Task를 만들기만 하고요. 실제 작업은 worker가 담당합니다. 사람으로 치면 코디네이터가 팀장이라면 워커는 실무를 담당하는 직원이라고 할수 있겠습니다.

그래서 이 팀장이 하는일은 일을 쪼개서 워크를 띄우고 보고를 기다립니다. run create.. 이런 명령어를 쓰는데 이것들을 외울 필요는 없지만 눈에 익혀놓으면 사용하실때 “아 지금 어떤 단계구나” 하고 이해하기 편할거예요

## 슬라이드 10/12 — 실행 흐름

실행 흐름을 보면

일단 목표를 받으면 코디네이터가 run을 생성합니다. 이 run은 이번 작업의 이름표라고 orca에서 정의하는데 예를들면 하나의 전체 작업 상황표라고 보시면 됩니다. 이 안에서 코디네이터와 워커가 메시지를 주고 받아요.

그 다음 일을 쪼개서 task를 생성하는데 이 단계는 업무만 쪼개진 상태인거고 아직 담당자는 배정되지 않은 상태입니다.

그 다음 dispatch에 의해서 각 task가 워커에 배정되는데 이때 에이전트별 터미널이 자동 실행됩니다.

그다음은 대기하면서 작업 완료를 기다리고, 이 상태일때는 코디네이터와 대화가 가능해집니다. 얘는 업무 배정끝내고 기다리기만 하는 상태라 하는일이 없거든요. 그러다가 워커가 일 끝냈다고 메시지 보내면 그제서야 취합하고 모든 작업 끝냈는지 확인해서 터미널들 정리해주는거죠.

이게 그 명령어들인데 우리가 터미널에 직접 써서 실행시켜도 되지만 이 명령어 쓰고 돌리는 걸 orca가 대신해주는거라고 이해해주시면 됩니다

## 슬라이드 11/12 — Run의 메시지 종류

아까 Run에서 코디네이터와 워커가 메시지를 주고받는다고 했는데 이게 왜 그러냐면 coordinator와 worker는 아예 다른 프로세스라서 서로의 화면을 볼 수 없습니다. 그래서 Run을 통해서 일을 잘 하고 있는지 확인하는건데 여기서 주고받는 메시지 종류가 이렇게 6가지 입니다.

이중에 자주 쓰는 건 worker_done, question, reply 이 셋인데 보통 워커가 코디네이터 즉 팀장에게 대부분 보냅니다.

decision_gate만 성격이 다릅니다. 주고 받는게 아니라 스스로 특정 Task를 막아 세우고 다음 단계로 갈지 판단하는 게이트예요. 이걸 통과하면 다음 작업 에이전트에게 일을 넘겨주겠죠.

## 슬라이드 12/12 — 주식 판단 시스템 구조

그럼 오늘 만들어볼 주식 판단 시스템 구조를 먼저 보면 총 6개 층으로 구분했습니다.

1층은 근거 수집 계층인데 재무 정보와 뉴스·공시를 병렬로 나눠서 수집합니다. 수집된 데이터가 AI의 판단의 근거가 되겠죠

2층은 독립적으로 판단하는 계층입니다. Claude 팀과 Codex 팀이 각자 Bull, Bear, Risk 순으로 판단해요.

이 전략은 애널리스트들이 실제로 쓰는 논쟁 구조에서 가져왔습니다. 한쪽은 강제로 상승론을, 한쪽은 하락론을 펴게 해서 놓치는 부분 없이 논리적인 판단을 할수 있게 하는 방법입니다.

중요한 건 이 세 관점을 서로 다른 하네스로 나누지 않았다는 거예요. 클로드팀과 코덱스팀 각자 똑같은 작업을 하고 결과물을 비교하는게 목적인데

관점 차이랑 모델 차이가 섞이면 공정한 비교가 안됩니다.

3층은 교차 반박입니다. 클로드팀과 코덱스팀의 판단을 서로 검토해서 교차검증을 하는 계층입니다. 최대 3라운드까지.

4층은 기계적 검증을 담당하는데 AI는 수치계산에 약하기 때문에 Python이 코드를 기반으로 출처, 기준일, 수치를 확인하고 검증하는 층입니다.

5층은 결과들을 종합적으로 취합하고 정리하는데 새로운 판단이 들어가지는 않습니다. 판단은 오직 2,3층에서만 합니다.

6층에서는 두 팀의 판단을 비교할 수있는 대시보드를 만드는 층인데 시각적으로 보기 편하게 오픈소스 라이브러리로 만들어 볼겁니다.

6층까지 끝나면 이걸 보고 사람은 최종 의사결정을 하면 되겠죠. 이 종목을 살지 말지ㅎㅎ
