# 골든셋 — Orca 오케스트레이션 덱 (12장)

**출처:** 같은 Orca 주제를 다룬 12장짜리 덱. 이 저장소로 옮겨 오기 전 다른 프로젝트에서 확정된 기준 산출물이다.
**확정일:** 2026-08-22

> 색 이름은 이 저장소 기준으로 옮겼다 — 원본의 teal이 여기서는 **brand(`#fc1c49`)**다.

1차본에서 2차 피드백까지 거치며 **13장 → 12장**으로 정리된 덱이다. 새 강의 덱을 만들 때 이 문서의 「왜 이렇게 됐나」를 먼저 읽는다. 결과만 따라 하면 같은 지적을 다시 받는다.

## 1. 이 덱이 작동하는 이유 — 구조 분해

### 개념 사다리 — 아래에서 위로 한 칸씩

```
2  Orca = ADE          에이전트가 아니라 작업장
3  왜 나왔나            에디터 하나에 에이전트 하나라는 전제를 깼다
4  용어                 harness · agent · Orca
5  Git                  코드가 올라가 있는 원격 저장소
6  worktree             그 프로젝트를 복제한 폴더 = Orca의 작업 단위
7  병렬 패턴            그 폴더들을 어떻게 굴리는가
8  오케스트레이션 스킬   그 굴림을 대신 관리하는 별도 스킬
9  역할                 그 스킬 안의 coordinator · worker
10 실행 흐름            그 역할들이 만드는 객체
11 Run 우편함           그 객체들이 주고받는 메시지
12 오늘 만들 것          전부가 쓰이는 실제 구조
```

**한 칸도 건너뛰지 않는다.** 각 장은 바로 앞 장의 개념만 전제한다. 4번(용어)이 3번 뒤에 온 이유도 이것 — 5번부터 harness·agent가 쏟아지기 때문이다.

### 층위를 뭉개지 않는다 — 이 덱에서 가장 많이 틀린 지점

| 층 | 무엇 | 어디서 |
|---|---|---|
| 작업 환경 | Orca (ADE) | 2 · 4 · 6 |
| 그 위의 기능 | 오케스트레이션 **스킬** | 8 |
| 저장 | Git 저장소 (원본) | 5 |
| 작업 | worktree (복제본) | 6 |

1차본은 "Orca가 분배·취합·관리를 해준다"라고 써서 **환경과 스킬을 한 덩어리로 뭉갰다.** 공식 문서는 오케스트레이션을 별도 스킬로 규정하고, 소스도 "설치만으로 자동 협업하지 않으며 별도의 orchestration 기능을 사용한다"라고 쓴다. 저장소와 worktree도 마찬가지로 다른 층이다.

### 색·아이콘 연속성

| 대상 | 색 | 아이콘 |
|---|---|---|
| Claude Code · 실행하는 쪽 | brand | 🟢 |
| Codex · 두 번째 주체 | purple | 🟣 |
| coordinator · 조율 | yellow | 🧭 |
| 인프라 · harness · 터미널 | gray | 🪑 |
| 저장소 | gray | ☁️ |
| worktree | brand/purple/gray | 📁 |
| 한계 · 기존 방식 | orange | ⏳ |
| 완료 · 결과물 | green | — |

**아이콘도 색과 같은 규칙을 따른다.** 같은 대상은 덱 전체에서 같은 아이콘을 쓴다. 5번의 ☁️(저장소)가 6번 트리의 뿌리에서 그대로 나오고, 거기서 📁(worktree)가 갈라져 7번 협업의 뿌리로 이어진다. 이 연결이 있어야 "저장소에서 워크트리가 나온다"가 말 없이 읽힌다.

### 비유의 층위를 맞춘다

```
사무실 (Orca) > 책상 (harness) > 직원 (agent)
                                   ├ 팀장 (coordinator)
                                   └ 담당 직원 (worker)
```

소스는 Orca를 "운영실"이라 부르지만 **책상과 직원이 있는 공간을 운영실이라 하면 층위가 어긋난다.** 사무실로 옮겼다. 팀장과 담당 직원은 다른 종족이 아니라 같은 사무실의 직원이며, 어느 터미널에서 어떤 명령을 받았느냐로 갈린다.

### 정의가 먼저, 비유는 보조

4번 용어 슬라이드의 위계가 기준이다.

```
harness                                      ← 원문 용어
에이전트를 실행하고 도구와 파일과 세션을 관리하는 환경   ← 정의 (본문 크기)
🪑 개인 책상                                  ← 비유 (작게, 흐리게)
```

비유만 넣으면 "그래서 실제로 뭔데"가 남는다. 정의만 넣으면 안 붙는다. **둘 다 넣되 크기로 위계를 준다.**

| 7 | 오케스트레이션 — timeline 3단계 | **오케스트레이션 스킬** — TEXT 선언형 | 개념 정의를 순서(workflow)로 그리면 안 된다. 그리고 Orca와 스킬은 **다른 층**이다 |
| 8 | 용어부터 맞추기 — 좌우 반반 | **용어 정리** — 7:3, 정의 + 비유 | 도식이 주인공이면 비율로 말해야 한다. 비유만으로는 정의가 안 선다 |
| 9 | 두 역할 — `COORDINATOR` 딱지 + `팀장` 타이틀 | **팀장** 딱지 + `coordinator` 타이틀 | 외워야 할 원문이 타이틀에 와야 한다. **클래스·색·위치는 그대로 두고 텍스트만 스왑** |
| 10 | 실행 흐름 — 카드에 상태 전이·기술 설명 | 한 줄 정의로 축약 | 슬라이드는 레퍼런스가 아니다 |
| 11 | 메시지 여섯 종 | **Run의 메시지 종류** | 개수는 정보가 아니다. 앞 장에서 만든 Run과 묶어야 두 장이 한 덩어리가 된다 |
| 12 | 다섯 성질 (LIST 5개) | **삭제** | 실습에서 명령을 치며 자연스레 나오는 함정 목록이라 이론에서 외우게 할 내용이 아니다 |
| 13 | 6층 카드 → 세로 구조도 → 6층 카드 | **6층 카드** | 구조도로 바꿨다가 원복. 카드 6장이 정보 밀도와 가독의 균형점이었다 |

### 사실 정정 — 공식 문서로 확인한 것

1차본은 소스 노트만 보고 만들어 다음이 틀렸거나 근거가 없었다. `orca skills get orchestration`(v1.4.182)과 git 공식 문서로 확인해 고쳤다.

| 항목 | 1차본 | 확인 결과 |
|---|---|---|
| Run | "메시지와 Task 상태가 분류되는 이름공간" (모호) | `A Run is only a durable namespace and coordinator inbox; it never schedules or places workers` — **칸반 보드가 아니다.** Orca의 칸반 보드는 워크트리 보드로 다른 레이어 |
| `check --wait` | 워커 상태를 관찰 | **메시지 타입**을 기다린다. 대기/작업중/완료 같은 상태 enum은 오케스트레이션 쪽에 없다 |
| gate | "Task DAG 진행 여부" | 공식 명칭 **decision gate**, 특정 Task 하나를 막고, resolve 주체는 문서상 coordinator |
| 경쟁 실행 영문 | "competitive execution" | **출처 없는 조어.** Orca는 `race`라 부른다 |
| 생명주기 권한 | Dispatch에 있음 | 맞음. 완료 확정은 worker, 세션 정리는 coordinator |
| git worktree | — | `Manage multiple working trees attached to the same repository`, Git 2.5(2015). Orca는 실제 `git worktree add`를 호출한다 |

## 4. 이 산출물에만 맞았던 것 — 규칙화 금지

- **12장이라는 분량** — 소스 섹션 수와 실습 구조도가 겹쳐 나온 결과다. 다음 덱의 기준이 아니다
- **사무실 비유(사무실·책상·직원·팀장)** — Orca의 계층이 마침 조직과 대응해서 통했다. 다른 주제에 억지로 옮기지 않는다
- **`race` vs 업계 용어의 긴장을 tip으로 설명한 것** — 이 도구가 자기 이름을 특이하게 붙였기 때문이다
- **Claude Code 로고 PNG 사용** — 그 프로젝트에 파일이 이미 있었을 뿐이다. 이 저장소에는 `/assets/`에 Claude Code · Codex 로고가 모두 있으니 그대로 쓴다
- **세 번째 하네스가 등장한 것** — 그 프로젝트의 맥락이다. 이 강의는 Claude Code와 Codex 둘이 기본이다
