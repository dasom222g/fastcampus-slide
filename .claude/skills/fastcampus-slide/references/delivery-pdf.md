# 촬영 후 납품용 PDF

**이 문서는 촬영이 끝난 클립의 PDF 생성·수정을 사용자가 별도로 요청했을 때만 읽는다.** HTML 제작·수정, 촬영 준비, 촬영 완료 보고만으로 실행하지 않는다. 촬영 전에 PDF 존재나 변환 준비 상태를 미리 확인할 필요도 없다.

## 범위와 산출물

- 촬영 완료 여부는 사용자의 현재·이전 확인을 우선한다. 불명확할 때만 요청된 클립의 `dashboard/clips.json` 촬영 기록을 확인하고, 그래도 모르면 그때 확인한다. 이미 받은 완료 확인을 다시 요구하지 않는다. 편집 완료까지 기다리는 조건은 아니다.
- 요청한 파트·클립·페이지만 처리한다. 옆 파트에 HTML이 있어도 범위에 추가하지 않는다. Google Slides 등 외부 덱이나 제외 지정 클립을 임의로 재현하지 않는다.
- **현재 HTML이 화면의 기준**, `docs/curriculum.md`가 클립 번호·파일명의 기준이다. 실제 `<article class="slide">` 개수와 순서를 사용한다. 예전 확정 목록의 장수가 다르면 현재 HTML을 우선한다.
- 기본 저장 위치: `output/pdf/Part NN/ChNN-NN. 현재 커리큘럼 클립명.pdf`. 기존 PDF 수정은 같은 파일에 반영한다. 클립별 개별 PDF를 제공한다.
- **ZIP·통합 PDF·추가 복사본은 요청받았을 때만 만든다.** 납품 파일을 슬라이드 인덱스나 제작 완료 게이트에 자동 추가하지 않는다.
- 사용 가능한 PDF 스킬과 브라우저 도구의 사용 지침을 함께 따른다. 이 절차에서 원본 HTML·CSS·대본을 수정하지 않는다. 출력용 스타일은 브라우저 세션에만 주입한다.

## 화면을 그대로 보존하는 변환

1. 원본 HTML을 Chromium에서 **2133×1200 CSS px, 브라우저 배율 100%, deviceScaleFactor 1**로 연다. `file://`의 링크·이미지 경로 보정이 동작하면 서버 없이 열 수 있다. 아니면 저장소의 미리보기 서버를 사용한다. 폰트가 CDN에 있으면 파일로 열어도 네트워크가 필요하다.
2. 화면용 CSS를 그대로 사용한다. A4·일반 인쇄 레이아웃·자동 맞춤·폰트 대체·글자 축소를 적용하지 않는다. HTML을 이미지 한 장으로 만들어 PDF에 붙이기보다 Chromium의 `Page.printToPDF`로 텍스트와 SVG를 보존한다.
3. `document.fonts.ready`와 이미지 디코딩을 기다린다. 각 이미지의 `complete`와 `naturalWidth`, 실제 사용한 폰트의 로딩 상태를 확인한다. 대체 폰트나 깨진 이미지 상태를 납품하지 않는다.
4. `?slide=N` 또는 원래 내비게이션으로 한 장씩 연다. 실제 활성 장이 원하는 페이지인지 확인한다. 원본이 절대 위치·불투명도로 장을 겹쳐 놓으므로 모든 장을 한꺼번에 인쇄하지 않는다.
5. 아래의 **클릭 후 최종 상태**를 확인한 다음 장별 PDF를 만든다. 슬라이드 이동 버튼·점·진행 막대·카운터만 출력에서 숨긴다. 패스트캠퍼스 로고 등 슬라이드 내부 요소는 보존한다.
6. 장별 PDF를 원래 순서대로 결합한다. 한 슬라이드가 한 페이지인지 확인한다. 빈 페이지를 끼워 넣거나 각 장을 다른 크기로 축소하지 않는다.

검증된 출력용 설정 예시:

```css
@page { size: 2133px 1200px; margin: 0; }
html, body {
  -webkit-print-color-adjust: exact !important;
  print-color-adjust: exact !important;
}
.nav-btn, .dot-nav, .slide-counter, .progress-bar,
.seminar-arrow, .seminar-dots, .seminar-counter, .seminar-progress {
  display: none !important;
}
```

```js
// 연결된 Chromium CDP 세션에서 호출하는 설정. 클라이언트에 맞춰 적용한다.
await send('Emulation.setEmulatedMedia', { media: 'screen' });
await send('Page.printToPDF', {
  displayHeaderFooter: false,
  printBackground: true,
  preferCSSPageSize: true,
  paperWidth: 2133 / 96,
  paperHeight: 1200 / 96,
  marginTop: 0, marginBottom: 0, marginLeft: 0, marginRight: 0,
  scale: 1,
});
```

`@page`와 브라우저 뷰포트는 같은 크기여야 `vw`·`vh`·`clamp()`에 따른 글자 크기와 줄바꿈이 유지된다. PDF의 pt 단위는 CSS px와 다르므로 숫자만 비교해 글자 크기를 다시 맞추지 않는다. `agent-browser`를 쓰면 해당 세션의 `get cdp-url`로 연결 정보를 얻을 수 있다. 이전 작업의 포트·세션 URL을 재사용하지 않는다.

## 자동 등장과 클릭 후 최종 상태는 다르다

**진입 애니메이션이 끝났다고 클릭 동작까지 완료된 것은 아니다.** PDF에는 설명이 완성된 최종 상태를 담되, 사용자 지정 상태가 있으면 그것을 따른다.

- 자동 등장 요소는 끝까지 표시되게 기다린다. SVG 연결선처럼 JS가 크기를 재계산하는 요소도 폰트 로딩·화면 전환 이후 안정된 것을 확인한다.
- 클릭으로 분기·이동·내용 전개가 시작되는 장은 실제 클릭 핸들러를 실행한 뒤 완료 상태를 확인한다. `.active`만 붙이거나 `opacity: 1`을 일괄 적용하는 것으로 대신하지 않는다. 모든 `transform`을 지우면 원래 배치와 의미가 깨진다.
- 클릭 도구가 성공을 반환해도 원하는 상태인지 확인한다. SVG 버튼의 넓은 경계 상자는 실제 클릭 대상과 다를 수 있다. 필요하면 정확한 대상에 `MouseEvent('click', {bubbles:true, cancelable:true})`를 전달해 기존 핸들러를 실행한다.
- Web Animations의 `finish()`는 **이미 시작된 유한 애니메이션**을 끝내는 보조 수단이다. 클릭 전에 사용해도 아직 시작되지 않은 동작은 실행되지 않는다. 타이머·무한 애니메이션을 무조건 가속하거나 종료하지 않는다.

실제 실패와 정답: Part 3 `Ch01-03. 브랜치와 워크트리`의 4페이지는 처음에 자동차가 원래 삶의 30살에 멈춰 있다. `.tm-traveler`를 클릭하면 10살로 돌아간 뒤 보라색 새 경로의 20살에 도착한다. **보라색 분기선, 아래쪽 20살, 새로운 삶 라벨, 그 위 자동차**가 모두 보이는 상태가 납품 기준이다. 현재 구현에서는 `.tm-running`, 자동차의 `translate(480px, 320px)`, 새 라벨의 opacity 1로도 확인할 수 있다. 이동에 약 6.56초가 걸리지만, 이후 구현이 바뀌면 현재 동작과 화면을 기준으로 판단한다.

## 특정 페이지만 수정할 때

- 기존 PDF를 임시 위치에 보존하고 대상 HTML 장의 원하는 상태만 다시 출력한다. **덱 전체를 다시 변환하지 않는다.** 다른 페이지와 다른 클립 PDF를 수정하지 않는다.
- `pypdf` 등으로 원래 순서의 대상 페이지만 새 페이지로 교체한다. 페이지 수·용지 크기·문서 메타데이터를 유지한다. 원본 HTML의 동작을 PDF 편의를 위해 바꾸지 않는다.
- 교체하지 않은 페이지의 콘텐츠 스트림과 추출 텍스트를 이전 PDF와 대조한다. 이전·수정본을 같은 크기로 렌더해 해당 페이지만 달라졌고 나머지 페이지는 픽셀 단위로 동일한지 확인한다.
- 다른 PDF의 보존 여부를 확인하려면 **작업 시작 전에** 해시를 기록해 전후 비교한다. 파일 수정 시각의 상대적 순서로 판정하지 않는다. macOS 한글 경로는 Unicode 정규화가 달라질 수 있으므로 대상 제외에는 문자열 비교 대신 `Path.samefile()`을 사용한다.
- 검수가 통과한 뒤 기존 납품 파일에 반영하고 임시 백업·장별 PDF·캡처는 정리한다. 별도의 새 납품 버전이나 ZIP을 만들지 않는다.

## 납품 전 확인과 보고

- PDF 페이지 수가 대상 HTML 장수와 같고, 순서·페이지 크기가 일관적인지 확인한다.
- `pdffonts` 등으로 사용 글꼴이 포함되어 있는지 확인한다. 텍스트 추출 가능 여부도 확인하되, 이것만으로 배치를 검증했다고 하지 않는다.
- `pdftoppm` 등으로 전체 페이지를 이미지화해 원본 화면과 비교한다. 제목·본문 크기, 줄바꿈, 색·배경, 그림·로고, 연결선, 최종 클릭 상태와 잘림을 확인한다. 일부 장 수정이면 교체 장을 시각 검수하고 다른 장의 동일성을 확인한다.
- HTML은 반응형이고 PDF는 고정 화면이다. **2133×1200에서 비교한 결과**라고 설명한다. 서로 다른 창 크기나 렌더러까지 픽셀 단위로 완전히 같다고 단정하지 않는다.
- 보고는 대상 범위·개수와 저장 위치 중심으로 짧게 한다. 특정 페이지 수정이면 변경한 페이지와 나머지 페이지 보존 여부만 전달한다. 요청 없이 압축하거나 추가 산출물을 만들지 않는다.
