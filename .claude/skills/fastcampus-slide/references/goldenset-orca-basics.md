## 언제 적용하는가

비개발자에게 도구의 정체·실행 주체·작업 단위를 처음 소개하거나, 포함 관계·용어 정의·분배와 취합을 시각화할 때 읽는다. **현재 클립이 답해야 할 질문을 먼저 정하고, 그 질문에 필요한 구조만 보여주는 판단**이 핵심이다.

Part 2의 이 클립은 Orca 기본 소개다. Git과 워크트리 원리는 Part 3, 오케스트레이션 구조·설정은 Part 4에 있다. 뒤 파트의 상세 설명을 이곳으로 당겨오지 않는다. 반대로 “뒤에서 배운다”는 이유로 작업 단위와 협업 가능성까지 빼지 않는다.

이 골든셋이 다른 클립의 내용·장수·레이아웃을 일괄 강제하지는 않는다. 최신 사용자 지정이 우선이다. 골든셋 등록 과정에서 승인 HTML과 베이스 템플릿을 수정하지 않았다.

## 3. 시각 표현에서 배울 것

### 의미가 있는 경계와 선

- **2장의 외곽선 하나**는 공동 작업 공간의 범위다. 내부 A/B에 별도 카드나 색 배경을 다시 씌우지 않는다.
- 2장의 회색 분기선은 포함·연결 관계다. 작업 순서를 뜻하는 화살표로 바꾸지 않는다.
- 5장의 선은 실제 분배·취합의 방향이다. 에이전트별 색은 해당 경로와 이어진다.
- 5장의 세 에이전트는 협업 흐름의 예시다. 이를 특정 병렬 패턴의 전체 정의나 모든 작업의 동시 실행 보장으로 확대하지 않는다.
- 조율자의 왕복 보고 구조가 잘못된 개념인 것은 아니다. **이 입문 장의 질문에는 지나치게 상세해서 제외한 것**이다.

### 장면·정의·대비의 크기

1장 사무실은 좌측에서 본문 높이를 충분히 쓰고, 우측에는 큰 선언과 작은 비유가 있다. 로봇을 단순히 나란히 놓는 것에서 끝나지 않고 책상·장비·공용 보드·벽으로 환경을 보여준다. 4장은 폴더 도식을 크게 두어 실제 작업 공간이라는 정의를 바로 읽게 한다.

| 현재 승인 구현 | 너비·크기 근거 | 적용 범위 |
|---|---|---|
| `.orca-office-scene` | `min(100%,94rem)`, 열 `1.1fr 1fr`, 간격 `clamp(2.5rem,4vw,4rem)`, 그림은 본문 높이와 `contain` | 이미지가 왼쪽인 이 표지의 승인 변형 |
| `.orca-agent-workspace` | `min(100%,72rem)`, 바깥 패딩 `1.5rem 2rem`, 내부 두 열 | 공간 경계와 열린 하위 항목 |
| `.worktree-folder-scene` | `min(100%,86rem)`, 열 `1.1fr 1fr`, 도식 높이 `clamp(17rem,36vh,27rem)` | 큰 대상 하나 + 용어 정의 |
| `.orchestration-flow` | `min(100%,86rem)`, 목표·분배선·에이전트·취합선·결과의 다섯 열 | 읽는 순서가 있는 분배·취합 |

수치는 정답을 검증하는 근거이며 모든 장면의 새 전역 기본값이 아니다. 템플릿 1번을 지정받았다면 그 패턴을 따르고, 이 표지처럼 별도 승인본을 지정받았다면 해당 실물을 따른다. 템플릿 규칙을 베꼈다는 이유만으로 그림이 충분히 크다고 판정하지 않는다.

3장의 IDE/ADE 풀네임·중심 주체·그림·하단 순서는 유지한다. 이 승인된 좌우 비교의 카드까지 “카드 금지”로 제거하지 않는다.

## 4. 내용과 대본의 경계

- 4장 화면에는 워크트리의 실체와 역할. Git이 선택한 버전의 파일을 준비한다는 배경은 대본에 짧게 있고 원리는 Part 3으로 넘긴다.
- 5장 화면에는 분배·취합 기능. 조율 담당자와 스킬 설정은 Part 4에 둔다. 설치만으로 모든 협업이 자동 연결된다는 뜻으로 바꾸지 않는다.
- 화면에서 설명을 덜어냈다고 대본에서 전부 빼거나, 대본에 있다는 이유로 화면에 전부 넣지 않는다. 최종 5장과 대본 번호·그림을 가리키는 설명은 일치해야 한다.
