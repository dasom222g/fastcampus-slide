## 1. 핵심 메시지를 잡는 방법

### 먼저 수강생이 구분해야 할 것을 한 문장으로 쓴다

“워크트리를 설명한다”는 주제다. “에이전트의 작업 파일을 분리하려고 별도 작업 폴더를 쓴다”가 이 장의 주장이다. 주제를 적은 뒤 바로 아이콘 세 개를 배치하면 중요한 관계가 사라진다.

스토리보드에는 짧게 다음 세 가지를 남긴다.

1. **수강생의 질문** — 이 장이 없으면 무엇을 오해하는가?
2. **한 문장 답** — 주체·동작·대상이 무엇인가?
3. **그림으로 증명할 관계** — 같은 것/다른 것, 포함/분리, 순서/의존, 배정/보고 중 무엇인가?

예를 들어 “여러 에이전트의 상태 확인”의 핵심은 완료·작업 중·승인 대기라는 범례가 아니다. **한 창에서 여러 상태를 함께 본다**는 효용이다. 그래서 세 상태를 하나의 창 안에 넣는다. 반대로 “여러 에이전트의 동시 실행이 기본값”을 보여줄 때 개별 폴더를 그리면 공간 분리를 필수 조건으로 오해한다. 같은 창에서 대상 수와 실행 방식을 바꾸는 비교가 맞다.

### 관계가 결정되면 구조를 고른다

| 전달할 관계 | 읽혀야 할 그림 | 승인 사례 |
|---|---|---|
| 기본 방식이 바뀜 | 같은 외형 안에서 수·흐름만 달라짐 | Orca 소개 3장 |
| 같은 범위에 속함 | 실제 범위를 뜻하는 경계 하나, 그 안의 모든 구성원 | Run 정의 / 같은 작업 공간 |
| 순서를 따라 진행 | 같은 크기의 단계, 연결된 화살표, 서로 다른 단계색 | 저장소 흐름 8장 |
| 앞 결과가 필요함 | 앞 작업에서 뒤 작업으로 가는 선과 시작 조건 | Task 의존 관계 |
| 같은 기준에서 분리 | 작은 출발점 위, 큰 독립 공간 둘 아래 | 워크트리 정의 |
| 논리와 실체가 대응 | 줄기 A→공간 A, 줄기 B→공간 B의 이름·색 매핑 | 브랜치와 워크트리 관계 |
| 주체 사이 소통 | 주체는 양옆 중앙, 메시지는 이름·설명·방향이 같은 행 | 메시지 종류 |
| 누구에게 말하는가 | 사람→조율자, 조율자→여러 실행자라는 층 | 목표는 오케스트레이터에게 |

**아이콘은 명사, 선은 관계, 경계는 범위, 색은 같은 대상을 추적하는 장치다.** 네 요소 중 하나를 바꾸면 의미가 달라졌는지 다시 확인한다.

## 2. 강의의 연결과 인과를 확인하는 방법

### 문제 → 원인 → 대응은 같은 축이어야 한다

실패 사례: “셋 다 어정쩡하게 나온다”(품질) → “순서대로 기다리니 시간이 든다”(대기) → “병렬 처리”(대기 해소).

승인된 수정: “세 개가 다 끝날 때까지 기다림” → 순차 처리의 대기 → 독립 작업의 병렬 처리. 이미 맞는 원인·대응을 보존하고 어긋난 문제 문구만 고쳤다. 번호와 주제어가 같다는 이유로 인과관계가 맞다고 판정하지 않는다.

두 번째 축도 “조건을 잃음”이라는 좁은 해석이 아니라 **작업이 길수록 앞의 맥락이 흐릿해짐**이다. 뒤의 역할 분담도 필요한 맥락을 맡은 역할에 집중시키는 대응으로 이어진다. 사용자 설명의 이유를 먼저 읽고 표면 단어만 바꾸지 않는다.

### 용어를 먼저 정의하되 전체 흐름은 뒤로 숨기지 않는다

승인 순서: **목표와 완료 기준 → Run과 Task의 정의 → Coordinator가 관리하는 전체 실행 흐름 → 의존·배정·조율·판단 상세**.

- 미정의 Run/Task를 흐름에서 갑자기 꺼내지 않는다.
- 이해하기 쉽게 한다고 실제 용어를 없애지 않는다. 용어 + 짧은 뜻을 함께 쓴다.
- 전체 흐름을 맨 마지막에만 두어 상세 장들이 무엇의 일부인지 모르게 하지 않는다.
- 예고 장은 예고만 한다. 뒤 클립의 상세 설명·실습 화면을 선점하지 않는다.
- 실제 사용 화면은 시연이 필요한 경우에만 쓴다. 승인 없이 현재 개발 세션의 작업 캡처를 강의 예시로 넣지 않는다.

## 3. 실패 → 승인 수정 → 재사용 판단

| 실제 실패 | 승인된 수정 | 다른 주제에서도 확인할 기준 |
|---|---|---|
| 표지에 목차를 넣거나 간결하게 하다 제목·부제를 삭제 | 클립명과 같은 제목, 부제, 핵심 장면 | 표지는 클립 정체를 보여준다. 목차 금지와 제목 삭제를 혼동하지 않는다. |
| 같은 템플릿인데 1·2·3장의 본문 크기가 다름 | 역할별 공통 토큰과 같은 강조 규격 | h1/본문/캡션은 역할별로 다르되, 같은 역할은 규격이 같다. |
| 박스가 싫다는 피드백을 모든 경계 금지로 해석 | 통합 화면·작업 공간·Run의 범위는 경계 복원 | 장식인가, 실제 포함 관계인가를 판단한다. |
| 같은 공간의 워커만 폴더에 넣고 코디네이터는 밖에 둠 | 같은 공간 안에 세 주체 전부 배치한 B안 채택 | 경계 안팎이 의도와 다른 공간 차이를 만들지 않는가? |
| 폴더가 가로로 늘어진 배너가 됨 | 최대 너비와 내부 간격을 줄이고 높이 확보 | 글자·아이콘을 줄이기 전에 컨테이너 비율을 조정한다. |
| “gap을 지웠는데도” 위아래 공간이 큼 | flex 중앙 정렬·고정 높이·SVG viewBox 여백까지 추적 | CSS 속성명 대신 실제로 누가 공간을 차지하는지 측정한다. |
| 공간을 넓히려 모든 패딩을 삭제하고 폴더를 과대 확대 | 기준 장의 폴더 크기와 기본 여백 복구 | 사용자 요청이 중복 여백 삭제인지 모든 여백 삭제인지 구분한다. |
| 연결선이 너무 짧거나 너무 김 | 대상의 실제 외곽과 최소 간격을 기준으로 끝점 계산 | SVG 바깥 박스가 아니라 보이는 폴더·아이콘을 앵커로 쓴다. |
| 코디네이터가 위로 몰려 두 보고 선의 각도가 다름 | 두 워커 아이콘 중심의 평균에 코디 아이콘 배치 | 전체 라벨 묶음 중앙과 실제 아이콘 중심을 구분한다. |
| 메시지 아이콘이 양옆에 떠 있고 설명이 푸터로 넘침 | 메시지 옆 아이콘, 세 행 균등, 주체는 전체의 중앙 | 주체·메시지·설명의 각 정렬 축을 따로 정한다. |
| 주체 좌우만 바꾸고 선 방향은 유지 | question/보고와 reply 발신·수신에 맞춰 반전 | 화면 좌우가 아니라 발신자→수신자가 의미의 기준이다. |
| 흐름 네 단계가 같은 색·분리된 묶음이라 단절됨 | 동등한 단계와 색, 선, 작업 이름을 한 축에 배치 | 순서가 단순한 카드 나열보다 먼저 읽히는가? |
| 같은 대상의 줄기명·폴더명·색이 다름 | A→A, B→B와 색상 대응 | 장 사이에도 식별자를 유지한다. |
| `.git`이 큰 주요 파일처럼 보임 | 작은 크기·낮은 opacity·우측 하단 | 중요하지만 배경인 요소는 시각적 위계로 구분한다. 이 크기는 숨은 항목 사례의 변형이다. |
| 커밋 필드에 특정 예시 메시지를 정의처럼 넣음 | 항목명과 그 의미를 설명, 예시는 대본에서 | 항목 이름/항목의 뜻/예시 값을 구분한다. |
| 작업 의존을 후속 둘의 병렬 처리로 설명 | 이전 작업 결과가 있어야 시작 가능 | 같은 그림이라도 제목·부제가 가리키는 인과가 맞아야 한다. |
| Task A/B 뒤에서 갑자기 블로그·카드뉴스 상세 이름을 씀 | 배정 장에서는 Task A→Worker A, B→B | 이름의 일관성이 상세 예시보다 중요한 구간을 구별한다. |
| 배정 텍스트가 선 아래로 멀리 떨어짐 | 선 위 가까이 배치, 행 전체는 수직 중앙 | 연결 동작의 라벨은 노드 제목과 구별한다. |
| “보완”, “다음 작업”으로 루프 대상이 모호 | 재작업과 Task 식별자 사용 | 어느 작업으로 돌아가는지 구조로 보이는가? |
| 전체 실행 흐름에 주체가 없음 | Coordinator가 Task로 쪼개고 워커 배정·확인·정리 | 흐름의 책임자와 실제 작업자를 혼동하지 않는다. |
| 요청은 입력·결과물뿐인데 아래에 완료 기준을 따로 주장 | 요청에 사실 일치 확인·각 파일 저장을 추가 | 요청문과 아래 분해가 같은 내용을 말하는가? |
| “회사 말투”를 그대로 완료 기준이라 함 | 확인 가능한 사실 일치·결과물 저장을 제시 | 스타일도 명시된 규칙이 있으면 판단 기준이 된다. 막연한 말투만으로 완료 여부를 판정하지 않는다. |
| 마지막까지 수평 구조 반복 | 상단 사람·조율자, 하단 세 실행자의 층 구조 | 강의의 최종 효용이 다른 시각적 위계로 정리되는가? |
| 비교 후보를 선택 뒤에도 최종처럼 남김 | 승인 B안만 정식 번호로 유지, 대본 동기화 | 추가해 비교 요청과 최종 선택 이후 정리를 구분한다. |

## 4. 애니메이션은 설명의 순서다

### 세 종류를 분리한다

| 종류 | 언제 시작하나 | 승인 동작 |
|---|---|---|
| 진입 등장 | 슬라이드 진입 | 시간선 → 나이 라벨 → 차 → 한 줄 설명 |
| 개념 전개 | 설명 순서 | 경계 → 범위 이름 → 내부 항목, 줄기 → 공간 → 담당자 |
| 사용자 조작 | 해당 요소 클릭 | 차 이동, 작업 공간 패널 전환. 자동 반복 없음 |

- **경계도 등장시킨다.** 경계만 처음부터 보이는 오류를 막으려 별도 `.scope-frame.anim-item`을 둔다. 부모 전체에 등장 효과를 걸어 내부 요소를 통째로 움직이지 않는다.
- **고정 지도는 예외다.** 저장소의 3~5장 중 뒤의 두 장처럼 같은 구조에서 강조만 바꾸는 장은 `data-motion="none"`으로 정지시킬 수 있다. 모든 장에 효과를 붙이는 규칙이 아니다.
- **클릭 전환에도 fade는 남긴다.** 자동 타이머 삭제와 전환 효과 삭제는 다르다.
- **클릭 후 즉시 반응한다.** 자동차의 1.44초 초기 정지 구간을 제거했다. 자동 설명용 기다림을 클릭용 키프레임에 그대로 두지 않는다. 이후 중간 시점의 설명용 정지는 별개다.
- **포인터 클릭에 불필요한 테두리를 만들지 않는다.** 버튼별로 처리한다. 키보드 초점 피드백은 유지하되 전체 앱 outline을 지우지 않는다.
- **다시 들어오면 출발 상태.** 클릭하기 전 위치·선택 상태를 정의하고, 재진입·재생·빠른 이동도 확인한다.
- **모션 감소에서도 의미는 남긴다.** 클릭 전 대기, 클릭 후 최종 상태라는 구분은 유지한다. 이동만 생략한다.

마지막 화면만 찍으면 경계 누락·통째 등장·초기 지연을 놓친다. **진입 직후 / 단계 중간 / 완성 / 클릭 전후 / 재진입**을 분리해 확인한다.

## 5. 다른 에이전트의 작업 절차

1. 실제 서버 URL이 어느 HTML로 연결되는지 확인한다. 현재 승인본을 대상으로 삼는다.
2. 사용자 수정에서 바꾸려는 주장과 보존해야 할 부분을 분리한다. 명시하지 않은 제목·문구·장수까지 같이 바꾸지 않는다.
3. 앞·현재·뒤 장의 주장을 나란히 읽는다. 문제의 축, 용어 도입, 예시 식별자가 연결되는지 확인한다.
4. 카탈로그에서 관계에 맞는 패턴을 고른다. `data-pattern` 기사와 관련 CSS/JS/defs를 복사한다. 모든 템플릿을 새 덱에 넣지 않는다.
5. 슬롯을 실제 소스의 내용으로 교체한다. 그림의 범위·선·색·이름까지 새 주장에 맞춘다.
6. 본문 정렬과 요소의 실제 경계를 확인한다. 작은 화면은 복잡도·여백을 먼저 조정한다. 한 장만 글자 크기를 줄여 완료 처리하지 않는다.
7. 최종 HTML을 기준으로 `fastcampus-script` 대본과 짝 문서를 동기화한다. 미선택 후보는 요청 없으면 대본을 쓰지 않는다.
8. 실제 브라우저에서 렌더링과 동작을 확인한다. 사용자가 새로고침하며 검수 중이면 매번 링크를 반복하지 않는다.

## 6. 일반화하면 안 되는 것

- 특정 장의 gap=0, 폴더 폭, 2/3명의 에이전트 수는 그 장의 결정이다. 전역 기본값으로 만들지 않는다.
- 과거 도구는 여러 에이전트를 못 쓴다는 주장을 만들지 않는다. 비교의 핵심은 기본 사용 방식과 관리 부담이다.
- Orca 환경과 오케스트레이션의 조율을 같은 기능으로 설명하지 않는다.
- 폴더 그림은 실제 공간을 뜻할 때 쓴다. Run 같은 관리 단위를 물리적 폴더라고 가르치지 않는다.
- 현재 확정본이 발전했다고 과거 미채택 12~15번 패턴이 다시 승인된 것은 아니다. 이번 패턴 번호 12~15는 **현재 승인 덱에서 새로 추출한 다른 구조**다. 번호가 아니라 provenance와 구조를 확인한다.
- 촬영 상태·커리큘럼·대본 승인 상태를 템플릿 추출 때문에 임의로 바꾸지 않는다.
