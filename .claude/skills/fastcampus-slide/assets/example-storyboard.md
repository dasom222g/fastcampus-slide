## 용어 규칙 (Hermes 표기에 맞춘다)

| 이 덱에서 쓰는 말 | Hermes 표기 | 쓰지 않는 말 |
|---|---|---|
| 작업 | Task | 카드 |
| 상태 | Status (`Triage`/`Todo`/`Ready`/`In Progress`/`Done`/`Blocked`) | 칸, 단계 |
| 컬럼 | 보드 화면에서 상태별로 나뉜 세로 열 | — |
| 프로필 | Profile (담당자) | 팀원(단독 사용), 에이전트 |
| 부모 작업 / 자식 작업 | Link으로 연결된 앞뒤 작업 | 앞선 카드 |
| 위임 | `delegate_task` | 서브에이전트 호출 |

- 상태 이름은 **영문 원문 그대로** 노출한다. 보드 화면의 컬럼 이름과 같아야 학습이 이어진다
- 한국어 뜻은 상태 이름 아래 한 줄로 붙인다 (`~하는 상태`로 통일)
- `Todo`의 뜻은 **"만들어졌지만 아직 실행할 수 없는 상태"**다. 부모 작업 대기는 그 전형적인 사유일 뿐 정의가 아니다 — 소스도 "카드는 있으나 아직 실행 불가. **보통** 부모 작업이 끝나기를 기다리는 중"이라고 적는다
- 표기는 `Todo` 한 단어로 쓴다 (`To Do` 아님)

## 주제 도출

| 항목 | 내용 |
|---|---|
| 한 줄 주제 | AI 팀의 일은 대화 속이 아니라 보드 위의 작업으로 만들어져 정해진 상태를 따라 흐른다 |
| 청중 | AI에게 일을 시켜본 적은 있지만 여러 AI가 협업하는 구조는 처음 보는 사람 |
| 핵심 주장 1 | 위임(`delegate_task`)은 임시로 생겼다 사라져 성장하지 못하지만, 프로필은 기억을 갖고 보드에 남는다 |
| 핵심 주장 2 | 작업은 정해진 상태를 차례로 지나며, 각 상태는 "지금 무엇을 기다리는가"를 뜻한다 |
| 핵심 주장 3 | 새 기능 없이 작업을 연결하는 것만으로 팀 구조가 만들어진다 |

**버릴 내용**

- `delegate_task` 비교표의 기술 항목(형태 = RPC 호출 / 영속 메시지 큐 + 상태 기계, 협업 방향 = 계층형 / 대등형) — 용어를 설명하는 데만 시간이 들고 이점이 드러나지 않는다
- 비교표의 `사람 개입` 행 — 슬라이드 2의 카드 3장 안에 넣으면 축이 넷이 된다. 같은 슬라이드 하단 한 줄로만 남긴다
- 설계 철학 3표현(DB의 row, OS 프로세스, 영속성·관측 가능성) — 개념어라 그림으로 옮기면 이해가 아니라 암기가 된다
- 보드를 여러 개 만드는 법과 보드 간 격리 — 처음에는 보드 하나만 쓰므로 흐름 이해에 불필요
- 작업공간 3종의 세부(공유 폴더 경로 지정 방식, git worktree) — 슬라이드 3의 `Workspace` 카드에서 "임시 · 공유 · 코딩용 세 종류"까지만 다룬다
- `Archived` 상태 — 완료된 작업을 화면에서 숨기는 정리 동작이라 작업 흐름 자체는 `Done`에서 끝난다
- Triage 자동 분해와 프로필 설명 품질 — 흐름을 이해한 뒤에 손대는 운영 설정 영역
- 내부 동작 수치(60초 순회) — 덱 주제와 무관한 운영 수치
- METRIC 타입 미사용 — 소스의 수치가 모두 위 항목에 해당해 덱에 쓸 수치가 없다

**감수한 것**

- 슬라이드 4는 상태 5개를, 슬라이드 3은 부품 6개를 한 화면에 놓아 요소가 가이드 권장(4개)을 넘는다. 둘 다 "전체를 한눈에"가 목적이라 쪼개지 않고 `grid-3--tight`(카드 6장) · 기본 `timeline`(5장)으로 처리
- `Blocked`는 정상 경로에서 벗어나는 상태라 열에 넣지 않고 하단 한 줄로 다룬다
- 타입과 클래스 대응은 템플릿 기준: `CARD_GRID` → `grid-3` + `col-card`, `ICON_ROW` → `timeline`, `TREE` → `fan`
