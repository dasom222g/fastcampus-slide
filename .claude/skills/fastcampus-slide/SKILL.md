# FastCampus Slide

패스트캠퍼스 강의 슬라이드 덱을 만든다. 외부 스킬이나 다른 프로젝트에 의존하지 않는 독립 스킬이며, 디자인 시스템·레이아웃 타입·템플릿을 모두 이 폴더 안에 갖고 있다.

소스에 제한은 없다 — md 학습 자료, 강의 대본, 정리 노트, 채팅에 붙여넣은 텍스트 무엇이든 받는다.

**스킬 원본은 `.claude/skills/fastcampus-slide/`에 유지한다.** `.agents/skills/fastcampus-slide`는 원본을 가리키는 심볼릭 링크다. 두 벌로 복사하지 않는다. 링크 안의 파일 내용을 수정해도 같은 원본에 반영된다. 유지보수는 `.claude` 원본을 직접 수정하는 것을 기본으로 하고, 심링크 자체를 일반 폴더나 복사본으로 교체하지 않는다.

## 작업 전 — 반드시 읽는 것

1. **`docs/curriculum.md`** — 이 클립의 파트·챕터·클립 번호와 제목. **파일 이름의 기준**이다
1b. **`artifacts/<part>/_source/<clip>.md`** — 이 클립의 슬라이드 소스(구성안). **무엇을 몇 장에 담을지의 기준**이다
2. **`docs/course-brief.md`** — 청중·톤·용어 규칙·강의를 관통하는 축. **무엇을 어떻게 말할지의 기준**이다
3. **`docs/confirmed-copy.md`** — 강사 확정 문구. **소스나 내 표현과 어긋나면 이 문서를 따른다**
3b. **`docs/patterns.md`** — 멀티에이전트 패턴 4가지의 이름·구조·색. 패턴이 한 번이라도 등장하는 덱이면 **반드시** 읽는다
4. **`artifacts/*/_feedback/*.md`의 `## 3. 다음부터 이렇게 해` 섹션 전부** — 이전 덱에서 받은 지적이 누적된 곳이다. 안 읽으면 같은 지적을 또 받는다

커리큘럼과 소스 자료가 어긋나면 **커리큘럼을 따르고** 어긋난 지점을 보고에 적는다.
피드백을 반영해 산출물을 고칠 때는 **사용자가 직접 고친 부분을 되돌리지 않는다.**

## 저장소 구조 — 클립 하나 = 덱 하나

계층은 **파트 → 챕터 → 클립**이고, 슬라이드는 클립 단위로 만든다. **이론 클립만 만들고 실습·데모 클립은 만들지 않는다.**

```
artifacts/<part>/                  파트 하나 = 폴더 하나 (part1, part2 …)
  outputs/<ch>-<n>-<slug>.html             클립 하나 = 덱 하나. 이것만 배포된다
  _storyboard/<같은이름>.md         구성 확정 문서 — HTML보다 먼저 저장한다
  _script/<같은이름>.md             최종 슬라이드와 한 벌인 구어체 발표 대본
  _feedback/<같은이름>.md           슬라이드별 피드백 입력 파일
  _source/<같은이름>.md             이 클립에만 쓰는 추가 자료 (커리큘럼 외 자료를 받았을 때)
  _images/                          이 파트의 이미지·생성 이미지 (하위 폴더 없이 파일만)
  _qa/                              검수용 슬라이드 캡처·비교 화면 (슬라이드 요소와 분리)
assets/                            모든 덱이 공유하는 에셋 (패스트캠퍼스 · Claude Code · Codex · Orca 로고)
index.html                         덱 목록 — 커리큘럼 순서대로
```

- **파일 이름은 `ch{챕터번호}-{클립번호}-{영문슬러그}`** — 예 `ch01-03-orca-setup.html`. 번호는 커리큘럼의 번호를 그대로 쓴다
- **덱과 소스·스토리보드·피드백·대본은 확장자만 빼고 이름이 같다.** 이름이 어긋나면 짝을 찾을 수 없다
- 공개 주소는 `vercel.json` rewrite로 `/<part>/outputs/<파일명>` → `/artifacts/<part>/outputs/<파일명>.html`
- **HTML 안의 에셋 경로는 루트 절대경로만 쓴다** — `/assets/orca-logo.svg`, `/artifacts/<part>/_images/foo.png`. 상대경로(`./`, `../`)를 쓰면 배포 주소에서 깨진다
- 여러 덱이 함께 쓰는 로고·아이콘은 `assets/`에, 각 파트의 이미지는 해당 `partN/_images/`에 파일로 바로 둔다
- **이미지 폴더는 파트까지만 구분한다.** `artifacts/partN/_images/<파일명>` 구조를 쓴다. `_images/` 아래 클립·슬라이드·버전·후보별 하위 폴더를 만들지 않는다. 파트 밖의 `artifacts/_images/`로 합치지도 않는다. 비교 제작 루트도 `codex*/partN/_images/<파일명>`처럼 동일하게 적용한다.
- **`_images/`에는 슬라이드 요소로 쓰는 이미지와 그 생성 후보만 둔다.** 검수용 전체 슬라이드 캡처, 브라우저 스크린샷, 비교 화면, 컨택트시트는 `partN/_qa/`에 저장한다. 이미지 보존·폴더 정리 때도 캡처를 `_images/`에 합치지 않는다. 슬라이드 본문 요소로 실제 사용하는 제품 화면 캡처는 `_images/`에 둘 수 있다.
- 파일명이 겹치면 `ch01-02-what-is-orca--cover.png`처럼 파일명에 용도를 붙인다. 최종본 정리 때 사용 이미지와 탈락 후보를 모두 보존하고, 이동한 이미지의 HTML·스토리보드·템플릿·인덱스 경로를 갱신한다. 파일 존재와 실제 브라우저 로딩까지 검증한다.
- 외부 URL 이미지는 쓰지 않는다
- 작업 문서(`_source`, `_storyboard`, `_feedback` 등)와 `docs/`는 `.vercelignore`의 명시된 규칙으로 배포에서 제외한다. **런타임 이미지가 있는 `_images/`는 배포에 포함한다**

**미리보기·시각 검수는 로컬 서버로 한다.** 루트 절대경로와 rewrite 때문에 별도 처리 없는 `file://`에서는 에셋이 깨진다. 직접 열기도 요청받으면 파일 모드의 경로 해석을 별도로 구현·검수한다. 터미널 문제 골든셋에 그 사례가 있다.

```
vercel dev          # rewrite·cleanUrls까지 배포와 동일하게 확인 — http://localhost:3000/<part>/outputs/<clip>
```

### 시각 정책 — 아이콘만으로 때우지 않는다

**이모지 아이콘 하나로 슬라이드를 채우지 않는다.** 개념에 구조가 있으면 그 구조를 눈에 보이게 그린다.
슬라이드를 설계할 때마다 "이 장은 무엇을 **보여줘야** 하는가"를 먼저 정하고, 아래에서 수단을 고른다.

| 무엇을 보여주나 | 수단 | 왜 |
|---|---|---|
| **관계·흐름·분기·루프** (구조도) | **인라인 SVG / CSS 도식** | 한글 라벨이 선명하고, 다크 테마 색 변수를 그대로 쓰며, 나중에 문구만 고칠 수 있다 |
| 단계·순서 | 관계에 맞춰 그린 SVG 도식 | 순서와 연결을 실제 의미에 맞게 표현한다 |
| **장면·상황·비유** (사람이 겪는 일, 캐릭터) | **생성 이미지** → `_images/` | 그림이 해야 할 일은 분위기와 상황이지 라벨이 아니다 |
| 단일 개념 선언 | 공통 `.statement` 선언문 | 핵심 문장의 위계를 유지한다 |

**구조도를 생성 이미지로 만들지 않는다.** AI 이미지 생성은 한글 라벨을 정확히 렌더하지 못한다 —
박스 안 글자가 뭉개지면 구조도가 아니라 장식이 된다. 라벨이 있는 그림은 전부 SVG/CSS로 그린다.

**생성 이미지를 쓸 때:**
- 배경은 덱 배경(`#0d1117`)에 녹아야 한다. 밝은 배경 위 일러스트를 그대로 얹지 않는다
- 같은 대상(에이전트·사람·시스템)은 **덱과 파트를 넘어 같은 캐릭터·같은 색**으로 유지한다
- 서사형 이미지는 스토리보드에 **장면 원장**(등장 주체별 출발점 → 현재 위치 → 목적지 → 흔적)을 먼저 쓰고, 생성 후 같은 항목으로 대조한다
- `_images/`에 저장하고 HTML에서는 `/artifacts/<part>/_images/<파일명>`으로 참조한다

**SVG 도식을 그릴 때:**
- 색은 `:root` 변수(`var(--brand)` 등)를 `stroke`/`fill`에 그대로 쓴다. 인라인 색상 금지
- 텍스트는 `<text>`가 아니라 **HTML 요소를 CSS로 배치**하는 쪽을 먼저 검토한다 (한글 폰트·줄바꿈이 자연스럽다).
  SVG는 선·화살표·연결만 그리고 라벨은 HTML로 얹는 하이브리드가 기본이다
- 화살촉은 `marker` 또는 CSS `border` 삼각형. 글리프(`▶` `▼`)를 쓰지 않는다
- 두 구조를 비교할 때는 **같은 시각 구조에서 뿌리와 잎만 바뀌게** 한다

### 강의 전체에서 고정된 색 배정

색 연속성은 한 덱 안에서만이 아니라 **이 강의의 모든 덱에 걸쳐** 지킨다. 수강생이 3강에서 익힌 색이 5강에서 뒤집히면 안 된다.

| 대상 | 색 |
|---|---|
| Claude Code · 실행하는 쪽 · 이 덱의 기본 축 | brand (`#fc1c49`) |
| Codex · 두 번째 주체 · 파생 | purple |
| coordinator · 조율 · 대기 | yellow |
| Orca 인프라 · harness · 저장소 · AI 아님 | gray |
| 기존 방식의 한계 · 문제 · 차단 | orange |
| 완료 · 로그인 성공 · 결과물 | green |

새 대상이 나와 표에 없는 색을 배정했으면 **이 표에 한 줄 추가한다.**

## 시각 게이트 — 글자만 있는 장을 만들지 않는다

**장면·상태·타이포의 최신 기준은 `references/goldenset-terminal-problem.md`다. 이미지 밀도는 `references/goldenset-image-density.md`와 아래 두 덱도 참고한다.**
좋다고 확인된 덱의 실제 수치이므로 감으로 정하지 말고 여기서 가져온다.

### 패턴 선택과 크기

- `references/slide-layouts.md`의 **등록된 8개 패턴**에서 구조를 고른다. 현재 템플릿은 표지·좌우 도식·좌우 장면·열린 3열·상태가 있는 3열·분기 구조·요청/응답 구조·전환 비교다.
- `scene`은 이미지/도식과 문장을 결합하고, `triptych`는 대등한 세 개념을 도식으로 설명한다. 글자를 박스에 나열해서 대신하지 않는다.
- 같은 역할의 본문은 `.statement`, 항목 제목은 `.heading`, 설명은 `.copy`로 통일한다. 기준 장을 지정받으면 family·size·weight·line-height·letter-spacing·강조까지 비교한다.
- 넓은 화면에서 묶음을 중앙에 두고 최대 폭을 제한한다. 긴 문구나 좁은 폭 때문에 글자부터 줄이지 않는다.
- 새 관계가 필요하면 스토리보드에서 의미를 먼저 확정하고 해당 덱에 구현한다. **미채택 예제를 공통 템플릿으로 승격하지 않는다.**

### 템플릿을 수정할 때 — 2026-09-08 사용자 정정

- **템플릿은 실제 강의 덱을 모은 파일이 아니다.** 화면은 역할이 드러나는 중립 문구와 교체 슬롯으로 작성한다. 실제 클립 제목·설명·제품 로고·작업 화면·임의 수치를 넣지 않는다. 공통 FastCampus 푸터만 유지한다.
- 승인 슬라이드에서는 **레이아웃·타이포·여백·관계 표현**만 추출한다. 실제 콘텐츠는 새 덱의 소스와 스토리보드에서 가져온다.
- 최신 디자인으로 갱신할 때는 예전 CSS와 예제 전체를 검토한다. 기존 것을 그대로 둔 채 뒤에 새 예제를 덧붙여 서로 다른 규격을 섞지 않는다.
- 이전 12~15번 미채택 예제는 철회했다. 이후 사용자가 구조도와 과도기 대비의 템플릿화를 명시적으로 요청하여 6~8번을 추가했다. 이전 예제를 복구하지 않고 현재 참고 덱의 구조를 중립화했다. 새 패턴은 사용자 요청이나 채택 근거를 선택 가이드에 남긴다.
- 등록된 패턴 수·선택 가이드·HTML 예제를 함께 갱신한다. 검수는 2133×1200을 기본, 1280×800을 보조로 한다.

## 핵심 원칙: 구성이 확정되기 전에는 HTML을 쓰지 않는다

**소스에서 바로 HTML로 건너뛰면 안 된다.** 슬라이드 구성을 즉흥적으로 짜게 되고, 근거 없는 문장과 수치가 섞여 들어간다. 스토리보드는 "무엇을 말할지"를 확정해 "어떻게 그릴지"와 분리하는 장치다.

```
소스 → [1] 주제 도출 → [2] 스토리보드 작성·저장 → [3] 스토리보드 보고 HTML 제작
```

**단, 소스가 이미 스토리보드(확정된 구성)라면 그것을 그대로 쓴다.** 같은 걸 다시 만들지 않는다.
필요한 것은 "스토리보드라는 파일"이 아니라 **"HTML을 쓰기 전에 구성이 확정돼 있는 상태"**다.

**게이트 (어길 수 없는 조건):**
- 구성이 확정되기 전에는 HTML 작성을 시작하지 않는다. 스스로 구성해야 하는 경우라면 스토리보드를 **파일로 저장한 뒤에** 제작을 시작한다
- HTML의 모든 문장은 확정된 구성에 있는 문장이어야 한다. HTML 단계에서 새 메시지를 만들어내지 않는다
- 구성이 확정되면 사용자 확인 없이 곧바로 제작으로 넘어간다 (원스톱)

## 입력 판정: 어디서 시작할 것인가

가장 먼저 소스가 얼마나 여문 상태인지 판정한다. **판정 결과를 사용자에게 되묻지 않는다.**

| 소스 상태 | 판정 근거 | 시작 지점 |
|---|---|---|
| **원자료** | 슬라이드 단위로 나뉘어 있지 않은 모든 것 — 학습 자료·대본·노트·붙여넣은 텍스트 | Step 1부터 전부 |
| **구성 초안** | 슬라이드 단위로는 쪼개져 있으나 화면에 들어갈 문구나 근거가 비어 있다 | Step 2부터. 주어진 구성의 **순서와 메시지를 유지한 채** 빈 칸만 채워 스토리보드로 완성한 뒤 제작 |
| **확정 스토리보드** | 슬라이드마다 제목·핵심 메시지·화면 요소가 정해져 있다 | Step 3부터. 스토리보드를 새로 만들지 않는다 |

**판정 기준 한 줄:** 슬라이드 단위로 쪼개져 있고 각 화면에 들어갈 내용이 정해져 있으면 확정으로 본다. 파일 위치·파일명·형식이 아니라 **내용의 성숙도**로 판단한다.

**구성 초안·확정 스토리보드일 때 지킬 것:**
- 사용자가 정한 슬라이드 순서·개수·메시지를 임의로 바꾸지 않는다. 더 나은 구성이 보여도 만들고 나서 보고에 한 줄로 제안한다
- 규칙 위반이 있어도(제목이 문장형, 요소 초과, 근거 없음) 임의로 고치지 않고 그대로 만든 뒤 보고에 적는다
- 빈 칸을 채울 때 소스에 없는 수치·고유명사를 만들어내지 않는다 (사실 규율은 그대로 적용)

## Step 1: 소스 분석 → 주제 도출

읽고 아래를 확정한다. 결과는 스토리보드 상단 "주제 도출" 블록에 기록한다.

- **한 줄 주제**: 이 덱이 전달하는 단 하나의 메시지 (완결된 한 문장)
- **청중**: 누가 보는가 (강의 덱이므로 "무엇을 이미 알고 무엇을 처음 보는 수강생인가"까지)
- **핵심 주장 3개**: 덱 전체를 지탱하는 근거 축
- **버릴 내용**: 소스에 있지만 넣지 않는 것 + 이유
- **용어 규칙**: 소스가 특정 제품·시스템을 가르친다면, 원문 표기를 그대로 노출할 용어를 확정한다 (화면 표기와 제품 화면이 일치해야 학습이 이어진다)
- **총 슬라이드 수**:

| 소스 분량 | 슬라이드 수 |
|---|---|
| A4 1~2장 | 6~8장 |
| A4 3~5장 | 8~12장 |
| A4 6장 이상 | 16장을 넘기지 말고 나머지는 "버릴 내용"에 명시 |

**사용자가 슬라이드 수나 구성을 직접 정해줬으면 그것이 우선이다.** 위 표는 스스로 정해야 할 때의 기준이다.

소스가 여러 개면 먼저 하나의 줄거리로 합친 뒤 위를 확정한다. 소스끼리 내용이 어긋나면 어느 쪽도 단정하지 말고 보고에 적는다.

**소스는 클립 단위 문서다.** `artifacts/<part>/_source/<clip>.md` 하나가 이 덱의 범위 전부다 — 옆 클립 파일을 열어 내용을 끌어오지 않는다.

- frontmatter의 `슬라이드: N장`이 **총 슬라이드 수**다. Step 1의 분량 기준표보다 우선한다
- `슬라이드: 없음. 말로 전달`이라 적힌 섹션은 덱에 넣지 않는다
- 인용문(`>`)으로 적힌 문장은 **화면에 그대로 올릴 문구**다. 바꿔 쓰지 않는다
- 새 소스를 받았는데 파일이 없으면 덱과 같은 이름으로 `_source/<clip>.md`에 저장한 뒤 시작한다

### 사실 규율 (가장 중요)

- 소스에 없는 **수치·고유명사·인용을 절대 만들어내지 않는다**
- 모든 슬라이드에 근거(소스 내 문장이나 섹션)를 스토리보드에 남긴다
- 흐름상 필요하지만 근거가 없는 슬라이드는 근거 칸에 `출처 없음 — 연결용`이라 적고, 수치·고유명사를 쓰지 않는다
- 소스의 애매한 표현을 단정으로 바꾸지 않는다 (예: "가능성이 있다" → "된다" 금지)

## Step 2: 스토리보드 작성 → `artifacts/<part>/_storyboard/<clip>.md`

덱 골격은 아래를 기본으로 하고, 소스 성격에 따라 중간 블록만 조정한다.

```
1  표지            COVER_SCENE        클립 정체 + 제목 + 시각 1점. 표지에 목차·학습 항목 목록 금지
2  주제 선언        (내용에 맞게) 덱을 꿰는 한 문장 (목차가 아니라 선언으로 연다)
3  문제 제기        (내용에 맞게) 왜 이 얘기를 하는가
4~ 근거 블록 A      (타입 자유)   핵심 주장 1
   근거 블록 B      (타입 자유)   핵심 주장 2
   근거 블록 C      (타입 자유)   핵심 주장 3
n   마무리          (내용에 맞게) 한 문장으로 닫거나 전체 구조를 그림 하나로
```

### 표지 게이트 (어길 수 없다)

**모든 덱의 1번은 표지(`COVER_SCENE`)다. 표지에 목차를 절대 넣지 않는다.** 제목과 시각 1점으로 주제를 소개한다. `WHAT YOU LEARN`, 배우는 것, 학습 목표, 핵심 주장 목록, 번호가 붙은 미리보기도 목차이므로 금지한다. 과거 피드백·예제에 목록을 권하는 내용이 남아 있어도 이 사용자 지시가 우선한다.

- `slide__label`: `Part N · Chapter N · ChNN-NN · N분` — 커리큘럼 그대로
- `slide__title`: **커리큘럼의 클립 제목 그대로** — 제목 12자 규칙의 유일한 예외. 강조 `.hl` 한 곳
- `slide__sub`: 스토리보드 「주제 도출」의 한 줄 주제
- 표지 본문에는 시각 1점만 둔다. `learn`·`learn-item`·목차 열을 만들지 않는다.
- 시각 1점: 이 클립의 이미지 중 **바로 다음 장에 나오지 않는 것** (`scene__visual`). 장면 이미지가 없으면 주제를 표현하는 도식 한 점을 설계한다
- 표지는 `슬라이드: N장`에 포함된다 — 소스 frontmatter의 N = 표지 1 + 본문 섹션 합
- 표지 다음이 곧 주제 선언(2번)이다. 표지가 있다고 선언 슬라이드를 빼지 않는다

- 한 슬라이드 = 한 메시지. 두 개가 나오면 쪼갠다
- 연속 장의 역할을 확인한다. 같은 관계를 비교·확대하는 장은 골격과 타이포를 유지하고, 설명 방식이 바뀔 때 패턴도 바꾼다.
- 패턴은 `references/slide-layouts.md`의 구조별 선택표에서 고른다. 필요한 관계를 기존 패턴으로 표현할 수 없을 때만 의미가 분명한 변형을 만든다.
- METRIC 타입은 소스에 실제 수치가 있을 때만 쓴다
- **색 배정도 구성의 일부다.** 화면 요소마다 색 톤을 정해 적고, 위의 「강의 전체에서 고정된 색 배정」 표를 먼저 확인한다. pink·rose·lime은 일반 강조색으로 쓰지 않는다

**쓰기 전에 `assets/example-storyboard.md`를 연다.** 각 칸을 어느 수준까지 채워야 하는지의 형식 기준이다. 그 파일의 과거 레이아웃 이름·CSS는 현재 템플릿에 적용하지 않는다. 형식 규칙은 `references/storyboard-format.md`에 있다.

예제를 복사해 내용만 바꾸는 방식으로 작성하고 `artifacts/<part>/_storyboard/<clip>.md`로 **저장한다.**
슬라이드별로 타입·핵심 메시지·근거·화면 요소(실제 들어갈 텍스트 + 색)·애니메이션 순서·발표 노트를 채운다.
자리표시자("적당한 설명")를 남긴 채로 Step 3에 넘어가지 않는다.

## Step 3: HTML 덱 제작 → `artifacts/<part>/outputs/<clip>.html`

1. `assets/base-template.html`을 `artifacts/<part>/outputs/<clip>.html`로 복사해 시작한다 (확정 디자인의 중립 템플릿 예제가 들어 있다)
2. 스토리보드가 지정한 타입의 `<article class="slide">`만 남기고 나머지 예제 슬라이드는 삭제한다 (첫 장은 COVER_SCENE 표지 패턴으로 두며 목차는 넣지 않는다)
3. 남긴 슬라이드를 스토리보드 순서대로 재배열하고 `data-index`를 **0부터** 다시 매긴다. `active` 클래스는 첫 슬라이드에만
4. 스토리보드의 "애니메이션 순서"대로 요소를 배치한다 — **등장 순서 = DOM 순서**다. 등장할 요소에 `anim-item`만 붙이면 타이밍은 JS가 처리한다
5. `<title>`을 덱 주제로 바꾸고, 하드코딩된 `<span id="tot">N</span>`을 실제 슬라이드 수로 맞춘다
6. 각 `<article>` 위 주석에 스토리보드의 발표 노트를 옮긴다
7. 푸터는 템플릿 그대로 둔다 — 모든 슬라이드가 패스트캠퍼스 로고 하나다
8. 에셋 경로는 루트 절대경로로 쓴다 (`/assets/...`, `/artifacts/<part>/_images/...`)
9. **커스텀은 「시각 게이트 3」의 기준을 통과한 것만** 쓴다 — 의미를 그리는 장치는 되고, 박스 격자는 안 된다. 통과했으면 `deck.html` 안에 `/* ── 이번 덱 전용 변형 ── */` 주석 블록으로 몰아서 정의하고, 일회성 변형은 베이스 템플릿에 넣지 않는다. 사용자 요청으로 재사용 패턴을 승격할 때는 예제·선택 기준·검수를 함께 추가한다
10. `index.html`에 이 덱 링크(`/<part>/<clip>`)를 추가한다 — 목록은 **파트 → 챕터 → 클립** 3단이다.
    해당 파트 `<section class="part">` 안에서 이 클립의 챕터 `<div class="chapter">`를 찾아 그 `<ul>`에 커리큘럼 순서대로 넣고,
    파트·챕터 블록이 없으면 블록부터 만든다(번호·제목은 `docs/curriculum.md` 그대로).
    `.meta`는 클립의 실제 슬라이드 장수만 쓰고 (`길이`·소요시간은 표기 금지),, 머리말 `.count`와 파트의 `.part__meta` 개수도 갱신한다.
    챕터 번호는 파트마다 1부터 다시 시작한다 — Part 1의 `Ch02-01`과 Part 2의 `Ch02-01`은 다른 클립이다

**이 단계에서 하지 않는 것:** 슬라이드 추가·삭제·순서 변경, 스토리보드에 없는 문장·수치 창작, 핵심 메시지 재해석.
Step 3에서 구성 문제를 발견하면 **스토리보드를 먼저 고치고** 내려온다. HTML만 고쳐서 두 파일이 어긋나게 두지 않는다.

## 골든셋에서 나온 규칙 (어길 수 없다)

표지·상태 표현은 `references/goldenset-terminal-problem.md`, 입문 도구 설명의 범위·정의·포함 관계는 `references/goldenset-orca-basics.md`를 따른다. 아래 개념·용어 규칙은 `references/goldenset-orca-judgment.md`에서 축적했다. 주제별 적용 범위를 지키고, 과거 덱의 주장·분량을 현재 원고에 이식하지 않는다.

- **동일 템플릿의 동일 역할은 공통 타이포 규칙을 쓴다.** 사용자가 기준 장을 지정하면 폰트 종류·크기·굵기·행간·자간·강조 행을 맞춘다. 긴 문구는 영역부터 조정한다.
- **장식 박스·가로선을 임의로 추가하지 않는다.** 한 화면·소유 관계를 설명하는 창 경계는 의미가 있으므로 별개다.
- **상태는 색과 형태로 구분하고, 설명은 핵심 효용을 말한다.** 상태 범례로 “한 화면에서 여러 에이전트 확인”이라는 메시지를 대체하지 않는다.

### 청중과 용어

- **청중 수준을 먼저 확정한다.** 개발자 대상이 아니면 도메인 용어(브랜치·clone·체크아웃 등)를 덜어내고 개념 하나만 남긴다. 소스가 개발 문서라고 청중도 개발자인 것은 아니다
- **제목에 낯선 원문 용어를 그대로 쓰지 않는다.** `worktree 분리`가 아니라 `Orca의 작업 단위`다 — 그 용어를 아는 사람만 따라오는 제목은 실패다
- **낯선 용어가 쏟아지기 직전에 용어 슬라이드를 넣는다.** 용어 정리는 형식적 절차가 아니라, 이후 슬라이드가 서 있을 바닥이다
- **정의가 먼저, 비유는 보조다.** 비유만 쓰면 "그래서 실제로 뭔데"가 남는다. 정의를 본문 크기로, 비유를 작고 흐린 한 줄로 둔다
- **비유는 층위를 맞춘다.** 책상과 직원이 있는 공간을 "운영실"이라 부르면 층이 어긋난다
- **원문 용어를 타이틀에, 한국어를 딱지에 둔다.** 외워야 할 말이 보조로 밀리면 안 된다

### 사실

- **제품·도구를 가르치는 덱이면 공식 문서나 CLI로 확인한다.** 소스 노트만 믿지 않는다 (`orca skills get <skill>`, 공식 docs). 근거가 없는 용어는 쓰지 않는다 — 그럴듯한 영문 조어가 특히 위험하다
- **레이어를 뭉개지 않는다.** "환경"과 "그 위에서 도는 기능"은 다른 층이고, 원본과 복제본도 다른 층이다. 한 문장 안에서 섞이면 뒤 슬라이드가 전부 어긋난다

### 문장

- **`slide__sub`와 `tip`은 기호(`—`) 없이 한 문장으로 압축한다.** 두 문장이 필요하면 슬라이드가 잘못 나뉜 것이다
- **개수는 정보가 아니다.** `메시지 여섯 종`이 아니라 `Run의 메시지 종류`다. 제목은 무엇인지를 말한다
- **줄글 대신 정의를 쓴다.** 카드 본문은 설명 문단이 아니라 한 줄 정의다
- **수사적·시적 표현을 쓰지 않는다.** 사실만 담백하게

### 그림

- **구조는 말로 쓰지 말고 구조로 보여준다.** 두 패턴을 비교할 때는 **같은 시각 구조에서 뿌리와 잎만 바뀌게** 하면 차이가 말 없이 읽힌다
- **새 패턴 전에 등록된 8종의 선택표를 확인한다.** 장면·관계·병렬 구성 중 의미에 맞는 것을 고른다. 제공하지 않는 구조는 스토리보드에 정의하고 새 변형으로 구분한다. 같은 역할의 타이포는 공유한다
- **화살표에 글리프(`▶` `▼` `↕`)를 쓰지 않는다.** SVG 선과 화살촉으로 그린다
- **아이콘 연속성은 색 연속성과 같은 규칙이다.** 같은 대상은 덱 전체에서 같은 아이콘을 쓴다. 아이콘이 이어지면 슬라이드 사이의 관계가 말 없이 읽힌다
- **아이콘은 의미로 고른다.** 형태만 예쁜 것 말고, 그 슬라이드가 주장하는 바와 같은 방향을 가리키는 것을 쓴다
- **개념 정의 슬라이드를 순서(timeline)로 그리지 않는다.** 순서가 아닌 것을 파이프라인으로 그리면 없는 인과가 생긴다. 정의는 공통 `.statement`로 핵심 문장을 강조한다
- **카드로 쪼개면 늘 나아지는 게 아니다.** 핵심 하나를 크게 말해야 할 자리에 카드 3장을 놓으면 힘이 흩어진다
- **화면을 반으로 나누는 게 기본값이 아니다.** 도식이 주인공이면 7:3처럼 비율로 위계를 만든다

### 이야기 압축과 순서

- **제품·기능 덱은 사용자가 보는 장면에서 시작한다.** `보이는 화면 → 실제 정체 → 시스템 제약 → 직접 겪은 문제 → 해결 규칙 → 실행 흐름`을 우선 검토한다. 역할·옵션 목록으로 시작하지 않는다
- **핵심 해결책이 규칙 묶음이면 한 장에 모은다.** 역할·호출·파일 설명으로 흩뜨리지 말고 규칙 자체를 큰 카드 그리드로 먼저 보여준다
- **삭제 테스트를 한다.** 한 장을 빼도 핵심 주장이 그대로면 그 장은 기능 설명일 뿐이다. 다른 이름으로 되살리지 않는다

### 이미지 주도 슬라이드

- **이미지 안에 네거티브 스페이스가 있으면 별도 텍스트 열을 만들지 않는다.** 이미지를 프레임 전체에 쓰고 빈 공간 안에 큰 텍스트를 오버레이한다
- **서사형 생성 이미지는 상태도처럼 검증한다.** 인물 수, 출발점, 현재 위치, 목적지, 이동 방향, 발자국·시선의 시간 순서가 모두 맞아야 한다
- **결론은 그림과 붙인다.** 이미지가 문제를 보여주면 핵심 비용도 이미지 위 캡션으로 결합하되 사람·동선·자료를 가리지 않는다
- **프롬프트 전에 장면 원장을 쓴다.** 등장 주체별 `출발점 → 현재 위치 → 목적지 → 흔적`을 한 줄씩 적고, 생성 후 같은 항목으로 대조한다

### 시각 크기와 카드 밀도

- **초반부의 주인공은 크게 둔다.** 표지·핵심 이미지 박스는 남는 본문 높이를 쓰고 의미 없는 여백 때문에 텍스트와 피사체가 멀어지지 않게 한다
- **내용이 많다고 먼저 줄이지 않는다.** 영역 높이·여백·제목·본문 크기를 확보한 뒤 문장을 압축한다. 그래도 넘치면 메시지 단위로 장을 나눈다
- **특정 슬라이드의 크기 조정은 전용 modifier로 국소화한다.** 공통 카드 크기를 바꿔 다른 장을 망가뜨리지 않는다

### 기술 문장과 색

- **시스템 제한은 사용자의 행동을 기준점으로 쓴다.** `전송 한 번` 대신 `사용자 메시지 한 번`처럼 무엇을 했을 때 무엇이 얼마나 이어지는지 명시한다
- **기본 색축은 brand + purple이다.** orange는 문제·경고처럼 의미가 분명할 때만 쓰고, 일반 장식에 pink·rose·lime을 쓰지 않는다
- **색 선택을 중간에 흔들지 않는다.** 스토리보드에서 역할과 색을 확정하고, 사용자 요청으로 바꾸면 변수·클래스·스토리보드를 한 번에 동기화한다

### 수정 요청을 받았을 때

- **"텍스트만 바꿔줘"는 텍스트만 바꾸라는 뜻이다.** 클래스·색·위치를 함께 바꾸지 않는다. 더 나은 구성이 보여도 만들고 나서 보고에 한 줄로 제안한다
- **사용자가 직접 고친 부분은 되돌리지 않는다.** 전체 규칙을 적용할 때도 그 부분은 건너뛰고 보고에 남긴다
- **일부 슬라이드만 고쳐도 번호가 밀리면 전부 갱신한다** — `data-index`, `<span id="tot">`, 발표 노트의 `N / M`, 스토리보드

## Step 4: 반드시 지킬 규칙

**디자인·구조 규칙은 `references/slide-layouts.md`를 따른다.** 색상 시스템·타이포·간격·`data-index`·타임라인 columns 규칙이 모두 거기 있다. 이 문서에 수치를 옮겨 적지 않는다.

여기서 지킬 것은 **내용에 관한 규칙**이다.

- **클립·강의의 소요시간은 슬라이드와 덱 인덱스 어디에도 표기하지 않는다.** `Ch01-01 · 8분`, `약 10분`, `3.4시간` 같은 길이 표기를 표지 라벨·본문·푸터·목록에 넣지 않는다. 커리큘럼에 시간이 있어도 화면으로 옮기지 않는다. 최종 검수에서 소요시간 표기가 없는지 확인한다.

- 모든 텍스트 한국어. 단, 용어 규칙에서 원문 노출로 확정한 용어는 영문 그대로 (한국어 뜻을 한 줄로 병기)
- 슬라이드 제목: 명사/명사구, 최대 12자, 문장형 절대 금지. 강조는 `.hl` 한 곳만
  - O: `다섯 상태`, `위임과의 차이` / X: `상태가 다섯 개 있다`
  - **1번 슬라이드(표지)의 제목은 커리큘럼 클립 제목 그대로** (12자 규칙의 유일한 예외) — `표지`·`커버`처럼 슬라이드 종류를 적지 않는다. 2번(주제 선언)부터는 명사구 12자 규칙
- 표지 선언문·tip·마무리 문장: 수사적·시적 표현 금지. 사실만 담백하게 한 문장
- 카드 본문·부연은 한 문장. 두 문장이 필요하면 tip으로 빼거나 슬라이드를 쪼갠다
- 한 슬라이드 = 한 메시지. 요소가 넘치면 슬라이드를 쪼갠다

**조작(내비게이션) 성공 기준 — 어길 수 없다:**
- 페이지 이동은 **좌우 화살표 버튼 · 하단 점(dot) 클릭 · 키보드(←/→/스페이스)**로만 일어난다
- **본문(화면) 아무 곳 클릭으로 페이지가 이동하면 실패다.** `#deck`·`body`·`.slide`에 이동용 click 리스너를 절대 달지 않는다 (강의 중 화면을 가리키며 클릭해도 슬라이드가 넘어가면 안 된다)
- 완성 후 반드시 확인: click 리스너는 JS의 `_buildDots()`(점)와 `_bindButtons()`(화살표 버튼) 안에만 있어야 한다

**시각 검수 성공 기준 — 어길 수 없다:**
- **기본 검수 뷰포트는 2133×1200 CSS px**이다. 사용자가 확인한 실제 강의 브라우저 크기이므로 로컬 서버에서 전 슬라이드를 이 크기로 렌더하고 최종 시각 판단도 이 화면을 기준으로 한다. 브라우저 배율 100%로 고정한 테스트 뷰포트 값이며 이미지의 픽셀 크기와 구분한다.
- 1280×800은 작은 화면의 넘침을 확인하는 보조 검수로 유지한다. 1920×1080 검수만으로 기본 검수를 대신하지 않는다.
- 모든 슬라이드에 패스트캠퍼스 로고가 깨지지 않고 보이는지 확인한다 (에셋 경로가 루트 절대경로여야 한다)
- 애니메이션이 모두 끝난 상태도 캡처해 카드·캡션·이미지의 최종 배치를 확인한다
- 표지는 이미지 crop, 텍스트와 피사체의 거리, 네거티브 스페이스 중복을 확인한다
- 생성 이미지는 스토리보드의 인물 수·출발점·현재 위치·목적지·방향·흔적과 대조한다
- 카드 6장 슬라이드는 높이·패딩·제목·본문을 줄여 억지로 맞추지 않았는지 확인한다
- **넓은 화면을 채우기 위해 카드나 컨테이너를 가로로 늘리지 않는다.** 로고·제목·본문의 실제 크기와 적절한 줄 길이를 먼저 정한 뒤 내부 padding, 카드 사이 gap, 외곽 padding 순으로 폭을 계산한다. 독립된 요소 묶음은 `width: fit-content` / 내용에 맞는 grid 열과 `max-width: 100%`를 우선 검토하고 중앙에 배치한다.
- 뷰포트 비율(`width: 70%`, `100%`, `vw`)만으로 요소 묶음의 폭을 정하지 않는다. 2133px에서 카드가 긴 빈 상자로 늘어나는지 확인한다. 폭을 줄일 때 글자·로고 크기도 함께 줄이지 않으며, 전체 폭이 의미상 필요한 표·타임라인·흐름도는 예외로 판단한다.

### deck.html과 함께 feedback.md를 만든다 — 완료 게이트

**슬라이드 HTML만 만들고 끝내면 미완료다.** 덱을 새로 만들 때마다 사용자가 바로 장별 피드백을 적을 수 있는 짝 파일을 반드시 함께 만든다.

- 경로: `artifacts/<part>/outputs/<clip>.html` → `artifacts/<part>/_feedback/<clip>.md`
- `assets/feedback-template.md`를 복사해 frontmatter의 산출물·날짜·상태와 문서 제목을 채운다
- `## 1차`의 `### 2. 개별` 아래에 HTML의 **모든 슬라이드를 번호와 실제 제목으로 미리 펼친다**

```markdown
#### 슬라이드 1 — {실제 제목}

-

#### 슬라이드 2 — {실제 제목}

-
```

- 1번부터 마지막 장까지 하나도 빠뜨리지 않는다. HTML의 `<article class="slide">` 개수와 피드백 파일의 `#### 슬라이드 N` 개수가 같아야 한다
- 피드백 파일이 이미 있고 내용이 있으면 **절대 덮어쓰지 않는다.** 기존 차수와 사용자 피드백을 보존하고, 구조 변경으로 새로 생긴 슬라이드의 빈 항목만 해당 차수에 추가한다
- 슬라이드를 삭제하거나 제목을 바꿔도 기존 피드백 기록은 지우지 않는다. 새 차수에 현재 슬라이드 목록을 다시 펼쳐 이력을 보존한다

### 슬라이드와 대본을 한 세트로 만든다 — 완료 게이트

슬라이드 제작 후 최종 화면에 맞춘 **전체 발표 대본**을 함께 작성한다. HTML 주석의 발표 노트나 스토리보드의 설명으로 대신하지 않는다. 대본을 쓰기 전에 [references/narration-script.md](references/narration-script.md)의 형식·말투를 읽는다.

- 경로: 덱과 같은 루트의 `<part>/_script/<clip>.md`. `codex/`, `codex-v2/` 같은 별도 제작 루트에서도 같은 규칙을 쓴다.
- 전체 제목은 `## {클립 제목} 슬라이드 대본 (N장)`, 각 장은 `## 슬라이드 i/N — {실제 슬라이드 제목}`으로 쓴다. 표지는 `(표지)`를 붙인다.
- 실제로 읽을 수 있는 구어체 문단으로 화면의 핵심·설명·다음 장 연결을 담는다. 사용자 설명의 핵심을 새로운 사례로 대체하지 않는다.
- 내용·제목·순서·장수가 바뀌면 대본도 함께 갱신한다. 비교 슬라이드의 제목에 v1·v2가 있으면 대본에도 같은 제목을 쓴다.
- 검수 시 대본을 최종 HTML·클립 소스와 대조한다. 소스의 ‘슬라이드 없이 말로’ 내용은 직전 장 대본 끝에 이어 쓰며 별도 슬라이드 번호를 만들지 않는다.
- 완료 보고에는 슬라이드 접근 경로와 대본 파일 링크를 함께 제공한다.

## Step 5: 완료 보고

```
✓ artifacts/{part}/_storyboard/{clip}.md   (이번에 만든 경우만)
✓ artifacts/{part}/outputs/{clip}.html             (최종 결과물)
✓ artifacts/{part}/_feedback/{clip}.md     (슬라이드별 피드백 입력 파일)
✓ artifacts/{part}/_script/{clip}.md       (최종 화면과 일치하는 전체 발표 대본)
  공개 주소: /{part}/{clip}
  커리큘럼 위치: Part N › Chapter N › ChNN-NN. {클립 제목}

  주제: {한 줄 주제}
  구성: 총 N장 — {타입 목록}
  조작: ← → 버튼·하단 점·키보드로 전환 (본문 클릭으로는 이동 안 함)
  근거 없는 연결용 슬라이드: N개 (있으면 번호 나열, 없으면 생략)
```

사용자가 준 구성을 그대로 쓴 경우에는 스토리보드 줄을 빼고, 대신 아래를 적는다:
- `구성: 주신 스토리보드 그대로 (N장)`
- 규칙 위반이 있었으면 슬라이드 번호와 항목을 한 줄씩
- 더 나은 구성이 보였다면 제안 한 줄 (반영하지 말고 제안만)

## Step 6: 수정 요청 처리

**구조 변경**(슬라이드 추가·삭제·순서·핵심 메시지): 스토리보드를 먼저 고치고 → HTML을 고친다. **두 파일은 항상 일치해야 한다.**
슬라이드 수가 바뀌면 `data-index` 전부와 `<span id="tot">`를 갱신한다.

**텍스트·디자인·타이밍만 변경**: HTML만 고쳐도 된다.

**조정 포인트 안내**: 사용자가 직접 만질 수 있는 값은 위치를 알려준다.
형식: `"조정하고 싶으면 CSS의 .클래스명 에서 속성명 값을 바꾸시면 됩니다"`
색은 `:root`의 색 변수, 등장 속도는 JS `_runSlide()`의 `150 + n * 260` 숫자를 가리킨다.

**사용자 수동 편집 보존**: 사용자가 직접 고쳤다고 말한 부분은 절대 되돌리지 않는다. 요청된 항목만 정확히 수정한다.

## 자주 나는 실수

- **원자료를 받고도 구성 확정을 건너뛰어 HTML부터 씀** — 가장 흔하고 가장 나쁜 실패. 근거 없는 문장이 섞인다
- **표지 없이 본문(주제 선언)부터 시작함** — "뭘 배울지"라는 그릇이 없어 시작부터 지친다. 1번은 반드시 표지 패턴(`scene scene--cover` 등)
- 반대로, **이미 확정된 스토리보드를 받고도 스토리보드를 다시 만듦** — 사용자가 정한 구성을 흔드는 실패
- **에셋을 상대경로(`./assets/...`)로 참조함** — 배포 주소 `/<part>/<clip>`에서 로고가 깨진다. 루트 절대경로만 쓴다
- **덱과 부속 문서의 이름이 어긋남** — 넷은 확장자만 빼고 이름이 같아야 짝을 찾을 수 있다
- **옆 클립 소스까지 끌어옴** — 범위는 `_source/<clip>.md` 파일 하나다
- **소스 frontmatter의 `슬라이드: N장`을 무시하고 장수를 스스로 정함** — 그 숫자가 우선이다
- **실습·데모 클립의 슬라이드를 만듦** — 이론 클립만 만든다
- **`index.html`에 새 덱 링크를 추가하지 않음** — 목록에 없으면 아무도 못 찾는다
- **본문 클릭으로 페이지가 넘어가게 만듦** — 이동은 버튼·점·키보드로만
- **deck.html만 만들고 feedback.md를 안 만듦** — 모든 슬라이드 번호·제목이 펼쳐져 있어야 완료다
- 스토리보드에 자리표시자를 남긴 채 HTML로 넘어감 — 결국 HTML 단계에서 즉흥 창작하게 된다
- **`assets/example-storyboard.md`를 안 열고 형식만 보고 씀** — 근거 칸·색 배정·용어 규칙이 얕아진다
- **덱 전용 CSS를 베이스 템플릿에 넣음** — 템플릿은 모든 덱의 공통분모만 갖는다
- **글자만 있는 박스로 덱을 채움** — 가장 비싼 실패. 기준 덱은 12장 중 11장에 이미지·SVG가 있다
- **박스 격자를 커스텀 클래스로 새로 만듦** — 같은 역할인데 크기·여백만 다르게 만든 중복 스타일
- **이미지·카드를 작게 넣음** — 장면은 가용 높이를 충분히 쓰며 묶음의 최대 폭을 확인한다
- **골든셋을 주제가 다르다고 건너뜀** — 골든셋은 판단 기준을 가르친다. 적용 범위에 맞는 참조를 읽되 최신 승인 정답을 우선한다
- 도식의 요소 수와 열 규격 불일치 — 실제 요소 수에 맞춰 정렬을 검수한다
- 같은 대상의 색이 슬라이드마다·덱마다 바뀜 — 「강의 전체에서 고정된 색 배정」 표를 먼저 본다
- 소스에 없는 수치로 METRIC 슬라이드를 만듦 — METRIC은 실제 수치가 있을 때만
- 요소를 한 장에 넣기 위해 높이·여백·글자를 과도하게 줄임 — 메시지 단위로 분리한다

## 슬라이드 HTML 저장 위치 — 사용자 확정

모든 슬라이드 HTML은 `artifacts/partN/outputs/<clip>.html`에 저장한다. 파트 폴더 바로 아래에 HTML을 만들지 않는다. 대본·소스·스토리보드·피드백·이미지는 각 파트의 기존 `_script`, `_source`, `_storyboard`, `_feedback`, `_images`에 둔다. 선택된 비교 덱은 정식 경로로 승격했고 `codex`·`codex-v2`·`codex-v3` 폴더는 사용자 요청으로 정리했다. 슬라이드와 대본은 `artifacts/`의 실제 파일을 직접 수정한다.

### 비교 작업물 승격 — 작업 폴더는 언제든 삭제 가능

- 승격은 선택한 HTML·대본·소스·스토리보드·피드백과 필요한 에셋을 정식 `artifacts/`·`assets/` 경로에 **실제 파일로 복사하거나 이동**하는 작업이다. 기존 정식 파일의 사용자 편집은 보존한다.
- **슬라이드 작업 파일에는 심볼릭 링크를 만들지 않는다.** 작업 폴더에서 정식 파일을 가리키는 링크도, 정식 파일에서 작업 폴더를 가리키는 링크도 금지한다. 작업 폴더를 다시 열어 수정해도 정식 파일이 바뀌면 안 된다.
- 정식 HTML의 에셋 경로와 인덱스·짝 문서를 정식 경로로 갱신한다. 작업 폴더 삭제 후에도 링크·이미지·대본을 모두 사용할 수 있어야 승격 완료다.
- 정리할 때는 작업 폴더의 링크를 따라가지 않고 링크 자체만 제거한다. 삭제 전후 정식 파일의 해시가 같은지 확인한다.
- 위 규칙은 임시·비교 슬라이드 작업물에 적용한다. `.agents/skills/fastcampus-slide`가 `.claude`의 스킬 원본을 가리키는 기존 스킬 공유 링크와는 별개다.
